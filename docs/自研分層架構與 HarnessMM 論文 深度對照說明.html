一、 核心架構總覽：三層式分工與學術對照

將自研架構之「高階 Orchestrator、中階 Worker/Specs、低階 Executor」三層設計與 HarnessMM 前沿框架進行比較：

比較維度 您的自研架構設計 學術論文 (HarnessMM & 前沿 Agent)
總體目標 分層管控、提升執行穩定性與容錯能力，同時兼顧運算效率。 透過 受保護的決策重用 (GDR) 與 遞歸自我改進 (RSI) 降低 Token 消耗，並維持或提升任務成功率。
高階層級 高階技能層 (Orchestrator)：透過檢索清單進行領域匹配與任務拆解。 領域與任務配置：由高階策略或指令集 (Instructions) 界定任務範圍與代理人行為邊界。
中階層級 中階技能層 (Worker/Specs)：確認 skill contract 與提供重規劃所需的背景規格書。 伴侶配置與規格 (Companion Specs)：透過反覆運算與訓練產生最佳化的提示詞、驗證規則與領域支援。
低階層級 低階技能層 (Executor/EDG)：組成有向拓樸圖，執行單一腳本與參數確認。 可執行決策圖 (EDGs)：儲存精確動作、字面參數 (Literal Arguments)、相依性與公開執行護欄 (Public Guards)。
容錯與重規劃 三層回退機制：低階出錯退回前一個成功節點 → 中階根據規格書重規劃 → 高階重新檢視領域。 Guard 觸發與 Fallback：透過公開護欄驗證收據 (receipts)，失敗、未支援的證據或選擇器棄權時，將控制權交還給慢速模型 (Slow Actor) 進行修正。

二、 論文核心機制與自研架構的深度對應

1

有向拓樸圖 (EDG) 與參數具體化

EDG Protocol
論文觀點 (HarnessMM)

傳統 Harness 在每個工具回傳後重新呼叫大模型進行慢速推理，浪費大量 Token。HarnessMM 透過 EDG 將已經解析好的動作、具體字面參數（Literal Arguments）及因果相依性（Dependencies）固定在圖結構中，後續靠工具回傳的「執行收據 (Receipts)」直接驅動下一步。

您的自研架構對應

中階確認 skill contract 後，組合出低階技能執行時的有向拓樸圖。這完美對應了「以圖結構取代每次動態盲目對話」的設計理念，有效收斂模型發散並提升執行效率。

2

決策重用與回調替代 (GDR & CCS)

GDR / CCS
論文觀點 (HarnessMM)

系統利用 Guarded Decision Reuse (GDR) 啟動持久化決策，並透過 Certified Callback Substitution (CCS) 在原生介面上直接執行該動作，省去對應的慢速推理回調。

您的自研架構對應

低階技能層在實際執行單一腳本工具時，輸入參數與步驟均已確認，並在節點間依循圖結構運行，直接落實了「跳過重複推理、以結構化方式執行已知動作」的工程實踐。

3

錯誤回報、防護欄與多層次回退

Guards & Fallback
論文觀點 (HarnessMM)

當遇到非預期回傳、非零返回碼 (Nonzero Return Codes) 或護欄驗證失敗時，系統會觸發 Fallback，將控制權交還給推理模型。

您的自研架構對應

當低階節點多次出錯，系統會「返回前一個成功執行的原子行為節點」，並透過中階背景規格書重新規劃；若仍無法解決，則一路往上退回至高階重新審視領域，具備強健的容錯能力。

4

背景規格書與遞歸自我改進 (RSI)

RSI Strategy
論文觀點 (HarnessMM)

系統透過反覆訓練與驗證，精煉出最佳化的伴侶配置與規格，在部署前凍結以作為穩定引導依據。

您的自研架構對應

中階層的「背景技能規格書」平時提供穩定的執行指引，出錯時作為重規劃的核心知識庫，兼顧了泛化性與邊界控制。

三、 技能合約 (Skill Contract) 的職責分工與驗證機制

職責劃分哲學：中階定義，低階執行

針對 Skill Contract 的確認與驗證，架構採用明確的職責劃分：「中階負責定義與撰寫，低階負責即時檢核與強制執行」。

中階層 (Worker / Specs)

負責「合約的定義與規劃」

  • 角色：規格制定者 (Authoring & Planning)
  • 職責：規範技能應該長什麼樣（例如必填參數、型態、預期輸出結構）。
  • 原因：中階具備領域知識，能在組裝有向圖時確保所選技能符合子任務需求。
低階層 (Executor / Controller)

負責「合約的即時檢核與強制執行」

  • 角色：邊界檢查與防火牆 (Validation & Enforcement)
  • 職責：呼叫工具前，用程式化硬體邏輯（Schema 驗證）檢查輸入參數與前置條件。
  • 學術對應：正如 HarnessMM 指出："Literal closure is enforced by schema checks"，直接以代碼驗證參數與 Guards。
零 Token 消耗的高效攔截

避免每次都讓 LLM 讀合約判斷參數是否正確。低階直接透過代碼（Pydantic/Schema）確認，省時且節省推理成本。

嚴格的邊界防護 (Guard Enforcement)

作為系統防火牆，一旦低階發現參數或工具收據不符，瞬間拒絕執行並將錯誤打包向上回報，防止污染後續環境。

四、 規格書的細緻劃分：中階介面與低階腳本的協作

中階技能規格書

Interface, Contract & State Verification
1. Skill Contract（技能合約）

規範該技能所需的必填/選填輸入參數、資料型態以及預期的輸出 JSON 結構。

2. 當前狀態確認

確認目前環境的 state 是否滿足執行該領域任務的前置條件。

3. 重規劃指引 (Re-planning Direction)

低階報錯退回時，中階透過背景規格書理解合約何處被違反，進而調整策略。

低階技能規格書／執行層

Scripts, Literal Arguments & Execution Flags
1. 具體字面參數 (Literal Arguments)

將解析好的具體檔名、數值、字串直接綁定在有向圖節點（EDG）上。

2. 腳本與命令後綴 (CLI Flags & Options)

明確定義工具腳本的實際用法與後綴細節控制，如 --create、--cancel、--force。

3. 公開護欄與收據比對 (Guards & Receipts)

利用返回碼 (Return Code) 與收據 (Receipts) 決定下一步是否放行或觸發退回。

五、 異常處置、運行時狀態與副作用管理

在架構發展的實務中，當低階節點多次出錯需要退回到上一個成功節點時，如何有效處理系統狀態與歷史至關重要。以下為結合記憶體與任務模板的關鍵設計：

1. 狀態與歷史的分離

Runtime State vs. Graph Content

運行時狀態包含已完成的原生收據 (native receipts)、剩餘圖節點與公開事件歷史。執行推進時動態更新狀態，無需重寫整個圖架構。

2. 錯誤摘要與收據回報

Receipts & Fallback Trigger

遇到非零返回碼 (nonzero return codes) 或護欄驗證失敗時，將控制權連同錯誤摘要與執行收據交還給中階/慢速模型修復。

3. 記憶體與任務模板

Memory & Ledger Templates

透過結構化工作任務模板或應用程式記憶體 (Application memory) 保留關鍵變數與狀態變更，避免動態重規劃時上下文失控。

六、 結語與架構展望

邁向「企業級穩定生產」

您的自研分層架構完美體現了現代 Agent 控制系統的演進方向。透過中階的規格與合約制定、低階的有向拓樸圖 (EDG) 與確定性腳本執行，再加上運行時狀態分離與多層次的錯誤回退迴圈，系統在維持高泛化性的同時，精準鎖定了執行邊界，並實現了顯著的 Token 節省與高容錯率。
