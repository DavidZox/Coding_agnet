# 工作流撰寫規範

> 寫給：要新增或修改工作流（`skills_system/workflows/<名稱>.md`）的人。工作流是「多步驟、會重複做的維運流程」，步驟呼叫既有的技能；
> 步驟由程式照文本推進（`agent_core/workflow.py`），模型只在判斷點出手。技能本身怎麼寫見〈[技能撰寫規範](技能撰寫規範.md)〉。

## 什麼時候寫成工作流

- 同一件事會一再發生、做法固定（例：工作包卡住的處理、照手冊改設定、派工作包並確認跑完、重啟容器並確認、改派）。
- 「做完了沒」要由程式判斷，不能只靠模型說（每一步的檢查與最後的成功判準都由程式跑）。
- 不適合：每次做法都不一樣、要邊查邊想的調查——那種交給主對話或任務引擎（task_run）；任務引擎的計畫可以把工作流當成其中一步。

也可以用 `/make_skill <名稱>` 從一段做對的對話產生草稿：程式排版、用同一套規則驗證，使用者看過預覽再核准（寫到 `workflows/`、SKILLS.md〈工作流〉）。

## 格式

```markdown
---
type: Workflow
title: 工作包卡住的處理                    # 短標題
description: 工作包卡住、不往下一站：…       # SKILLS.md〈工作流〉的一行：什麼情境用它
version: 0.1.0
dependencies: ["workpackage_status", "rmf_handshake", "file_ops"]   # 步驟用到的技能（程式核對）
changes_state: true                        # 有沒有會改變狀態的步驟（程式核對）
---

# 用途
# 需要的資訊
* `{wp_id}`：卡住的工作包編號（例：`WP_L2`）
* `{note_file}`：處理紀錄要附加到哪個檔案（選填，例：`ops_notes/2026-10-10.md`）
* `{wp_id2}`：…（選填，預設 `auto`）
# 步驟
1. 【執行】查狀態：`EXECUTE: scripts/workpackage_status_cmd.py {wp_id}`　檢查：輸出有「[PASS]」
2. 【執行】查交握：`EXECUTE: scripts/rmf_handshake_cmd.py status {wp_id} --seconds 15`　檢查：輸出有「的交握狀況」或「已經 COMPLETED」
3. 【檢查】看第 2 步的判斷：「已經 COMPLETED」→ 結束；「完成訊號多半遺失了」→ 第 4 步；其他 → 結束
4. 【執行】補發：`EXECUTE: scripts/rmf_handshake_cmd.py fin {robot}`　檢查：輸出有「已經由 manual_trigger 補發」
5. 【確認】<要使用者確認什麼>
6. 【告知】<要回報什麼>
# 成功判準
* `EXECUTE: scripts/workpackage_status_cmd.py {wp_id}` 輸出有「COMPLETED」
* 第 4 步的輸出有「已經由 manual_trigger 補發」
# 異常與注意事項
* …
```

## 四種步驟

| 步驟 | 寫法 | 程式怎麼做 |
|---|---|---|
| 【執行】 | 一行寫完：標題、`` `EXECUTE: scripts/<腳本> <參數>` ``，可加 `檢查：輸出有「A」或「B」` | 參數只用到「需要的資訊」與 `{today}`／`{now}` → 程式直接執行；用到別的 `{名稱}` → **判斷點**：模型只填那幾個值（腳本由規格固定），前面判斷點填過的同名值直接沿用。執行完由程式比對檢查；技能回 `[ERROR]`、而且值是模型填的 → 帶著錯誤請模型改一次值；其他失敗 → 工作流停在這一步 |
| 【檢查】 | `看第 N 步：「輸出裡的字」→ 第 M 步；「另一種字」→ 結束；其他 → 第 K 步` | 程式依序比對，第一個成立的分支就走；都不成立走「其他」；沒有「其他」、或沒有分支（只寫要判斷的事＝關卡）才交給模型選 |
| 【確認】 | 寫要使用者確認什麼 | 工作流停下來；主對話執行 `workflow_run --continue`，系統的確認畫面列出這個【確認】與接下來會改變狀態的步驟，使用者核准才繼續 |
| 【告知】 | 寫要回報什麼 | 列進報告，主對話照報告回答 |

規則（`agent_core/workflow_spec.validate`，`evals/workflow/selftest.py` 每一份都會檢查）：

- 步驟從 1 連號；【執行】一定有命令，腳本要存在；分支只能往後跳（沒有迴圈）；「看第 N 步」只能看前面的【執行】步。
- `dependencies` 要列到步驟用的每一個技能；`changes_state` 要跟步驟一致（會不會改變狀態用確認關卡同一套判斷）。
- 「需要的資訊」寫 `選填` 的沒給時，用到它的【執行】步驟自動略過；`` 預設 `…` `` 可以用 `{today}`、`{now}` 與其他需要的資訊（例：config_edit 的 `{block}` 預設 `id: {robot}`）。
- 成功判準兩種寫法程式驗證得了：`` `EXECUTE: …` 輸出有「X」``（唯讀的命令）、`第 N 步的輸出有「X」`；其他寫法照列在報告裡、不算通過或沒過。

## 寫得穩的訣竅（2026-10-23 實測）

- **檢查與分支的字照技能輸出抄**：技能的第一行已經寫好判斷（`交握狀況：完成訊號多半遺失了`、`已完成：COMPLETED`），用那幾個字。
- **判斷點越少越穩**：值能從「需要的資訊」來就不要讓模型填；要寫進檔案的紀錄，開頭的時間、工作包、機器人用模板寫死
  （`--text "## {now} 工作包 {wp_id}（機器人 {robot}）\n{note}"`），模型只寫內容——第一版只讓模型寫整段，26b 有一次漏了機器人。
- **聽 topic 的步驟給夠時間**：工作流沒有迴圈，不能「再聽一次」。交握要聽 15 秒（授權逾時 10 秒＋冷卻 10 秒），聽 4 秒會碰上冷卻、
  判斷成「這幾秒剛好沒有授權」，改派的工作流第一版就停在那裡。
- **程式做得到的不要交給判斷點**：改 YAML 設定檔的一個值用 `file_ops set {file} {key} {value} --after "{block}"`（`{block}` 預設 `id: {robot}`；程式在那一台的區塊裡找那一行），
  不要讓判斷點抄「要取代的原文」——e4b 抄不出只對到一處的多行原文（config_edit 第一版）。改成 set 之後整個工作流沒有判斷點、0.3 秒。
- **會改變狀態的步驟不用另加【確認】**：開始時的確認畫面已經列出它們；【確認】只放在「要看前面的結果才決定、使用者應該先看一眼」的地方。
- **選填的資訊讓整步可以略過**：命令用到選填、又沒給的 `{名稱}` 時那一步略過，確認畫面也不列它（config_edit 的 `{backup}`）；標題裡用 `{名稱}`，畫面與報告會代入實際的值（「只改 tb1 那一段的 max_speed」）。

## 怎麼測

```bash
python3 evals/workflow/selftest.py                          # 離線：每一份都驗證得過、跟 SKILLS.md 對得上（新增工作流要在 SKILLS.md〈工作流〉加一行）
python3 evals/workflow/sandbox.py --model gemma4:26b        # 沙盒裡直接執行（技能真的跑、判斷點用真模型），用對應的維運情境計分
python3 evals/ops/run.py --only <情境>                       # 主對話會不會選用工作流（AGENT_WORKFLOWS=0 是「沒有工作流」的對照）
```

自己試一個工作流：對話裡 `/workflow show <名稱>` 看步驟（程式解析出來的樣子）、`/workflow <名稱> 名稱=值 …` 直接執行（不經過 AI 選擇，
確認畫面列出實際要執行的命令）；不用互動的 `python3 Agent_Runner.py --workflow <名稱> 名稱=值 … [--yes]` 印出報告與結束碼（排程、之後的心跳用）。

新的工作流在 `evals/workflow/sandbox.py` 的 `CASES` 加一個案例（用哪個維運情境的世界與檢查、怎麼呼叫、預期結束的狀態）。
