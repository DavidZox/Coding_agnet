## 1. 構想的摘要（我的理解；第 2 輪使用者沒有更正）

**三層**

| 層 | 讀的知識檔 | 做什麼 | 出錯時（三級回退） |
|---|---|---|---|
| 高階：Orchestrator | `DOMAIN.md`：每個領域的邊界、說明、入口技能 | 判斷問題屬於哪個領域，寫出第一層的子目標，連同使用者的原始問題交給那個領域 | **第 3 級**：領域判錯或越界時，清掉那個領域的上下文，帶著「不是這個領域」重新分流。全部用完時停下來，寫失敗報告給人 |
| 中階：Domain Worker | 領域的 `SKILLS.md`；複合技能的規格（合約、`topology` 的 `depends_on`／`sub_skills`、SOP 與替代做法） | 挑技能，做合約檢查：必填參數先從上下文找，能自己查的自己查，查不到或要使用者決定的才問。補上漏掉的前置依賴，排出決策圖（DAG／EDG）交給低階 | **第 2 級**：收到低階「結果沒有用」時，照 SOP 換替代做法重排。重排太多次就熔斷，把摘要往上報 |
| 低階：EDG Executor | 工具規格：字面參數、`# 語法`、`# 回傳`、`# 異常` | 照圖一個一個執行腳本。執行前用程式檢查參數，不花模型呼叫；照收據決定下一步 | **第 1 級**：參數錯、逾時這類技術錯誤在原地修正重試。結果沒有用（例如只有 `/rosout`）時往上交給中階 |

**跨層的機制**
- **子目標往下傳**：每一層交下去時都寫一個這一層的子目標，同時附上使用者的原始問題。下一層照子目標從原文挑要的參數。
- **子工作階段隔離**：試錯留在子工作階段裡，只把整理好的結果交回主對話。
- **執行狀態跟圖分開存**：收據、事件、帳本另外存。重排時不用重寫整張圖。
- **12 種異常**分到三層（低階 4、中階 4、高階 4），每一種都有對策。

### 跟業界做法的對照（2026-11-19 使用者問，第 5 步 5-2 的評測期間）

使用者問了兩件事：(1) 改成「階層技能書＋有向圖（DAG）」是不是比較好？之前主對話直接執行很不穩、任務引擎出錯時反應很差，是不是技能書用錯了，
業界有沒有在用？(2) 是不是沒有人分這麼多層？分層是觀察到「一步一步做每次都不穩、出錯也不能穩定糾錯」，加上讀了很多論文才這樣做的，這樣不好嗎？

下面的出處是公開的文章、論文與框架（這一輪沒有重新上網查原文，細節以原文為準）；數字是我們自己的評測。

**結論**：以我們的條件（本地小模型、離線、長任務要穩），這個方向比之前好，評測數字支持；每一塊都有對應的公開做法，分層本身是很標準的做法，
不是缺點。沒有一個現成框架跟這個組合完全一樣：每一層都由程式核對、最底層是照收據執行的決策圖、整套為小模型設計，這是它的特色。

**之前不穩，不是技能書用錯**
- 技能書（索引＋用到才載入規格）就是現在的主流做法：Anthropic 的 Agent Skills（2025）也是先只給名稱與一句說明、用到才載入全文
  （progressive disclosure），Claude Code 的 skills 也是。
- 不穩的原因在別處：一個小模型在一條越來越長的對話裡，同時負責規劃、執行、判斷做完沒、記住出錯的原因；試錯都留在主對話；任務引擎把計畫
  一次排好，出錯時沒有帶著原因重新規劃，「做完了沒」也是模型說了算（第 6 節的 29：沒做完卻回報完成）。

**各層對應的公開做法**

| 這個架構 | 一般的叫法 | 公開的例子 |
|---|---|---|
| 高階：交給領域（DOMAIN.md） | routing、handoff | Anthropic〈Building effective agents〉（2024）的 routing、orchestrator-workers；OpenAI Agents SDK 的 handoffs；Google ADK 的階層式多代理 |
| 技能書分層、用到才載入 | progressive disclosure | Anthropic Agent Skills、Claude Code skills |
| 中階：複合技能（SOP）→ 合約 → 排圖 | workflow／SOP、plan-and-execute | MetaGPT（把 SOP 寫進流程）、LangGraph、LangChain 的 plan-and-execute |
| 低階：照 DAG 執行、照收據守門 | 先規劃成 DAG 再執行 | LLMCompiler、ReWOO、HarnessMM（EDG＋收據） |
| 子工作階段：自己的對話，只交回報告 | subagent、context isolation | Anthropic 的多代理研究系統（2025）、Claude Code 的 subagents |
| 程式核對事實與做完沒、schema 限制輸出 | structured outputs、guardrails | JSON schema 輸出（Ollama、OpenAI）、OpenAI Agents SDK 的 guardrails |
| 三級回退、帶著上一次的經過重新規劃 | replanning、reflection | LLMCompiler 的 replan、Reflexion |

〈Building effective agents〉的核心建議跟這個方向一致：做法固定的寫成固定流程（workflow），只有需要彈性的地方才交給模型判斷。

**分這麼多層的例子**（分層的理由——把責任切開、每一層就近發現與修正錯誤——是這類系統分層的標準理由）
- **機器人的三層架構**：3T（Bonasso 等，1997）與 Gat〈On Three-Layer Architectures〉（1998）把系統分成規劃（deliberative）、排程序（sequencer，
  用 RAP 這種寫好的程序）、技能（reactive skills，執行與監控）。對應這裡的高階（分流）、中階（複合技能＝寫好的程序）、低階（照圖執行、看收據）。
- **Nav2 的 behavior tree 與 recovery**：出錯先在原地修（清 costmap、原地轉、後退），修不好重新規劃路徑，再不行才放棄、交給上層——就是三級回退的想法。
- **HTN 規劃**（hierarchical task network）：任務照「方法」拆成子任務、最後是基本動作；複合技能就是「方法」。
- **LLM 的 agent**：Microsoft Magentic-One（2024：Orchestrator 記 task ledger 與 progress ledger，卡住時帶著新的事實重新規劃、換人做）、Agent S
  （2024：manager 拆子任務、worker 執行並反思）、HuggingGPT（2023：規劃 → 選模型 → 執行 → 回答）、Voyager（2023：技能庫、執行錯誤回饋、自我驗證）、
  Google ADK 的多層 agent。

**為什麼小模型更需要結構**：小模型最弱的是長流程裡自由發揮；把每一步縮成「從清單選一個」「填 schema 的幾個欄位」最穩。大模型的系統常把核對、
重試交給模型自己，結構可以比較輕；小模型做不到，就要由程式補上。

**走一遍**（現在的做法）

問題：「amr_base_sw 裡哪些 Python 檔用到 `use_sim_time`？各在哪個函式？」
1. **高階**：主模型分工 `{"domains": [{"domain": "repo_analysis", "goal": "在 amr_base_sw 的 .py 裡找 use_sim_time，列出檔案與所在的函式", "items": ["哪些 Python 檔用到 use_sim_time", "各在哪個函式"]}]}`，程式核對之後交給中階。
2. **中階**：挑 `py_usage`；合約是 `name=use_sim_time`、`path=amr_base_sw`（路徑找不到時照 `fetch` 用 find_file 查一次）。骨架代入參數就是決策圖：`search_text`（.py、整個字）→ 每個檔案一個 `code_ast_reader --refs`（檔案由程式從收據帶入）；報告由程式照收據整理（每一處的檔案:行號與所在的函式）。
3. **回退**：
   - 參數錯、逾時：第 1 級，修正後重跑。
   - 範圍裡的 .py 沒有：第 2 級，看範圍裡的 C++ 檔，有就換成 `cpp_symbol`，沒有就在整個工作目錄找一次；命中太多就問使用者縮小範圍。
   - 問的其實是容器裡正在跑的參數值：中階回「不屬於這個領域」，程式排除、主模型改分給 `robotics_infra`（第 3 級）。
4. **回答**：主模型照報告填 `answers`（每一項的回答與出處），程式核對出處、數字與名稱，照項目排給使用者（附出處那一行的原文與決策圖的連結）。

| 高 1 分流錯 | 清掉那個領域的上下文，帶著排除條件重新分流 | 模型：Orchestrator 照中階的回報 | 做：每個領域最多進一次；沒有可分的領域就是高 4 |
| 高 2 意圖漂移 | 對照原始問題，漂移就重排（漂移分數 > 0.65） | **跟圖不同**：分數不可靠，也是門檻值 | 改成結構：分流時把原始問題拆成要回答的項目（結構化輸出），往下傳；最後由程式檢查每一項都有核對過出處的答案，或明寫查不到與原因。沒答到的項目只補那幾項，不重排整張圖 |
| 高 3 跨領域資源衝突 | 照優先權仲裁 | — | 第一版唯讀，不做。會改狀態的領域回來時再談（確認關卡、鎖） |
| 高 4 全部用完 | 停下來，寫診斷報告引導人工介入 | 程式 | 做：寫做了什麼、哪裡失敗、收據的 `#編號` |

- 次數（第 1 級一次、重排的上限）是預算，不是調來讓某一題過的門檻；收斂與否另外由「不重跑同樣的節點」判斷。
- **「返回前一個成功的節點」**（對照報告的寫法）：唯讀的步驟不需要。會改狀態的步驟就算退回節點，狀態也不會改回來，要另外設計（停下來問人，或明寫的復原步驟）。第一版不做。

### D6 合約檢查的自動補參數
- **架構圖**：背景工具或歷史上下文找得到的（檔案路徑、容器名稱）自己補，不吵使用者；主觀意圖、敏感憑證、本地完全找不到的才停下來問（`validate_contract` 的 `can_auto_fetch`）。
- **定案**：「能不能自己補」寫在規格裡，由程式判斷，不讓模型臨時決定。
  - 工具規格的每個必填參數寫明怎麼找：`fetch`（用哪個工具、怎麼帶參數，例如路徑用 find_file、容器用 docker_containers）或 `ask`（要使用者決定：意圖、要改哪一台、憑證）。
  - 補的順序：
    1. 原始問題、子目標或歷史裡有（附出處）：直接用。
    2. 有 `fetch`：查一次。剛好一個就補上；好幾個時選哪一個是使用者的意圖，把候選列給使用者選（子目標寫明「全部」時，每個候選各排一個節點）；一個都沒有就問使用者，或回報找不到。
    3. `ask`：問使用者。
  - 不往下展開：查參數用的工具，它自己的參數必須已經確定。
  - 自己補的值寫進圖與收據，最後的回答列出「自己補的」，補錯時看得出來。
  - 憑證一律不自己找（第一版的領域也用不到）。

### D7 層與層之間傳什麼
- **架構圖**：每一層往下都帶使用者的原始問題與這一層的子目標，下一層照子目標從原文挑參數；試錯留在子工作階段，往上只交整理好的結論。
- **定案**：各層之間都用有長度上限的 schema。
  - **高 → 中**：原始問題（原文；使用者貼的長內容先存成 `#編號`，傳引用）、子目標、要回答的項目（D5 高 2）、引用的 `#編號` 與核對過的事實、已經排除的領域。
  - **中 → 低**：決策圖（節點的工具、字面參數、依賴、預期）。判斷節點另外帶子目標、原始問題與它要看的收據。
  - **低 → 中**：每個節點的收據（狀態、錯誤種類、數量、項目）與完整輸出的 `#編號`。
  - **中 → 高**：
    - 狀態：做完、死路、不在這個領域（附理由）、要問人（附問題）、失敗。
    - 每條結論附出處（`#編號:行號`），由程式核對；沿用提煉的核對（`extract.missing_tokens`）。
    - 沒答到的項目、自己補的參數。不交原始輸出。
  - **要問人時**：中階的狀態（圖、收據）存在 JobStore，主對話把問題轉給使用者；使用者回答後由程式接回同一個 worker 的同一個節點，不重排，也不靠模型記得要接著做（第 6 節：接著問確認的是 harness，不是模型）。
  - **執行狀態跟圖分開存**：`logs/<種類>_jobs/<編號>/` 存圖、每個節點的收據與事件；重排時只改圖。

### D8 每一層用哪個模型
- **架構圖**：沒有指定。
- **現在**：預設 `gemma4:e4b`，提煉也用同一個模型（摘要可以另外指定）；維運評測用 `gemma4:26b`。
  Ollama 讓 gemma4 一次只跑一個 slot（`config.py` 的說明），用兩個模型就要同時放在顯示卡上，或來回載入。
- **定案**：
  - 每一層（分流、排圖、判斷節點、提煉）的模型都可以分開設定。
  - 第一版全部用主對話的模型。
  - 評測用 26b、e4b 各跑，再決定排圖要不要用比較大的模型。

### D9 知識檔放哪裡
- **架構圖**：`knowledge_base/DOMAIN.md`、`knowledge_base/<領域>/SKILLS.md`、`<領域>/<複合技能>.md`、`<領域>/tools/*.md`；技能與工具的規格都寫 `domain`。
- **定案**：裡面的結構照圖，資料夾名稱沿用 `skills_system/`。
  - 新增 `skills_system/DOMAIN.md`；每個領域一個資料夾：`skills_system/<領域>/SKILLS.md`，複合技能也放在裡面。
  - **跟圖不同**：工具規格留在共用的 `skills_system/tools/`，不放進各領域。一個腳本一份規格，好幾個領域會用同一個工具（例如 result_* 每個領域都用）。
    - 領域的 `SKILLS.md` 列出它能用的工具；完整性檢查確認每個工具至少屬於一個領域、列出的工具都存在。
    - 工具屬於哪些領域只寫在這裡，工具規格不另外寫 `domain`（第 3 節已跟著改）。
  - 名稱沿用的理由：`skills_system` 也是 Python 套件，程式用 `from skills_system.scripts import …` 讀共用層（`agent_core` 的 guard、dispatch、extract 等；程式與評測共 23 個 .py 檔提到這個路徑）。
    改名會讓程式碼變成 `knowledge_base.scripts`，評測複製專案的清單也要改。文件寫明「`skills_system/` 就是架構圖的 `knowledge_base/`」。

### 框架的簡化：每個 session 都是一個完整的 agent（2026-11-21 使用者提出，待討論）

給試錯的次數，但不限死開放的試錯；圖慢慢長出來，出問題就回到前一個節點（前一個子工作階段），帶著經驗重新做一次。不要一直想用文字控制
中階的每一步，那樣反而造成問題。但先確定單一個子工作階段穩定，這要優先。

**跟之前的討論、原型的關係**：
- 目標一樣：第 4 步的 I（帶著上一次出錯的原因回到前一步重新規劃）、〈方向的實驗〉使用者的補充（邊規劃邊做、有向圖一步一步長出來）；
  〈方向的檢討〉也寫過「限制放在什麼算數（核對），不放在怎麼做（流程）」。
- 不一樣的是**節點有多大**：

  | | 一個節點是什麼 | 流程由誰定 | 結果 |
  |---|---|---|---|
  | 中階 | 一個工具呼叫 | 〈骨架〉代入參數（文字寫好的流程）；模型挑技能、抄參數、判斷 | 合用時最穩；不合用就交給子工作階段 |
  | 原型（設計筆記 2.45） | 一個工具呼叫 | 模型每一步讀公佈欄排下一步 | 合約那一類的錯少了，一步一步排帶進新的起伏（重複、廣搜、選錯檔案），沒有比較好 |
  | 這次的想法 | 一個子工作階段（一個子目標） | 節點裡模型自己試；程式只在節點的邊界管結果（answers 的核對） | 還沒做 |

- 現在的程式裡已經有一層：分工的每一項就是一個節點（一個領域一項，照順序做），後面的收到前面查到的；再交給同一個領域時，程式帶上一次的
  經過（做法、參數、找過的字、停下來的原因）；同一項最多 3 次；子工作階段寫了別的領域查得到的，主模型再分工。
  還沒有的：同一個領域在一次分工裡分成好幾個節點（現在同一個領域只列一項）；後面的節點發現前面給的不對時，由程式回到前面那一個節點重做
  （現在是交回主模型，由它重新分工）。

**數字說的**（同〈框架的簡化〉）：
- 支持這個方向：
  - 到現在變好的大多是程式做的與程式核對的（收據的筆數、程式列舉的工具、answers 的核對與照項目排）。
  - 中階的模型角色本身帶來一類找的錯（合約照問題的字填搜尋的字、判斷看得到的範圍）；原型拿掉合約之後，這一類大多沒有了。
  - HarnessMM 論文自己寫的限制（附錄）：開放式的任務只有 1.4% 的動作走決策圖的快速路徑。
- 要小心的：
  - 複合技能合用時最穩（第 5 步的基準：中階自己做完的 26b 51/61、e4b 52/68 過）。照這個想法，這部分做成程式的工具留住，不是丟掉。
  - 開放本身不會自動變好：原型就是「開放＋程式管事實」，輸在一步一步排的起伏；子工作階段在比較難的題目上 26b 11/19、e4b 4/14。

**看法**：同意。用文字定流程，每一種題目要寫一份，不合用就得退回一步一步做；「節點裡開放地試、程式管節點的結果、能照流程做完的做成工具」
是通用的那條路，也合 CLAUDE.md 的原則（事實與做完了沒由程式判斷，模型只在需要判斷的地方出手）。做多節點與回退之前，要先想清楚三件事：
1. **誰判斷出了問題、是哪一個節點的問題**：程式判斷得了的先由程式判斷——後面的節點寫出用了前面的哪一個 #編號、哪裡不對，程式核對
   （路徑不存在、數字對不上、出處裡沒有那個名稱）；判斷不了的才由上一層的模型決定。不能讓節點自己說「做完了」（第 6 節：worker 說的
   做完、沒做完不可靠）。
2. **帶回去的經驗**：由程式從紀錄整理（做過的工具與參數、找到與沒找到的、為什麼被退回），跟現在的「上一次的經過」一樣；原文用 #編號，
   重做的節點自己用 result_view 看，不靠摘要。
3. **上限**：每個節點重做幾次、整張圖回退幾次、總步數與時間；不然會在兩個節點之間來回。節點以子目標為單位，不是一步一個工具（原型的教訓）。

**建議**：
1. 順序照使用者說的：先做 5c（repo_analysis 一律交給子工作階段，量單一個子工作階段穩不穩）。
2. 5c 分層時多記一件事（不用多跑）：沒過的那幾次，是不是前面的一步錯了、後面照著做（例：一開始選錯檔案，之後都在錯的檔案裡找）。
   這一類多，「回到前一個節點帶著經驗重做」才有明確的目標；不多，瓶頸就不在這裡。
3. 5c 的結果出來再一起決定：中階的挑技能、合約、判斷要不要拿掉；多節點與回退先做最小的一版（只加「後面的節點指出前面的錯 → 程式核對 →
   回到那個節點重做」這一條），量跨檔案、跨領域的題目。

**決定**（2026-11-21）：優先順序照使用者——先確定單一個子工作階段穩定（待辦 5c）。多節點與回退記進待辦第 5d 列，5c 的結果出來再討論。

  session 重新看要不要別的資訊或別的技能。

- 「做完了沒」由程式判斷。模型只填要填的欄位，前面決定過的值沿用。

    只是判斷挑錯行，直接從那些結果答；技能做不到才一步一步查。
  - 開放有邊界：回答要有收據裡的出處，跟中階一模一樣的叫法擋下來；中階的報告照樣交回主對話，查到的不會丟。
