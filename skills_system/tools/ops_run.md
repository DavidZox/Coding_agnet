# 用途
把複雜的維運任務交給系統：先規劃成 2～6 步（每一步的目標、技能、會不會改變狀態、做完怎麼檢查），把整份計畫給使用者確認
（核准＝計畫裡標明會改變狀態的步驟都核准了），再每一步派一個新的執行者照做：只做那一步的目標、只能用計畫列的技能改變狀態；
做完由系統跑那一步的檢查，沒過就換一個執行者重試一次，還是沒過就停下來（後面的步驟不做）。
一兩步就做得完的任務（查一個值、看 log、重啟一個容器）不要用這個，直接用對應的技能。

# 語法
`EXECUTE: scripts/ops_run_cmd.py "<任務描述>"`：規劃 → 使用者確認 → 執行，一個動作完成（不用自己先問使用者要不要執行）。
* 任務描述：照使用者的原話寫完整（名稱、路徑、數值、條件，例如「先備份」「不要動 tb2」都要帶到）。
使用者只想先看計畫：一樣用 ops_run，確認畫面就是整份計畫，使用者可以不同意（計畫會留著，之後 `scripts/ops_run_cmd.py` 不帶參數就是執行它）。
計畫的步驟都只查詢時不用確認，直接執行。

# 範例
`EXECUTE: scripts/ops_run_cmd.py "web_cache 停了，把它重新啟動，確認 /etc/web_cache.conf 的 max_size 還是 512M，最後在 ops_notes/web_cache.md 記一筆"`

# 回傳
`[PASS] 計畫執行完成（N/N 步…）` 或 `[ERROR] 計畫沒有做完：第 k 步沒有完成…`，接著每一步的結果（做了什麼、關鍵的值與名稱、檢查結果）。
依結果回答使用者：引用具體的值、名稱與前後變化；沒做完的說明卡在哪裡、原因與建議。

# 異常
規劃不出可以執行的步驟、或沒帶任務也沒有草稿：`[ERROR]`，改成自己用技能一步一步做。使用者沒有同意：`[DENIED]`，等使用者說明要怎麼調整（可以重新 ops_plan）。
