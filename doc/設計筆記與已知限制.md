## 2. 核心機制

### 2.1 兩種操作介面，共用同一顆大腦

- **`Agent_Runner.py`**：終端機互動介面（`SkillAgent` 類別 + `main()` REPL）。對話狀態、技能載入、腳本執行、壓縮、token 門檻都定義在這裡，是整個專案**唯一的核心來源**。
- **`web_console.py`**：純標準庫（無 Flask／FastAPI）的網頁版，`import` `SkillAgent` 與共用函式，把同一套推理迴圈改寫成「每次 HTTP 請求處理一小段、以 NDJSON 串流逐筆回傳事件」：後端每完成一次推論或工具執行就立刻推一筆，前端邊收邊渲染；本身**不重新定義任何核心規則**。

兩者只差在互動方式（終端機 vs. 兩欄式網頁），推理與工具執行邏輯完全一致。

### 2.2 回覆協議：固定 JSON，只有 `action` 會被執行

模型每一次回覆都是 `{"thought", "reply", "action"}`，由 `ask_ai()` 以 Ollama `format=AGENT_REPLY_SCHEMA` 強制結構。`reply` 是給人看的文字；`action` 是 `null` 或 `{"command": 技能名稱｜腳本路徑, "args": 參數字串}`。`parse_agent_reply()` 解析後，CLI 與 Web 顯示 `reply`（💭 thought 另外顯示，有 action 時附一行「▶ action」），`run_tool()` **只看 `action`**——`reply` 裡不論寫了什麼（解釋時抄的 `EXECUTE:` 範例、複述的整份規格）都不會被執行，「一次只做一步」也由單一 `action` 欄位天然保證。

- **非合法 JSON**：降級為顯示原文、該輪不執行，不退回文字比對。
- **空白回覆**（合法 JSON 但 `reply` 空、`action` `null`）：典型原因是模型在字串裡寫了英文雙引號，JSON 文法被迫提早結束。`ask_ai()` 帶著暫時提醒（不進歷史）自動重試一次；`AGENT.md` 要求 thought 精簡、thought／reply 不用英文雙引號。
- **兩階段完成率**：載入規格後回給模型的訊息是明確的下一步指令（「這一輪只是載入規格，下一輪直接依規格繼續任務，不要解釋、不要反問」），避免小模型停下來聊天。
- `args` 刻意是字串：所有腳本都吃位置參數，規格裡 `EXECUTE: <路徑> <參數>` 的範例就對應 `command`＋`args`，含空白的參數用 `\"` 包住。

### 2.3 技能系統：索引 + 按需載入的規格 + 既有腳本

- **`skills_system/SKILLS.md`**：輕量索引，每個技能一行「名稱 + 描述」，永遠在系統提示詞裡；開頭另有共同慣例（`[PASS]`／`[ERROR]`、逾時、目標容器）。
- **`skills_system/tools/<name>.md`**：每個技能一份 OKF 規格（用途、語法、範例、回傳、異常），只在被用到時載入。`/make_skill` 產生的流程技能（frontmatter `type: Procedure`）沒有自己的腳本，規格的步驟呼叫既有技能的腳本（2.10）。
- **`skills_system/scripts/<name>_cmd.py`**：實際執行的腳本。容器類共用 `_docker_common.py`、工作包類共用 `_rmf_common.py`。

**兩階段派發（progressive disclosure）**：`run_tool()` 拿到 `action` 後，`command` 若對應到存在的 `tools/<name>.md`，就把整份規格當系統回傳注入上下文、不執行（流程技能改成提醒「沒有自己的腳本，照步驟一步一步做」）；否則把 `command` 當腳本路徑執行。**沒有任何「技能名稱 → 腳本」對照表**，模型必須先讀規格拿到真實路徑才執行得了；猜錯檔名會收到可行動的 `[ERROR]`（檔名若含某個技能名稱，直接提示先載入該技能；`scripts/<技能>.py` 這種只差 `_cmd` 的寫法會被 `_normalize_script_name()` 補成正確檔名）。載入規格的回傳開頭明說「這一輪只是載入規格、還沒有執行任何東西」，模型若在技能名稱後附了參數，還會點名那些參數沒有被執行、狀態沒有改變（實測 e4b 用 `docker_open <容器>`、`change_dir <路徑>` 載完規格就當作已切換，直接做下一步）。`action.args` 拆解時丟掉空字串、引號不成對時退回空白切分並去掉殘留引號（實測模型會送 `. ""`、`"""`）；`find_file`／`search_text`／`change_dir` 直接吃拆好的參數清單，不再把參數接成一串重新 shlex。歷史訊息保存模型原始 JSON；壓縮摘要只取 `reply` 與 `[action]`，`thought` 不進摘要。

**手動載入**：Web Console 在輸入框打「/」的選單裡點技能（或 `/skill <名稱>`，CLI 同名指令），`manual_skill_block()` 產生的規格區塊（以 `[skill loaded]` 開頭）會附在下一則訊息後一起送出，省掉一輪「先載規格」；技能清單來自 `list_skills()` 解析 `SKILLS.md`。

**回傳慣例與逾時**：腳本一律由 stdout 回傳，成功以 `[PASS]` 開頭（原本直接回原始輸出的 `docker_runcmd`、`ROS2_node_info`、`ROS2_topic_echo` 單筆也加了 `[PASS]` 標頭行；`[CWD_CHANGED]`／`[TARGET_CONTAINER]` 狀態標記放在 `[PASS]` 之後），失敗（含逾時）以 `[ERROR]` 開頭並附原因與建議——`_content_for_context()` 靠這個前綴判定成功／失敗。沒有任何腳本自帶的門檻豁免：分析型輸出（`workpackage_status --watch`、`semantic_map`、`ROS2_topic_echo --duration`）也跟其他輸出一樣回傳完整資訊，超過門檻就交給獨立 session 擷取（舊版 `[PASS][digest]` 讓腳本自己的固定格式摘要放寬到 1500 tokens 直接進主對話，等於由不知道任務的腳本決定什麼重要，已移除）。每支會呼叫外部程序或網路的腳本都有自己的逾時上限（寫在規格裡），`run_tool` 另設 `TOOL_EXEC_TIMEOUT`（600 秒）當最後防線，腳本以非零 exit code 結束時補 `[ERROR]` 前綴、完全沒有輸出時給出明確訊息。

**工具結果如何進主對話**：以 user 角色、經 `tool_result_message()` 包裝——第一行 `[tool result]`（框架訊息判定、壓縮切點都認它），第二行【系統回傳】框架句明說「系統執行你上一輪 action（<腳本>）的結果，不是使用者提供的，不要感謝使用者」，CLI 三種模式、Web、捨棄通知都用同一個包裝。寫在每一則裡而不是只寫在 `AGENT.md`：實測 `AGENT.md` 已有 Harness Messages 規則，gemma4:e4b 仍會回「感謝您提供的語義地圖」；改用 Ollama 的 `tool` 角色也不行，gemma4 的模板會把 `tool` 訊息整個丟掉（模型完全看不到內容），這也是影像分析結果用同一招的原因。壓縮摘要渲染時框架句會被去掉，不佔摘要篇幅。

### 2.4 harness 替模型維護的狀態：工作目錄與目標容器

兩者機制相同：狀態放在 `SkillAgent`（`current_cwd`、`target_container`），顯示在 system prompt 的 Current Agent State 與 Web 標題列，執行腳本時傳給腳本（cwd／環境變數 `TARGET_CONTAINER`），腳本成功改變狀態時在輸出印一行標記，`_sync_state_from_tool_output()` 讀到就更新。`/clear` 不清這兩個狀態。

- **工作目錄**：`change_dir` 在 `[PASS]` 之後印 `[CWD_CHANGED] 路徑`；之後所有腳本以它為 cwd，相對路徑自然生效。
- **目標容器**：預設空。容器技能（`docker_runcmd`、`ROS2_*`）省略 `<container_name>` 時由 `_docker_common.resolve_container()` 取目標容器，沒有就回 `[ERROR]` 提示先 `docker_containers` 查、`docker_open` 選定；腳本成功操作某容器後在輸出末行印 `[TARGET_CONTAINER] <名稱>`（放末行是為了不破壞 `[PASS]`／`[ERROR]` 的開頭判定，與目前目標相同時不印）。所以目標容器＝最近一次成功操作的容器，`docker_open`／`docker_est` 是刻意選定或切換用。`AGENT.md` 要求模型直接用它、不再反問使用者要看哪個容器；`docker_runcmd` 只有一個參數時整串是指令、有目標且第一個參數不是任何現有容器的完整名稱時也把整串當指令（模型常忘記引號或省略名稱）；`ROS2_topic_echo`／`ROS2_node_info` 以 `/` 開頭的第一個參數判定為 topic／node、容器省略。軌跡記錄也帶著它。

### 2.5 上下文管理：真實 token 尺度、雙水位線、滾動融合摘要

**Token 計量**：Ollama 沒有 tokenize API，所以 AI 回覆用 `eval_count`、整體上下文用 `prompt_eval_count`（精確），使用者輸入與工具回傳用「字元數 ÷ `chars_per_token`」估算，`chars_per_token` 每次呼叫後以 `prompt_eval_count` 重新校準（中文為主約 1.8～1.9）。所有門檻與 `num_ctx` 同一尺度；Web 標題列的 `ctx` 前有 `≈` 代表估算值。

| 常數 | 值 | 作用 |
| :--- | :--- | :--- |
| `NUM_CTX` | 32768（`AGENT_NUM_CTX`） | 每次請求給 Ollama 的 context 上限，主對話、壓縮摘要、工具摘要三種 session 共用；記憶體小的設備可設回 12288 |
| `TOKEN_THRESHOLD`（硬水位） | `NUM_CTX × 75%`（`AGENT_HARD_RATIO`） | `ask_ai()` 呼叫前若超過，一定**同步**壓縮（`ensure_context_budget()`），確保壓縮先於 Ollama 在 `num_ctx` 處的靜默截斷；背景壓縮進行中則先等它完成 |
| `SOFT_TOKEN_THRESHOLD`（軟水位） | `NUM_CTX × 60%`（`AGENT_SOFT_RATIO`） | 只在**回合結束後**檢查（`after_turn_compression()`）：答案已送出、模型閒著，切點落在任務邊界；`/parallel_cal on` 時在背景執行緒做 |
| `MIN_COMPRESS_TOKENS` | `max(1000, NUM_CTX ÷ 20)` | 軟水位的「值不值得」門檻：可壓的舊內容太少就不花一次模型呼叫 |
| `KEEP_RECENT_TOKENS` | `NUM_CTX × 15%` | 壓縮時保留最新這麼多 token 的原文，在訊息邊界切、不拆開指令與其 `[tool result]`（`_split_for_compression()`） |
| `SUMMARY_MAX_CHARS` / `SUMMARY_MAX_PREDICT` | 1500 字 / 2500 tokens（2026-09-27 前是 600 / 2000） | 融合摘要的長度目標（實測會超過約三成）與 `num_predict` 硬上限；被截斷時 JSON 解析失敗退回原文。使用者原話另外由程式逐字保留（2.11） |
| `SUMMARY_ARCHIVE_KEEP` | 30（`AGENT_SUMMARY_KEEP`） | `logs/` 只保留最近 N 份 `summary_*.md` 與同名 `.json` |
| `SUMMARY_MODEL` | 同主模型（`AGENT_SUMMARY_MODEL`） | 壓縮摘要與工具摘要用的模型；與主模型不同時背景壓縮才真的平行 |
| `TOOL_RESULT_TOKEN_THRESHOLD` | 500 | 單次工具回傳超過就交給獨立 session 做任務導向擷取（`/summarize off` 時只給成功／失敗判定）；技能規格文件例外。完整內容仍顯示給使用者並標 ⚠️ |
| `TOOL_SUMMARY_INPUT_MAX_CHARS` | 16000 字（`AGENT_TOOL_SUMMARY_INPUT_CHARS`） | 獨立 session 一次最多讀多少原始輸出，超過保留頭尾（6:4）並告知模型中間省略了多少 |
| `TOOL_SUMMARY_MAX_CHARS` / `TOOL_SUMMARY_MAX_PREDICT` | 400 字 / 1200 tokens | 任務導向摘要的長度目標（寫進 prompt）與 `num_predict` 硬上限；被截斷時 JSON 解析失敗退回原文 |
| `TOOL_USE_INDEX_SHOW` | 30（`AGENT_TOOL_USE_INDEX_SHOW`） | system prompt 尾端「工具使用檢索清單」顯示視窗筆數（只算工具回傳）；設 0 關閉顯示（寫入不受影響） |
| `CONVERSATION_ARCHIVES_SHOW` / `CONVERSATION_SEGMENTS_KEEP` | 10 / 100（`AGENT_CONVERSATION_ARCHIVES_SHOW` / `AGENT_CONVERSATION_SEGMENTS_KEEP`） | 「過去的對話片段」一節顯示幾份／對話片段存檔保留幾份（跟工具回傳的 200 檔／50 MB 分開算） |
| `VISION_RESULTS_KEEP` | 100（`AGENT_VISION_RESULTS_KEEP`） | 附圖分析存檔保留幾份（跟工具回傳、對話片段分開算；原圖不保存，這份文字重跑不回來） |

Web Console 另有 `MAX_AUTO_ITERATIONS = 25`：Auto 模式連續執行工具超過此輪數強制中止本回合。所有 `ollama.chat()` 都帶 `num_ctx=NUM_CTX`（不帶時 Ollama 預設 4096 會在背後悄悄截斷）。

**滾動融合摘要**：`compress_context_to_file()` 切出保留區以外的舊訊息交給 `summarize_messages()`，摘要模型同時收到上一份 `rolling_summary` 與新片段（渲染成 `[user]`／`[assistant]`／`[harness …]` 純文字），輸出一份更新後的完整摘要取代上一份；結構由 `format=SUMMARY_SCHEMA`（overview／key_progress／results_and_errors／user_preferences／open_items）強制，`_render_summary_markdown()` 排成固定五段。每次壓縮寫 `logs/summary_<時間>.md` 與同名 `.json`，但 system prompt 只注入最新一份；啟動時從 `logs/` 最新一份載入，摘要跨 session 延續，`/clear` 不清，要完全重來請刪 `logs/`。以 `HARNESS_MARKERS`（`[tool result]`、`[vision result]`、`[skill loaded]`、`[PLAN_REQUEST]`…）開頭的訊息會被標成框架訊息，避免被記成使用者偏好。

**跨啟動接回的摘要可能過時（2026-09-27）**：滾動摘要啟動時從最新一份 `summary_*.json` 接回，`/clear` 也不清，所以一份很久以前的摘要會一直留在 system prompt。實際踩到：`plan_task` 移除後，早上那份摘要的未完成事項還寫著「指導系統執行 `plan_task` 技能」，新 session 使用者說「下達機器人任務」時模型照著去叫 `plan_task`，而 harness 只回「找不到腳本 plan_task_cmd.py，請先載入規格」，沒說這個技能根本不存在。改法三件：(1) `clean_summary`：摘要注入 system prompt 前，把提到「目前不存在的技能」的行拿掉（`stale_skill_names`：反引號包住、同一行有「技能」的 snake_case 名稱，或 `scripts/<x>_cmd.py`，在 `tools/` 與 `scripts/` 都找不到的；上下文模式名稱不算），標題行留著；下一次壓縮交給摘要模型的上一份摘要也是清過的，新摘要自然就沒有了。原本的摘要檔不改。(2) 接回的摘要還沒被這次 session 壓縮過時（`summary_carried_from`），開頭註明「這份摘要是之前的對話留下的（時間）……進度與未完成事項可能已經過時，技能以 Available Skills 為準，使用者沒提起就不要主動接續」。(3) `action.command` 填的是技能名稱、卻既沒有規格也沒有腳本時，回「沒有 `X` 這個技能……可能是舊摘要、舊對話或記憶裡提到、但已經移除的名稱，不要再使用」，不再讓模型以為只是少載了規格。**第一版是在 system prompt 點名「摘要裡提到的 plan_task 目前不是可用的技能」，真模型（e4b）3 次有 3 次反而先去叫 `plan_task`**——小模型看到名稱就被提醒，否定句沒什麼用；沒有點名的舊版 3 次都沒叫（使用者遇到的是機率性發生）。改成整行拿掉、不點名。第一版的 (3) 倒是有效：3 次都在下一步改用 `workpackage_send`。改成整行拿掉後重測（同一份舊摘要，e4b，「我要下達機器人任務」「幫我規劃一個多步驟的機器人任務」各 3 次）：6 次都沒有叫 `plan_task`，改用 `workpackage_send`／`semantic_map`／`docker_containers`，或直接問使用者任務細節。

**工具回傳的任務導向摘要（預設開啟；`/summarize off` 或 `AGENT_TOOL_SUMMARY=0` 關閉）**：超過門檻的工具回傳一律由 `summarize_tool_result()` 開一個獨立、乾淨的一次性 session 處理，這是「原始上下文 + 當前問題」式的壓縮（context-aware compression），不是通用摘要。獨立 session 收到三樣東西：完整原始輸出（超過 `TOOL_SUMMARY_INPUT_MAX_CHARS` 時保留頭尾並標明省略）、**使用者的目標**（`_build_task_anchor_text()`：Objective、這一輪任務的原始敘述、已核准的計畫）、**這一步的目的**（`_last_assistant_step()`：決策模型剛才的 `thought`／`reply` 與執行的 `action`——在 agent 迴圈裡，比使用者的原話更精確的「當前問題」）。prompt 把它定位成資訊過濾器：只留與目標直接相關的事實，名稱與數值照抄、不推測、不給建議，並用 `not_covered` 明說原始輸出沒有涵蓋什麼。輸出以 `format=TOOL_SUMMARY_SCHEMA`（answer／facts／errors／not_covered）強制結構，排成「執行結果／回答／相關事實／錯誤／未涵蓋」加一段附註（告訴主模型它看不到原文、需要其他資訊就換參數重查），解析失敗退回模型原文，session 失敗退回成功／失敗判定（判定訊息帶存檔編號，要模型用 `result_grep`／`result_view` 回查而不是重跑）。CLI 印出「🧠 獨立 session 任務導向摘要」、Web 以紫色 🧠 卡片顯示，兩者都是主對話實際收到的內容。**沒有腳本自帶的豁免**：`ROS2_topic_echo --duration` 等分析型技能改成回傳完整資訊（統計 + 全部原始訊息），什麼重要由知道任務的獨立 session 決定。代價是每次超過門檻多一次模型呼叫（同模型時與主對話序列執行）。

**數值交給腳本算，摘要只做過濾**：實測 gemma4:e4b 對「哪個檔案最新」「幾個 topic 含 costmap」這類比較／計數題 0/5 答對，開 `think=True` 也只有 2/5 且一次 17 秒；26b 開推論才 3/3，但一次 35～60 秒。所以比較、計數、排序、門檻判斷全部放進腳本：`list_dir` 標頭給數量與「最新修改」、`--filter`／`--newest`；`find_file`／`search_text` 標頭給數量；`ROS2_topic_list`／`ROS2_node_list` 的 `--filter` 計數；`ROS2_topic_echo --where 欄位<值` 算出幾則符合、第一則符合的序號與值。摘要 prompt 規定腳本算好的數字直接照抄、不得重數或推翻；各規格文件要求模型遇到這類問題改用對應選項。摘要 session 維持 `think=False`。

**工具結果存檔與回查（`result_list`／`result_grep`／`result_view`）**：摘要會丟細節、原文進主對話會污染上下文，兩者都不選：每次腳本執行的完整原始輸出由 `_record_trajectory()` 順手存成 `logs/tool_results/<session>_<編號>_<腳本>.md`（簡單 key: value 檔頭：編號、時間、腳本、指令、cwd、容器、狀態、字數、當時的任務；不用 PyYAML），並在 `index.md` 記一行；摘要 session 產出的「回答」會回填到索引那一行。編號＝軌跡 id，啟動時從既有存檔的最大編號續編（`_max_archived_id`，跨 session 不重複，純數字的 `#16` 在任何一次啟動都指到同一份），`/make_skill` 與稽核對得上。技能規格文件不存（它不是執行結果）。摘要 schema 多了 `suggested_questions`（最多 3 個延伸方向，各附可搜尋的關鍵字——關鍵字只給 harness 內部的自動追問用，不給主模型，見下面「追問一律走 `result_recall`」），附註告訴主模型「追問摘要沒寫到的內容用 `result_recall <編號>`，不要重跑工具」——觀察型技能不必再等一次擷取，摘要只讀頭尾時被省略的中段也取得到。交握原則寫在規格文件與附註裡（`AGENT.md` 沒有預算，見 2026-09-26 那段）：有真的缺口（`not_covered`）時，主模型要用自然的一句話問使用者，不列清單、不照抄 `suggested_questions` 的文字；已經直接回答時，延伸方向只是順口一提或略過。使用者回答追問時最新一句常只剩關鍵字，所以摘要錨點帶「任務線」——最近 3 則使用者訊息（`task_history`）。`result_grep` 的輸出走一樣的門檻：超過 500 tokens 交給獨立 session（它拿到的正是使用者的追問），沒超過直接進主對話。安全：正則長度上限 200、逐行比對帶 3 秒預算（防災難性回溯）、路徑只取檔名鎖在存檔目錄；保留最近 200 個檔且總量 50 MB（`AGENT_TOOL_RESULTS_KEEP`／`AGENT_TOOL_RESULTS_MAX_MB`），刪最舊的並同步索引；`logs/` 已 `.gitignore`（輸出可能含敏感內容）。CLI 印「📄 已存檔 #16」，Web 卡片標題帶編號並可點開 `/api/results/<編號>` 看原文。

**自動追問與 `result_recall`（2026-09-26）**：`summarize_tool_result()` 擷取後若 `not_covered` 還有缺口、且摘要自己給出了 `suggested_questions`，會拿第一條的 keywords 對同一份存檔自動再 `result_grep` 一次（`_exec_script` 直接跑腳本，不經過 `run_tool`、不記軌跡、不產生新編號——這不是模型的動作，是同一次工具回傳的延伸擷取，只印一行 `🔁 自動追問` 讓使用者看得到），把 grep 到的原文重新交給同一個擷取函式（`_extract_task_oriented`，`summarize_tool_result`／自動追問／`result_recall` 三處共用；迴圈本身抽在 `_extract_with_followups`，`summarize_tool_result` 與 `result_recall` 都走它），永遠錨回原始的「使用者目標＋這一步的目的」，不是拿上一輪的摘要文字當輸入。最多跳 `TOOL_SUMMARY_MAX_FOLLOWUP_HOPS`（預設 2，`AGENT_TOOL_SUMMARY_MAX_HOPS`）次；跳滿、grep 落空或沒有 keywords 可用時照實停下，`not_covered` 該是什麼就是什麼，不偽裝成已解決——使用者原始問題若本來就模糊，這裡不會硬鎖定一個可能不相關的答案。`AGENT.md` 另外要求主模型看到工具回傳同時有「未涵蓋」與延伸方向、而使用者最新一句話沒對應其中一個時，要用平常聊天的口吻自然地問一句（不條列、不照抄、不出現「延伸方向」「關鍵字」這些字）、`action` 填 `null`，不要自己猜一個方向執行；使用者的追問明顯跟前面的工具回傳有關、但沒有可用關鍵字時，改用 `result_recall <編號> "<問題>"`（下一段）——這是唯一一個沒有實體 `scripts/<name>_cmd.py` 的技能：`run_tool()` 在存在性檢查前攔截 `result_recall_cmd.py`，直接呼叫 in-process 方法（要呼叫 `ollama.chat`，不能像其他技能一樣包成 subprocess），把使用者的問題原文（不是關鍵字）交給獨立 session 重新讀那份存檔的完整原文提煉；跟自動追問不同，這是主模型主動選的一次動作，照樣記軌跡、產生新的存檔編號。（同日稍早的版本叫 `result_ask`，定位是「想不出關鍵字時的退路」；實測模型寧可先 `result_list` 也不選它，改名並改成檢索清單的主要路徑後才會用。）

**工具使用檢索清單與 `result_recall`（Tool Use Index，2026-09-26）**：三段式的「動態檢索」——(1) `tools_use_index.md`（跟 `index.md` 不同檔）只在任務導向擷取（`summarize_tool_result`／`result_recall`）真的跑過時記一筆：編號、時間、`session_id`、檔名、以及摘要 schema 新增的 `index_hint`（模型產出，目標 60 字左右的完整一句話、程式不截斷，說明「這次的問題」跟「這份原始輸出」的關聯，不是 `answer` 的重複，見 `_append_tool_use_index`）。跟 `index.md` 會隨 `_prune_tool_results` 一起被裁不同，這份**永遠只 append**，跨 session（甚至跨這支程式的重新啟動）持續累加。(2) `get_system_prompt()` 每輪都在尾端注入最近 `TOOL_USE_INDEX_SHOW`（預設 30）筆，格式 `#編號（時間）：描述`，連同使用規則與 `result_recall` 的執行語法一起（`_tool_use_index_block`）——這是「顯示視窗」不是資料上限，更早的紀錄還在檔案裡。(3) main session 判斷使用者這句話是在接續、追問或延伸其中一筆時（「剛剛那些腳本挑一個」「之前查的那個馬達後來怎樣」），直接執行 `scripts/result_recall_cmd.py <編號> "<這句話原文>"`（清單裡已給語法，不必先載規格，也不要先 `result_list`／`result_grep`）：harness 讀出那份存檔的完整原文，連同使用者現在的問題（以 harness 自己記的 `current_task` 為主——實測小模型會把清單描述抄進參數當問題，所以模型給的參數只當「聚焦點」）、當時的任務／指令、清單描述交給獨立 session 提煉（`_extract_with_followups`：有缺口時自動再 `result_grep` 最多 2 跳，逐步收斂），main session 只收到提煉後的重點，再據此回答或做下一步；`AGENT.md` 第 1 條也提醒回答前先看清單。**編號改成跨 session 全域唯一**：以前軌跡編號每次啟動從 1 起算，幾乎每個 session 的第一筆存檔都是 `#1`，`resolve_result()` 在目前 session 找不到某編號時會退回「最新一個有這個編號的任何 session」，對跨 session 檢索幾乎一定抓錯份；現在 `SkillAgent.__init__` 從既有存檔的最大編號續編（`_max_archived_id`），純數字就能唯一對到一份，模型只要抄清單上的 `#數字`（檔名仍寫進 `tools_use_index.md`，給人看／除錯用）。原始存檔仍受 200 檔／50 MB 上限輪替，清單指到的檔案有可能已被清掉，`result_recall` 回明確的 `[ERROR] 找不到結果 #N` 並要模型如實告知（見已知限制）。設計上刻意不要求模型自己比對清單去「想關鍵字」——清單只回答「有沒有一筆看起來有關」這個小模型做得到的淺層判斷，語意理解交給拿到完整原文的獨立 session。清單上的判斷寫成依序的四步：對話裡最近的工具回傳已經寫了那個具體名稱或數值 → 直接回答；在接續某一筆 → `result_recall`；問「現在／目前」→ 重跑工具；都不像 → 當新問題。

**獨立 session 也給 recall 建議、追問一律走 `result_recall`（2026-09-26 晚）**：使用者實測後發現三件事——(a) 摘要把 `result_grep` 關鍵字列給主模型（「對應 result_grep 關鍵字：DEFAULT_MODEL|VISION_MODEL|…」），模型把 `|` 改寫成 `OR` 又不加引號，`result_grep` 直接報錯再重試（實際紀錄 #21）；摘要等於一直把主模型往「自己想關鍵字」推，跟「回原文依問題提煉」的方向相反。(b) 使用者回答追問時只說「第一個」，`result_recall` 只拿最新一句當問題就錨錯（#13 的標頭是「針對「第一個」提煉」）。(c) `result_recall` 自己的輸出也被記進清單，跟原本那筆重複佔位，而且之後 recall 到它只拿得到「摘要的摘要」。改法：
- **recall 建議**：獨立 session（`summarize_tool_result` 與 `result_recall` 都是）現在也拿到檢索清單（排除正在處理的那筆；`_tool_use_catalog`），schema 多一個 `related_records`（使用者的問題「還需要」清單裡哪幾筆才答得完整，最多 2 筆，只是同類工具不算），程式只留清單裡真的有的編號（`_validate_related`，擋掉小模型編的編號或把自己列進去）。摘要結尾的下一步建議（`_followup_guidance`）依序：需要舊存檔 → 下一輪直接 `result_recall` 那筆、不要先問使用者；自動追問也解不開的缺口 → 用自然的一句話問使用者；已經回答 → 直接回答、不必再 recall。這就是「什麼時候不用 recall」的判斷來源：看過完整原文的是獨立 session，由它明說夠不夠，主模型不必自己猜。
- **追問一律走 `result_recall`**：延伸方向只列問題、不附關鍵字；附註、`AGENT.md` 第 5 條、`SKILLS.md` 與規格文件都改成「追問某份存檔裡摘要沒寫到的內容 → `result_recall <編號> "<使用者的話>"`」；`result_grep` 只剩「找某個字串在哪幾行」。
- **一次 recall 多份**：`result_recall 2,1 "<問題>"`（最多 `RECALL_MAX_RECORDS`＝3 份）把幾份原文（輸入上限平均分配、各自標 `===== 存檔 #N =====`）交給同一個獨立 session。實測只能 recall 一份時會來回跳：比較 tools 與 scripts 清單時，讀 #1 的 session 看不到 #2、說「還需要 #2」，讀 #2 的又說「還需要 #1」。現在「還需要」的建議直接給合併的指令（這一份＋那幾份），正在讀的幾份從檢索清單排除，不會再被列成「還需要」；多份時不做自動追問（原文已經都在）；其中某份已被輪替清掉時照樣讀其餘的，並標明哪份不在。
- **自動追問的兩個既有 bug**：grep「共 0 行命中」時以前照樣拿空結果去擷取，把第一輪列好的 26 個檔案換成「搜尋命中 0 行」（檢索描述也被寫成那樣）——現在落空就停（`GREP_NO_HIT_RE`）；有命中時以前整份換成 grep 片段的擷取，第一輪讀整份原文得到的事實就不見了——現在回答／未涵蓋用追問那跳的、事實與 `related_records` 取聯集、`index_hint` 留第一輪（`_merge_followup`）。`related_records` 已經指出缺的在別筆存檔時，也不在這份裡白跑自動追問。
- **錨點用任務線**：`result_recall` 的問題改用 `_build_task_anchor_text()`（最新一句＋前幾句，同 `summarize_tool_result`），模型給的參數只當聚焦點。
- **清單只收原始工具的結果**：`result_grep`／`result_view`／`result_list`／`result_recall` 的輸出（`DERIVED_RESULT_SCRIPTS`）不記進 `tools_use_index.md`；已經是提煉結果（`TOOL_SUMMARY_TAG` 開頭）的輸出也不再被摘要第二次（`is_exempt_result`）。
- **描述被截斷**：原本用 `len()` 截 50 個字元，英文路徑每個字母都算一個字，「檢查 skills_system/tools 目錄內容，尋找與記憶（memory）相關的檔案，特別是」照中文算只有 25 字左右就被切掉——模型其實有守住 50 字，是程式算錯。改用中文習慣的字數（`clip_hint`：中文字、標點各 1 字，一段英數算 1 字），真的超過才在後半段最後一個標點收尾並加「…」；prompt 也給了格式「<使用者想知道什麼>：<這份原文有什麼>」與範例，不要「此輸出是對…」這類開頭。之前已被截斷的幾行不會復原（當初只存了截斷後的文字）。
- **描述改成不截斷，對話片段有自己的描述並分區（2026-09-27）**：實際看 `tools_use_index.md` 時幾乎每行都以「…」結尾——截掉的正好是後半段的名稱與結論，main session 或獨立 session 拿到的只剩「想知道什麼」，看不出這份存檔有什麼，認不出跟現在的問題有關。對話片段更糟：描述拿的是滾動摘要的 overview，那是「上一份摘要＋新訊息」融合後的整段歷史，每份片段拿到的都差不多，又以「本次對話的重點是…」開頭，50 字只剩空話。改法：(1) `clip_hint` 換成 `tidy_hint`，只收空白、去掉模型自己加在結尾的「…」，**整句照存、不截斷**；長度改由 prompt 要求模型寫成 60 字左右的完整一句話（`TOOL_USE_INDEX_HINT_TARGET`），列不完寫「共 N 項，含 A、B」，不用「…」「等等」收尾。沒有把整段 overview 放進清單：清單每輪都在 system prompt，30 筆各放兩百字會多 3～4k tokens，小模型判斷「有沒有關」靠的是名稱而不是敘述，整段原文在存檔檔頭與 `result_recall` 裡都拿得到。claude_code 模式由程式組的描述（使用者的問題＋執行的指令）也不再截斷；存檔檔頭與軌跡的 `task` 欄也不再截 200 字；`index.md`（`result_list` 列出的那份）的「任務」「回答」欄以前截到 60／120 字，現在也整句照存。(2) `SUMMARY_SCHEMA` 多一個 `segment_hint`：**只描述被壓掉的這一段**（談了什麼、查到什麼、決定了什麼），模型沒給時退回這一段使用者的原話。(3) 對話片段跟工具回傳**分區不分號**：編號仍是同一個序列（一個 `#編號` 只對應一份，`result_recall` 兩種都能用，小模型不必學新技能、不必判斷該用哪個），但 system prompt 另有「過去的對話片段」一節（最近 10 份，附描述、附「問之前討論過／說過／決定過什麼就找這裡」的規則），不跟工具回傳搶 30 筆名額；以前這裡只有「被壓縮的對話原文存成：#10、#15」一行編號，模型不知道每段講什麼。種類看檔名（`_conversation_segment.md`），舊的清單行也分得出來。(4) 保留上限分開：以前對話片段跟工具回傳一起算 200 檔，工具多跑幾次最舊的對話原文就被刪了，而對話沒辦法重跑拿回來；現在工具回傳的輪替不動對話片段，對話片段另外留 100 份。(5) `result_recall` 取回對話片段時告訴獨立 session「這是過去的對話，[user] 是使用者說的話…」，要它回答當時談了什麼、決定了什麼、使用者怎麼說，而不是當成工具輸出整理。真模型實測（e4b／26b 各一次：三次工具摘要＋一次壓縮）：描述 50～86 字、都是完整一句、沒有「…」；對話片段的描述是那一段的巡檢排程、B 區施工、指定 amr_01／02，不再是整段歷史。已經寫進清單、以「…」結尾的舊行不會復原。

**訊息則數視窗停用**：`SkillAgent(max_history=None)` 是預設，上下文大小只由 token 門檻決定，舊內容一律摘要歸檔而不是無聲丟棄；`max_history` 只保留為可選保險絲。

### 2.6 三種執行模式

- **Manual（預設）**：每次工具執行完都要人工確認是否把結果加入上下文（y／n／stop）。
- **Hybrid**（`/hybrid on`）：一樣詢問，但不論加入或捨棄都讓 AI 接續推論。
- **Auto**（`/auto on`）：工具結果自動帶入下一輪，直到沒有工具需要執行（Web 上限 25 輪）。

三種模式問的都是「要不要把結果加入上下文」，工具早就執行完了；會改變實體狀態的動作另外有執行**前**的確認（2.11 執行前關卡），三種模式都一樣。

### 2.7 記憶

- **全域記憶 `Memory.md`**：只有使用者明確要求（「記住這件事」等）才由 `modify_memory` 寫入，格式 `[問題種類] | [問題描述] | [解決方法或結論]`；`load_long_term_memory()` 每輪整份放進系統提示詞（2026-09-27 前只放最後 30 行，條目一多最舊、往往最基礎的規則會無聲消失；現在以條目計，超過 `MEMORY_MAX_CHARS` 才丟最舊的，並在提示詞與 UI 明說還有幾條沒載入）。開頭一句說明每條的時間是寫入時間、描述狀態的舊條目只代表當時；`AGENT.md` 的記憶協議也禁止把「系統整體健康」這類時間點狀態寫成記憶。
- **技能綁定記憶已移除（2026-10-01）**：以前 `modify_memory --skill <技能>` 寫到 `skills_system/memory/<name>.md`，只在載入那個技能的規格時才進上下文。評測裡 4B 模型 6 次都寫全域、判斷不了該不該綁，而且綁在技能上的規則在「選技能」的當下看不到；加上它跟規格文件是兩份要對照的東西，使用者決定拿掉。現在記憶只有 `Memory.md` 一個去處，`modify_memory` 沒有任何選項（帶了 `--skill` 這類選項回 `[ERROR]`，不會把選項當成記憶內容寫進去）。某個技能的用法要固定下來，直接改那份規格；一段要照順序做、中間要問使用者的做法，用 `/make_skill` 做成流程技能（2.10）。一併拿掉的：`skills_system/memory/`、`/skills` 與「/」選單的「含經驗記憶」標記、評測情境 `memory_skill_routing` 與它的兩個檢查條件。
- **滾動摘要**（`logs/summary_*.md` + `.json`）：見 2.5。
- **Sticky Objective**：`objective set|show|clear`（Web 為 `/objective set <內容>`），持續出現在系統提示詞裡直到清除。

### 2.8 Plan 模式：計畫是系統保存的草稿，AI 只提出修改（2026-09-27 改版）

`/plan on|off`（CLI 打指令；Web Console 輸入框旁有 📝 Plan 切換鈕，開啟時變綠色並顯示「📝 Plan ✓」，點一下就是送出 `/plan on`／`/plan off`，跟打指令走同一條路徑、無需另外接 API）。開啟後**下一個**新任務不直接執行，先規劃。

**為什麼改**：舊版是「模型在主對話裡把計畫寫在 reply、使用者給意見再整份重寫」。實際使用時小模型每次重寫都不一樣——這次 3 條、下次 4 條、討論後又變 2 條，沒提到的步驟也被改掉；而且每一版都留在主對話裡，上下文越來越亂。現在（`agent_core/plan.py`）：

1. **草稿**：`/plan on` 後的新任務交給一次性的規劃 session（`plan_start_draft`，`format=PLAN_DRAFT_SCHEMA`）產生第一版，每一步是 `{技能, 要做什麼}`，技能名稱不在 SKILLS.md 裡的改成「不需技能」並提醒。也可以不開 `/plan on`，直接 `/plan add` 一條條自己列。草稿存在 `self.plan`、寫成 `logs/plan_draft.md`，**不進主對話**。
2. **修改**：兩條路。使用者直接下 `/plan add／insert／edit／del／move／show`（完全不經過模型）；或用說的，這時規劃 session 只輸出「要套用的操作」（`format=PLAN_OPS_SCHEMA`：add／insert／edit／delete／move），由 harness 套在草稿上——模型沒有機會重寫整份。
3. **核准**：`y` 之後任務原文＋`[PLAN_CONFIRMED]` 才進主對話，自動退出 Plan 模式；步驟與進度每次都顯示在動態區（`plan_block`）。規劃與修改階段從頭到尾不呼叫 `run_tool()`，確認關卡由程式路徑保證。核准計畫不等於核准每一個會改變狀態的動作，執行時一樣經過執行前確認。
4. **自動推進**：`plan_on_exec` 依執行紀錄判斷——這一步的技能執行成功就換下一步（「不需技能」的步驟在後面的技能成功時一起算完成；最後剩下都不需技能時，模型回答就算做完）。模型不必自己勾（先前讓模型自己維護清單的 `plan_task` 實測不穩定，已移除，見 2.11）。工具結果要不要加入上下文照 auto／hybrid／manual：沒開 `/auto on` 就每一步都要你確認。
5. **`/plan_exec_guard on|off`**（預設關；`AGENT_PLAN_EXEC_GUARD=1` 改預設）：只在有執行中的計畫時生效。開啟時，**不是目前這一步、又會改變狀態**的技能不執行，回 `[PLAN_BLOCKED]` 告訴模型現在是第幾步；唯讀技能、載入規格、存檔工具、這一步的技能都放行（小模型要保留修正錯誤的空間，例如 `[ERROR]` 後先用 `docker_containers` 查清楚）。模型停下來而計畫還沒做完時，自動送 `[PLAN_CONTINUE]` 提醒它下一步，使用者不必自己催。被擋、`[ERROR]`、停下來連續 `PLAN_MAX_FAILURES`（3）次就退出計畫（`aborted`），告訴使用者卡在哪一步。關閉時計畫只有顯示與進度，沒有任何限制。
6. **生命週期**：執行中的計畫在你中途插話時**保留**（舊版送出新訊息就清掉，回答 AI 的追問也會把計畫清掉）；做完或退出的計畫在下一個新任務時清除；`/plan done`、`/clear` 隨時清除。

### 2.9 多模態影像：`vision/` library 與 📷 附圖

影像邏輯集中在頂層套件 `vision/`，三個使用者共用：Web Console 的 📷 附圖、`vision/sniper.py`（框選截圖 → 推論的單頁工具）、`image_inspect` 技能。

- `vision/capture.py`：伺服器端螢幕擷取，WSL → PowerShell、Linux X11 → Pillow `ImageGrab` + `xrandr`；都沒有時前端改用瀏覽器的 `getDisplayMedia`（頁面需以 `http://localhost` 或 https 開啟）。裁切在瀏覽器端以原始解析度完成。
- `vision/images.py`：檔案、bytes、data URL、截圖裁切統一成 `PIL.Image`。
- `vision/inference.py`：`analyze(images, prompt)` 呼叫多模態模型（`VISION_MODEL`、`VISION_TIMEOUT` 可調；`format=` 可指定結構化輸出），失敗一律 `VisionError`。
- `vision/extraction.py`：`extract(images, user_text, sources)`，Web 附圖時給決策 AI 用的結構化提取（見下面「視覺提取」），模型呼叫仍走 `analyze()`。
- `vision/session.py`：`VisionSession`，螢幕選單 → 擷取 → 框選裁切 → 影像清單的工作階段。
- `vision/web/`：前端共用的框選覆蓋層與螢幕選單（`snip.js`／`snip.css`）。

**附圖如何進入主對話**：獨立視覺 sub-session——影像加使用者訊息先交給 `vision.extract()`（見下面「視覺提取」），結果以【系統影像分析】區塊（`[vision result]`）附在使用者訊息後再進入 `run_turn()`。主對話永遠是純文字，壓縮與 token 計量不需知道影像存在；代價是主 Agent 看到的是描述，追問需重新附圖。與影像有關的稱呼只在真的附圖時才出現在上下文（曾寫進 `AGENT.md` 導致模型在純文字對話裡也說「影像分析結果」）。視覺分析不套用工具回傳的精簡；長度提醒另用每張 600 tokens 的門檻（`VISION_WARN_TOKENS_PER_IMAGE`，結構化提取一張通常 400～700 tokens，套 500 的工具門檻幾乎每次都誤報），超過時卡片標 ⚠️。影像只在送出一次新任務時消費。

**視覺提取（2026-09-28）**：以前視覺 sub-session 是一段五條規則的 system prompt，使用者打的字直接當問題，回一段自由文字。main session 拿到的資訊跟使用者的情境對不太上：它分不出哪些是畫面裡讀到的、哪些是模型猜的，也不知道哪些東西可以拿去查系統。改成跟工具回傳的任務導向擷取同一個想法——**提取的順序與格式由程式保證**（`format=extraction_schema(張數)`），不是靠模型遵守範本：
- **每張影像依序提取**：`kind`（什麼畫面）→ `texts`（文字逐字照抄，一行一項）→ `overview`（系統性描述：整體佈局，再依位置逐一說出每個物體與區塊；沒有文字時要完整，因為決策 AI 只能靠它）→ `entities`（每個明確的個體：`name`、`name_from`〔影像中的文字／使用者說明／外觀判斷〕、`details` 外觀／位置／看得出來的狀態）→ `background`（個體以外的環境）。全部做完再寫 `relations`（多張之間的關係）、`clues`（可以拿去查系統的線索：編號、容器、topic、路徑、錯誤訊息，照抄）、`unclear`、最後才是 `focus`（針對使用者說明的重點）。JSON 的欄位順序就是生成順序：重點放最後，讓它根據已經提取出來的內容回答，不是先下結論再找證據；排版（`render_extraction`）時才把重點移到最上面。
- **使用者說明的三個用途**：決定關注方向（相關的文字與細節優先、完整地提取）、告訴視覺模型畫面裡某個東西是什麼（「黃色那台是 amr_03」→ 照它命名並標〔使用者說明〕，決策 AI 分得出這不是影像裡讀到的）、補充屬性；說法跟畫面明顯矛盾時照畫面寫並列進無法判斷；說明裡要系統做的事（「幫我重新派工」）不是給視覺模型的。只附圖沒打字時，視覺模型拿到的是「沒有說明：依順序完整提取」，而不是那句預設提示詞。影像來源（螢幕框選的區域／上傳的檔名、尺寸）一起告訴它（`VisionSession.take_all_items`、`describe_sources`）。
- **交給 main session 時附上用法**：「文字」「線索」照抄、可以直接當技能參數；〔使用者說明〕的名稱不是影像裡讀到的；「無法判斷」的不要自己補；影像只是某一刻的畫面，要現況就用技能重查。這幾句只在附圖時出現（同上，影像相關的稱呼不寫進 `AGENT.md`）。
- **長度上限由 schema 硬性規定**：實測 e4b 遇到沒有文字的影像時 `texts` 會一直輸出空字串直到 `num_predict` 用完（兩張圖、沒打字的情境 2/2 發生），JSON 斷掉、七千字的殘骸差點交給 main session。Ollama 的結構化輸出會照 `minItems`／`maxItems`／`maxLength` 生成（實測確認），所以 `images` 剛好等於附上的張數、每個陣列與字串都有上限——一定是合法的 JSON；字串上限放寬到正常內容碰不到，真的碰到時排版退回最後一個完整句子，照抄的單行被切會標「後面未抄錄」。另外兩個實測到的小毛病在排版時處理：同一段推論重複寫兩三次（去掉重複的句子）、prompt 寫了「不超過 60 字」之後模型在欄位裡寫「(總字數：59/60字，符合要求)」（拿掉數字限制，並移除這類註記）。JSON 仍解析不了時改用純文字格式再問一次（`FALLBACK_SYSTEM_PROMPT`），不讓斷掉的 JSON 進主對話。
- **實測（e4b，四個情境：終端機錯誤＋問題、無文字場景＋命名提示、兩張圖沒打字、中文介面＋要系統做事）**：最終版 3 輪 12 次 JSON 全部合法。終端機 6 行文字每次都完整照抄（舊版漏第一行、抄錯括號），線索抓得出 `/scan`、`amr_03`、任務編號；〔使用者說明〕與〔影像中的文字〕分得出來；兩張圖時有「影像之間」。改成「依位置逐一說出每個物體」之後，兩張圖沒打字的情境 3/3 都看到擋在路上的黑色箱子（改之前 0/2）；但給了「黃色是 amr_03、藍色是貨架」的命名提示時只有 1/3——e4b 會把注意力收斂到使用者提到的東西。26b 同一組兩輪：命名提示的情境 2/2 看到箱子並說明「位於兩者行進路徑的中間」，中文「異常：雷達逾時」也讀對（e4b 一直讀成「電逐漸時」）。漏看小物體與小字讀錯是 e4b 的視覺能力，prompt 救不回來；對影像依賴高的場景可以只把 `VISION_MODEL` 換成 26b（主模型不變）。端到端（e4b 當 main session，舊版與新版各跑）：五個情境裡 main session 選的技能沒有可量測的差異（要不要查、查什麼主要由問題決定）；「查畫面裡這個 topic」兩版都從影像拿到 `/scan` 去查，都沒有直接用畫面上的容器名稱 `rmf_core`，而是先列容器。新格式的效益目前在提取本身的完整度與可追溯性，不是 main session 的行為。

**附圖分析存成 #編號、記進檢索清單（2026-09-28）**：視覺分析原本只併進那一則使用者訊息，沒有存檔、也沒有進 `tools_use_index.md`——訊息被壓縮或換了 session 之後，main session 與獨立 session 都沒有辦法像工具回傳一樣從檢索清單認出它、`result_recall` 取回。現在分析成功就存成一份存檔（`archive_vision_result`，腳本欄 `vision_extract`，同一套編號與目錄），檢索清單的描述是視覺模型在同一次輸出裡寫的 `index_hint`（schema 最後一個欄位，寫法同工具回傳「<使用者想知道什麼>：<影像是什麼、關鍵名稱或結果>」，整句不截斷；純文字退路時用使用者的說明＋重點組一句）。它放在工具使用檢索清單那一區、前面標〔附圖分析〕，沒有另開一區：它跟工具回傳一樣是「之前看到的資料」，不是過去的對話，小模型少一區要判斷。種類跟對話片段一樣看檔名（`result_kind`）。原圖不存，recall 時獨立 session 被告知只能根據當時的分析文字回答、沒寫到的要請使用者重新附圖；因為重跑不回來，保留上限跟對話片段一樣另外算（`VISION_RESULTS_KEEP`＝100）。不記進操作軌跡（不是執行腳本）。真模型實測（e4b，附終端機截圖問「amr_03 為什麼停下來」後換一個新 session）：問「上次那張終端機截圖裡被重新指派的任務編號」3/3 第一步就 `result_recall` 那筆、答出 `wp_20260928_0142`（這個編號不在清單描述裡，是從存檔的逐字文字取回的）；問分析裡沒有的「視窗標題列」2/2 照實說資料裡沒有提到。同一個 session 立刻追問時 2/3 直接依上下文回答、1/3 多 recall 一次（答案一樣，多一次模型呼叫）。

### 2.10 自建技能：`/make_skill` 把做對的對話整理成流程技能的規格

把一件事做對之後（不論是否用 Plan 模式），輸入 `/make_skill <技能名稱>` 就能把這段過程變成可重複使用的技能。2026-10-01 重構：舊版只把「操作軌跡」（執行了哪些腳本、什麼參數）交給模型填參數化表單，再產生一支依序執行那些腳本的組合腳本（`_composite.py`）。實際用起來的問題是：做一個技能光知道用了哪些技能不夠，很多步驟跟使用者當時的對話有關——要先跟使用者確認的地方、要看某個回傳的某個欄位再決定怎麼走、使用者中途補充或糾正的做法，這些都不在軌跡裡，組合腳本也表達不了「停下來問使用者」。新版把**整段對話與工具回傳**交給草擬模型推論，產出的是一份**流程技能的規格**，不產生任何腳本。分工：**harness 記錄對話與軌跡、挑範圍、驗證、用範本排版、寫入索引；模型讀對話寫內容；使用者在預覽後核准**。新的腳本仍由使用者另外寫好（例如跟 Claude 討論後建立），再產生對應的規格。

1. **對話紀錄**（`SkillAgent.transcript`，`trajectory.py`）：這個 session 每一則訊息的副本——使用者的話、AI 的想法／回覆／action、當時進上下文的工具回傳——只增不減，存在 `messages` 之外。訊息會被壓縮刪掉、被 `/clear` 清掉、被 claude_code 清成佔位，所以在這些事之前抄（`_sync_transcript`：呼叫主模型前、記軌跡時、壓縮刪除前、`/clear` 前、`/make_skill` 前）；claude_code 換成佔位時新的 dict 標成已記過（`_transcript_replaced`），對話紀錄留的是清除前的原文。**起點**（`transcript_starts`）：`/clear` 與 make_skill 落在當下的尾端；計畫核准落在那則任務訊息，並記下計畫內容（計畫的步驟在動態區，不在 `messages`）。**操作軌跡**照舊（`trajectory`），每一步另外記下它在對話紀錄的位置（`transcript_pos`）。
2. **挑範圍**（`transcript_scope`）：預設「上一個起點之後」；`all`＝整個 session；`3-7`、`3,5,8`＝這幾個軌跡步驟，對話從第一步之前使用者的那句話開始、到最後一步之後使用者的下一句話之前。
3. **草擬**（`draft_skill_from_conversation`）：獨立一次性 session，`format=MAKE_SKILL_SCHEMA`（陣列與字串都有上限）。輸入：可用技能清單（`SKILLS.md`）、這段用到的技能的「# 語法」、操作軌跡（成功／失敗＋輸出開頭）、**使用者在這段說的話**（程式另外列成清單）、核准的計畫、整段對話紀錄（超過 `MAKE_SKILL_TRANSCRIPT_TOKENS` 時先把工具回傳縮成頭尾，還不夠才從最舊的訊息省略並註明）。輸出依序：用途 → **使用者的要求**（`requirements`：每一項照抄使用者的原話、寫明怎麼遵守、落實在第幾步）→ 需要的資訊（`{名稱}` 佔位符：說明、從哪裡取得、對話裡的實際值）→ 步驟 → 成功判準 → 注意事項 → 最後才是標題、索引描述、分類。步驟分四種：**執行**（呼叫既有技能的腳本，含失敗時怎麼辦）、**確認**（停下來問使用者）、**檢查**（看前面的回傳、依條件決定怎麼走）、**告知**（整理結果給使用者）。模型由 `AGENT_SKILL_MODEL` 指定（預設同摘要模型）。
4. **驗證**（`_normalize_skill_draft`）：執行步驟的指令必須是 `scripts/` 裡真的有的 `*_cmd.py`（或 `result_recall` 偽技能），否則是**錯誤、不能註冊**；技能名稱跟腳本對不上就改正並提醒；指令與做法裡沒宣告的 `{佔位符}` 補進「需要的資訊」並提醒；非執行步驟帶了指令就忽略並提醒；要求指到不存在的步驟改列為注意事項；分類不存在放「自建技能」；用到這段對話裡沒實際執行過的技能也提醒。
5. **排版**（`render_skill_doc`）：`tools/<名稱>.md`，frontmatter 是 `type: Procedure`、`dependencies` 是步驟用到的技能；段落：用途、使用者的要求（必須遵守）、需要的資訊、步驟（`【執行】…` 附 `EXECUTE:` 指令與失敗處理；`【確認】…（在 reply 問使用者、action 填 null）` 等）、成功判準、異常與注意事項（會改變狀態的步驟照常確認、底層技能的規格）。草稿先寫到 `skills_system/drafts/<名稱>/`（規格與 `draft.json`）。
6. **核准流程**：CLI（`_run_make_skill_flow()`）與 Web（`handle_skill_draft_response()`）共用狀態機 `start/revise/approve/cancel_skill_draft`。預覽列出讀了多少對話、需要修正的問題、提醒與完整規格；`y` 註冊（有錯誤時不註冊、草稿保留）；`n` 取消；其他文字＝修改意見，帶著上一版與意見、用同一段對話重擬。註冊只寫規格與 `SKILLS.md` 索引行，記一個新起點。
7. **用的時候**：模型以技能名稱載入規格時，`run_tool` 認得 `type: Procedure`，提醒「這個技能沒有自己的腳本：照步驟從第 1 步開始，一輪只做一步；確認步驟在 reply 問、action 填 null」；每個執行步驟就是一般的 `run_tool`，執行前關卡照常；流程技能的規格不參與「腳本屬於哪個技能」的對照（`_script_skill_map`），不會把 `ls_cmd.py` 這類腳本誤認成它的。
8. **實測（2026-10-01，評測的假工具，e4b 當 main session）**：引導對話四句——看每台車的電量、「低於 20% 的車另外列出來、先不要派任務」、「派 tb1 從 home 到 a3，派之前要先跟我確認站點和車」、「確認，派吧」。對話本身就不順：e4b 讀錯 topic、讀不到電量，第三句也沒問就直接派了。第一版（沒有 `requirements`）兩個模型都漏掉使用者說過的條件（e4b 甚至把描述寫成「低電量就自動派送回充」）；先列使用者的要求、程式另外附上使用者的原話之後，兩個模型都把三個要求逐條列出並落到步驟（包括 AI 當時沒做到的「派之前先確認」），26b 的步驟對應與注意事項（「不能用 `--topic`」「讀不到電量就不能做低於 20% 的判斷，要先回報」）明顯比 e4b 好，e4b 的檢查步驟會寫錯「跳到第幾步」。草擬耗時 e4b 約 8 秒、26b 約 5 秒（第一次 150 秒是換模型載入）。把 26b 的草稿註冊後開新的 session（e4b），使用者說「派 tb2 從 home 到 b1，派之前先檢查車隊電量」：模型自己選中這個流程技能、照步驟依序執行，讀不到電量時照注意事項先回報，在派工前明確問「請問以上資訊是否正確，是否要我繼續執行派工指令？」，使用者確認後才派——原本那段對話裡沒做到的，透過規格做到了。
9. **引導建議**：一個技能只做一件事；引導時把要確認的地方、條件、偏好說出來（這些會變成「使用者的要求」）；會變的值用真實值引導；只有一句話的做法用 `modify_memory` 記住就好。草擬模型建議用 `AGENT_SKILL_MODEL=gemma4:26b`。

### 2.11 2026-09-27：對照前沿 harness 的六項修改與兩種上下文模式

起因是一次對照 Claude Code、Manus 與 Anthropic〈Effective context engineering for AI agents〉的檢討，列出六個「不是規模不同能解釋」的問題。每一項的做法、理由與實測如下（程式怎麼組織見〈架構說明〉1.1、3.4～3.6、6、12 節）。

**1. 長期記憶不再無聲截斷，也有「會過期」的概念**：見 2.7。沒有改動 `Memory.md` 既有的內容；裡面「系統整體健康」「資源不足」兩條是當時的狀態快照，要不要刪由使用者決定。評測的 `memory_stale_state`（記憶裡有「系統整體健康」、問現在健不健康）第二輪 harness 模式 0/3：模型跑去 `result_list` 翻存檔、找不到就反問，而 claude_code 模式 3/3——差別在 claude_code 的規則固定有「問現在的狀態就重新執行工具」，harness 模式這句只寫在檢索清單裡，沒有舊存檔時清單不出現，這句也跟著不見。把它移到 `prompts/context_modes/harness.md` 第 0 條（一直都在）、記憶說明也點名要執行哪類技能之後，3/3。

**2. 壓縮時使用者原話由程式保留、被壓掉的對話也存檔**：摘要目標 600 → 1500 字；使用者原話逐字保留在「使用者說過的話」一節；被壓掉的片段存成 `#編號`（跟工具回傳同一套、記進檢索清單、可 `result_recall`）。這是 Claude Code 壓縮時「摘要裡列出使用者每一則訊息、並附完整對話紀錄路徑」的做法，也就是工具回傳那套可還原壓縮用在對話本身。

**3. 模型自己維護的任務清單（`plan_task`，已移除）**：對應 Claude Code 的 TodoWrite，做過一版腳本式的偽技能（`set`／`done`／`fail`，harness 模式依執行紀錄自動打勾、claude_code 模式模型自己勾）。使用者實測後覺得很不穩定（4B 模型會為單一步驟的任務也先列清單、編出 `plan_task_done` 這種不存在的指令、自己勾選多出一倍的動作），2026-09-27 拿掉，連同評測的 `plan_multistep` 情境。下表 plan_multistep 那一列是拿掉前的結果，留作紀錄。`/plan on` 核准的計畫照舊，只是改顯示在動態區。

**4. prompt 排列顧 KV cache**：system prompt 只放不常變的，Current Agent State、Objective、已核准的計畫移到每次接在最後一則訊息後面的動態區（不寫進歷史）。**檢索清單沒有跟著移**：分析時的建議是整份移到尾端，實作前算了一下，清單一千多 tokens，放在每次都要重算的尾端，等於每次呼叫多重算一千多 tokens；而它只在跑完獨立 session 時才多一筆（同一個模型時那一刻 cache 本來就被洗掉）。所以清單留在 system prompt，動態區只加一行最新一筆（對話一長，system prompt 尾端落在上下文中間，模型容易忽略）。另外加了 `logs/perf.jsonl`：`prompt_eval_count` 在 cache 命中時仍是完整長度，看不出命中，要看 `prompt_eval_duration`。最終評測的實測（RTX 5090、Ollama 0.34.4、gemma4:e4b，`evals/chat/perf_report.py`）：

| 主對話呼叫前發生了什麼 | harness：次數／每 1000 tokens 毫秒 | claude_code：次數／每 1000 tokens 毫秒 |
|---|---|---|
| 沒變（cache 應該命中） | 101 次／7.5 | 129 次／7.3 |
| system prompt 變了 | 6 次／50.3 | 22 次／37.4 |
| 跑過獨立 session 之後 | 18 次／24.6 | 5 次／13.0 |

cache 失效大約慢 5～7 倍；這台機器上一次失效約多 0.3 秒，較慢的設備會等比例放大。claude_code 模式沒有獨立 session 會洗掉 cache，檢索清單每多一筆造成的 system prompt 變動（22 次）就成了主要的失效來源——分析時預測過，列在 7.6。「跑過獨立 session 之後」沒有到完全重算的程度，推測 Ollama 保留了部分前綴，沒有再深究。

**5. 會改變實體狀態的動作，執行前由程式確認**：`guard.py`。以前 manual／hybrid 問的是「要不要把結果加入上下文」，工具早就執行完了；「派工單前先問」只是 `Memory.md` 的一條記憶。現在跟 Plan 模式同一個原則：由程式路徑保證，`run_tool` 沒有 `approved=True` 就不執行被擋的技能，auto 模式也一樣會停。為了不讓每個容器內的 `ls` 都要按確認，`docker_runcmd` 的唯讀指令放行（白名單要看參數：`source` 只認 `setup.bash`、`env`／`hostname` 不能帶參數、`sort -o`／`date -s` 不算唯讀…），判斷不了的一律問。評測第二輪抓到一個誤判：模型送 `docker_runcmd ls -l /opt/ros`（沒加引號），判斷只看最後一個參數 `/opt/ros` 而要求確認；改成照腳本的邏輯（第一個參數像容器名稱才當容器，否則整串是指令）後修正。

### 2.15 數據分析 agent：只做事實報告（2026-10-14 起；2026-10-17 整段量測；2026-10-22 程式量全部、模型只說明）

**為什麼改**（第八、九輪的數據）：
- 事實層已經穩：第九輪 140 次分析，報告裡 3084 個時間全部對得上數據，程式產物 5 次逐字相同。

  程式補時間窗、觀測角度）都要拿掉。

**一、數據技能（`_ros2_data_common.py` 與五支腳本）**
- **送進容器的方法**：原本每支腳本把自己 base64 後放在 `bash -c` 的參數裡；單一參數有 128 KB 的上限，共用模組又要一起送。改成 tar.gz＋base64
  經 `docker exec -i` 的 stdin 送進容器的暫存目錄（`_docker_common.docker_exec` 加了 `input_text`），執行完刪掉。主機不需要 ROS 2。
- **自訂訊息型別**：`ROS2_ENV_FALLBACK` 加上 `/workspace/install`、`/workspace/*/install`（這台的 ros2_web_container 是 `/workspace/app/install`），
  harness 用 ROS2_workspace_env 確認過的 Workspace（屬於這個容器時）另外載入。讀不到的 Topic 角色標成 undecodable，說明要先確認 Workspace。
- **路徑**：主機路徑依容器的 bind mount 換成容器路徑（`/home/david/ros2-web-app/app/…` ＝ `/workspace/app/…`），實驗名稱與 `latest` 相對於數據根目錄
  （沒設定時在容器的 /workspace 底下 4 層內找 `experiment_logs`）。成功操作的數據在輸出末行印 `[ANALYSIS_DATA]`，harness 同步成「目前分析的數據」
  （比照目標容器），之後的技能可以省略路徑。
- **Key 的類別**（`describe_keys`，每個 Topic 抽樣 120 筆判斷）：數值、向量（2～4 個浮點分量的訊息或固定長度陣列）、矩陣（covariance）、陣列、
  狀態（uint8／bool／octet、相異值少的字串、短的整數或字串序列＝集合）、鍵值（KeyValue）、文字、時間。toolkit 用子字串 `int` 判斷整數型別，
  `builtin_interfaces/Time` 也會中而被當成狀態跳轉；`sequence<…/ActionParam>` 被當成 scalar——都改成依 ROS 型別字串解析。
  **字串分兩種**：使用者的設計是「String 只給 Orchestrator」，但實際的數據裡很多字串其實是列舉（`mode`＝PROTECTIVE_STOP／NORMAL、
  `primary_reaction`＝INIT／NONE），它們的跳轉正是 worker 該看的；所以相異值 ≤8（或 ≤12 而且都很短）的字串當「狀態」，其餘是「文字」
  （worker 不量測）。DiagnosticArray 這種「有 name 欄位的訊息序列」依名稱展開（`status.level` 每個 status 一項），只列有變化的。
  空的序列要看宣告的型別：訊息的序列是「沒有項目」，基本型別的序列（`stop_reasons=[]`）是「空集合」這個狀態值（第一版把 28 個空的 values
  當成假項目）。分類規則改了就把 `INDEX_VERSION` 加一，舊的快取自動重建。
- **Log 的來源**：預設用 bag 裡的 /rosout（時間＝MCAP log_time，跟其他 Topic 同一個時鐘；範例數據 bag 裡 31 則、rosout.log 只有 11 則——
  `ros2 topic echo` 比錄製晚開始），沒有才用 rosout.log；只差在數字的訊息算同一句；rosbag2 自己的 Log（Subscribed to topic…，範例裡 31 則佔 22 則）
  預設不列、不交給 Orchestrator。編號 L# 在篩選之前編好，mcap_slicer --signal 與 analysis_run 用同一套。
- **寬鬆的寫法**（實測驅動）：e4b 的 worker 把時間窗寫成 `0.00s_30.54s`、`0.00,30.54`、`+0.00s,+30.54s`，四次量測白費；主對話自己加了不存在的
  `--measure max`。現在時間接受 `+秒`、尾巴的 `s`、`～`／`~`／`_`／`to` 分隔，小於 10 億的數字當距離數據開頭的秒數（不可能是 epoch）；
  主機端不認識的參數照認得的做完、輸出最後說明忽略了什麼（都是唯讀工具，比回錯誤讓模型重送一次省一輪）。

**二、多 agent 協同（`analysis_job.py`；2026-10-22 第十一輪的做法，第十輪改了什麼見〈四〉）**
- **同步的偽技能，不是背景服務**：只讀不改、通常一分鐘以內、不需要核准，所以照 ops_run 的做法在主對話的回合裡同步執行；
  進度經 `progress_callback` 推到 Web 右欄，產物寫在 job 資料夾給面板讀。
- **一次分析整段數據，最多 3 分鐘**（`ANALYSIS_MAX_SECONDS`，以整秒算：錄 3 分鐘常是 180.05 秒）。第九輪以前用 Log 訊號前後 5 秒的時間窗與
  動態切片，事實要靠 Orchestrator 挑對 Log（規劃漏挑時，時間窗外的變化根本量不到）。量整段之後，「沒有描述」就是「沒有變化」。
  更長的數據先用 mcap_slicer 切（主對話會做，或使用者指定）。
- **事實由程式量全部，模型只「選」和「說明」**：資料預備時 `mcap_analyzer --facts` 一次讀完整份數據，**每個可以解碼的 Topic 量全部的 Key**
  （數值、向量、狀態、鍵值、陣列；header 與共變異數除外）與訊息流，快取在 bag 資料夾的 `topic_facts.json`；`build_facts` 整理成有編號的事實：
  T#＝Topic（類別、發布、變化、到最後的值、沒有變化的項目）、E#＝事件（同一則訊息裡一起改變的項目算一個事件，項目全部列）、L#＝Log。
  時間線、前後 1 秒內的對照、同時發生、前後沒有任何變化的 Log、沒有量的 Topic 都從這裡算。哪個 Topic、哪個 Key 都量，同一份數據每次一樣；
  Orchestrator 的 worker 上限只決定「誰來說明」，沒有派到的 Topic 照樣有完整的事實與事件。
- **一則一則、有編號的輸出，不靠文字的長度**：worker 的說明（notes，最多 5 則）與 Synthesizer 的重點（highlights，則數上限跟著事實）都是
  `{refs, text}`——refs 指到 E#／L#／T#，text 一兩句話（格式上限 300 字只防失控）。時間由程式依 refs 補上（`_render_note`），模型不用寫、
  也不會寫錯；**重點引用的事件與 Log 的內容由程式列在那一則下面**（事件的完整內容、Log 的層級、節點與原文），模型只寫這一刻的重點——
  第十一輪第一版要模型寫「Log 的編號、層級與代碼」與事件的數值：lidar 同一時間 4 個 Topic、5 則 ERROR／WARN，模型逐項抄、寫滿 300 字被截斷，
  寫滿之後就結束整份（只剩 2～3 則）；抄數值時也偶爾把同一則訊息裡另一個項目的值寫錯（實測 1800 多個「由 A 變成 B」的寫法中約千分之一到二）。
  改成程式列出之後，模型寫「安全閘進入 ESTOP_LATCHED、安全指令變成 HARD_STOP」，正確的數值就在下面。一則寫到上限＝失控，交回一次，
  還是太長的截到最後一個完整的句子（`_salvage`），最壞只少那一則，不會像一整段摘要那樣被截斷在半句。
- **重要的時間點是程式給的清單，不是模型自己挑**（`_moments`）：時間線上的事件（狀態改變、開始／停止、中斷、恢復、第一則在中途）與 WARN 以上的
  Log，1 秒內的算一個時間點（M#）；只由反覆切換的 Topic 組成的時間點不算（計數抖動總是單獨出現；跟別的事件同時變的照算）。清單交給
  Synthesizer，每個時間點至少一則；寫完程式核對漏掉的時間點，跟有問題的那幾則一起交回一次，還是漏的由程式補一則（標「程式列出」，內容照樣列在
  下面）；每個時間點其他的事件與 Log 掛在第一則引用到它的重點（`also`）——那一刻的事實由程式列全，模型只寫重點。則數上限跟著清單
  （時間點＋反覆切換的 Topic＋2，至少 8、最多 24，num_predict 跟著放大）。第十一輪前幾版的教訓：固定最多 8 則時，產生器的 s1「重點涵蓋」82/96，
  沒過的一半已經寫滿 8 則；則數跟著事實之後 87/96，剩下的是模型照時間寫、上限用完就停（任務失敗那一刻沒寫到），或只引用一刻裡的幾個編號
  （同一刻安全閘 ESTOP_LATCHED 的事件沒引用）——固定的上限、讓模型自己挑重點，事實多的時候就會漏；改成清單＋核對＋程式補齊之後見〈六〉。
- **交回修正只補、不整份換掉**（`_retry_text`、`_merge_retry`）：只交回有問題的那幾則，要模型只輸出修好的；第一版通過的由程式保留，
  修好的併進來（同一組編號、同一段文字，或引用的編號全部已經在通過的裡面的，都不重複收——模型有時不照指示，把通過的拆開重寫一遍）。
  第一版叫模型「沒問題的照抄、輸出完整的」，實測常常少抄（camera：7 則裡 1 則太長，
  修正版只回 2 則，通過的 6 則跟著不見）——「輸出完整的一份」把保留通過的內容交給模型，是不必要的風險。
- **核對跟編號綁在一起**（`_check_note`，worker 與 Synthesizer 同一套）：refs 要是可以引用的編號（worker 只能引用自己那個 Topic）；
  不寫原因、誰造成誰、推測（`_NOT_FACT_WORDS`，Log 原文或量到的字串裡本來就有的不算）；寫「中斷」要引用中斷或恢復的事件、寫「開始發布」
  「停止發布」「恢復發布」要引用那種事件（`_PUBLISH_WORDS`）；文字裡寫的 +秒 要對得上引用的事實（±0.35 秒）。用詞是不是事實，看它引用的
  事件，不看整段數據有沒有這種事件——「整段持續發布的 Topic 寫成開始與停止」這種錯，引用的編號裡沒有 start／stop 就擋得下。
- **發布方式由內容與時間判斷**（`publish_pattern`，取代「10 則以上才判斷中斷」的則數門檻）：一半以上的訊息帶著狀態改變＝狀態改變時才發布
  （隔很久沒有訊息＝狀態沒變）；四分之三以上的間隔在中位數週期的 0.5～1.5 倍＝固定頻率；不到 3 則、其他＝只有一兩則、不定期。**只有固定頻率
  的 Topic 判斷訊息中斷與中途開始／停止發布**；其他的列出每一則的時間，第一則在錄製開始 5 秒之後的列成事件「第一則訊息」。
- **尖峰是「跳出去又回來」**（`find_spikes`，Hampel）：跟前後 9 筆的中位數差超過殘差 MAD 的 6 倍、前後回到原來的水準、而且夠陡（跳進去與跳出來
  都超過前後一步的典型值的 6 倍）。舊版「離均值 2.5σ」在 3 分鐘的感測器數據裡每個 Key 都量得到幾百個；斜坡換成定值（RobotState 的
  sequence.timestamp 歸零）、平滑的山頂（旋轉時四元數的 z）都不是尖峰。只有 ≤4 種值的數值（速度指令）列每次切換，不找尖峰。
- **對照只看時間，對不上的照實寫**：Log 與 Topic 的事件前後 1 秒內就列在一起（只寫早或晚幾秒），不說誰造成誰；事件沒有 Log 就標
  「沒有對應的 Log」，Log 前後沒有任何事件就標「沒有任何 Topic 的事件」——不硬對齊。
- **推測不進事實那一層**（第七輪的發現）：worker 只拿子任務（L# 換成時間）、自己那個 Topic 的事實與訊息定義，不給問題與 Orchestrator 的理解
  （理解裡有推測的原因，實測 26b 的 worker 照著寫「證實 L17 時 /cmd_vel_raw 中斷」32/40）。Synthesizer 只拿程式整理的事實與 worker 的說明
  （說明也是一則一則、核對過的），不給問題與理解。報告的分析過程不放 Orchestrator 的理解（完整的在 plan.json）。
- **訊息定義給 worker 當說明的依據**：MCAP 的 schema 存了每個型別的 .msg 原文（含註解與常數，例如 `LIMITED＝限速放行`），worker 用它說明
  欄位與值的意思——事實是程式量的，「這個值代表什麼」來自定義，不是模型猜的。
- **Orchestrator 檢查：相關的 Log 前後有變化、還沒有說明的 Topic**：WARN 以上或規劃時挑的 Log，前後 1 秒內有事件、還沒有 worker 說明的 Topic
  才是候選；沒有候選就不問。每一項要寫它對應哪一則 Log，程式核對 Topic 在候選裡、Log 是它前後的那幾則，最多 2 個、最多一輪。事實早就量好了，
  補派只是多一份說明。（第十輪的條件是「Log 前後量到的 Topic 都沒有變化」，量全部 Topic 之後幾乎不會成立，140 次 0 次觸發。）
- **主對話依報告的回答也核對**（`turn_guard.analysis_reply_check`）：回答裡有報告沒有的因果動詞（導致、造成、引起、引發、觸發、使得、歸因、根因；
  「可能」「是否」開頭的子句不算）就提醒一次、畫面附 ⚠️。報告最後一行的回答規則本身有這些字，核對時不算（實測第一版就因此漏抓）。
- **只有 Log 的錄製照樣出報告**：沒有可以解碼的 Topic、只有 /rosout 時（例如只錄到 bridge 的本地 domain），照樣整理去重後的 Log、
  WARN 以上的時間線與重點，不派 worker；有 Topic 卻一個都解不開才回錯誤（要先確認 Workspace）。第一版一律回「沒有可以分析的 Topic」，
  產生器的 s3 有 4 份這種錄製，評分全部算失敗。
- **T# 代表整個 Topic**：核對用詞與時間時，引用 T# 的一則連同那個 Topic 的事件算引用——「這個 Topic 在 +23.10s 至 +27.20s 連續發布（T3）」
  是對的（第一版只看 T# 本身沒有時間，交回 worker 重寫，143 個 worker 裡 5 次這種誤判）。
- **設定只存跟預設不同的值**（`save_analysis_settings`）：以前存全部的值，預設改了，存過設定的人仍是舊的預設（第十輪把 worker 上限從 4 改成 6，
  Web 存過設定的仍是 4）。舊版的設定檔讀的時候照用；在 ⚙️ 存一次就改成新格式。
- **時間戳與計畫由程式守**（第一輪起）：Orchestrator 只填 L# 與 T#，worker 看到的是 +秒；所有輸出的 +秒 都是距離數據開頭。計畫的 L#、Topic
  要存在、不重複、不超過上限，沒有變化的 Topic 不派（不算問題，記在 `skipped`）；問題具體列出交回修一次，還是沒有可用的指派就依「事件在相關的
  Log 前後」的次數補指派。

**四、第十一輪（2026-10-22）：第十輪留下的九個問題與結構化的修正**

使用者的要求：不找補丁（改門檻值這類），盡量用結構化的資訊輸出，讓以後的使用沒有副作用（例如不靠文字的上限），同時保持一定程度的說明。

| 1 | worker 上限 4 不夠（時間線 52/65，缺的全是沒派到的 Topic）→ 改 6 | 事實要靠模型挑 Topic、挑 Key | 程式先量全部 Topic 的全部 Key（`mcap_analyzer --facts`），worker 只說明；上限只決定誰說明，預設改回 4 |

## 5.4 離線驗證的做法

行為層面的回歸用 `evals/`（2026-09-27 起，見 2.11 與 `evals/README.md`）：同一組情境跑兩種上下文模式，真模型、假的外部工具、每次都在臨時副本裡跑。以下是改程式時搭配的 stub 驗證做法，接手時可比照：以假的 `ollama.chat`（回固定 JSON）驅動 `SkillAgent`／`web_console` 的流程；技能腳本對 `scripts/mock_server.py`（調度系統）或 PATH 前置的假 `docker`（容器技能）執行；把 `SkillAgent` 的 `script_dir`／`base_path` 等路徑指到暫存副本，避免測試寫進真的 `skills_system/`、`Memory.md`、`logs/trajectory.jsonl`；最後用 `gemma4:e4b` 真模型跑一組固定情境（每個技能至少一句自然語言需求、兩步驟任務、追問回查、plan 模式、`/summarize on|off` 前後對照、有／無 `Memory.md` 對照），以 auto 模式的完整迴圈執行並自動判定：是否先載規格再執行、有沒有猜腳本名、有沒有多餘的反問、有沒有把系統回傳說成「您提供的」、最終回答有沒有引用腳本算好的數字；對真系統只做唯讀操作，調度技能打 `mock_server.py`。

## 6. 已知限制

1. **小型本地模型的工具呼叫可靠度**：`gemma4:e4b` 偶爾會不下 `action`、直接「腦補」一份假的執行結果，或在未設目標容器且多個容器在跑時自行挑第一個。Plan 模式的確認關卡與 JSON 協議的「只看 action」消除了誤觸發，但擋不住模型自己編造結果；規格文件只能用文字要求「多個容器時請使用者指定」。
2. **`stt_engine` 綁死特定環境**：麥克風裝置名稱、Windows 路徑（`C:\temp`）、`ffmpeg.exe` 路徑寫死在腳本裡，僅適用作者的 WSL + Windows 錄音裝置。
3. **CLI 與 Web Console 不完全對等**：CLI 的 `objective set` 是多行輸入，Web 簡化成單行 `/objective set <內容>`；CLI 沒有 Auto 模式的輪數上限（有人在終端機前可 Ctrl+C）。
4. **單元測試還沒有整理成 `tests/`**：行為評測在 `evals/`（見 2.11 與 `evals/README.md`）；離線的自我測試有 `evals/chat/selftest.py`、`evals/analysis/selftest.py`、`evals/ops/selftest.py`（假模型、真的腳本），但還不是 pytest 的測試套件。評測情境只有 14 個、外部工具是假資料，通過不代表真實現場一定沒問題；情境本身的問法也會影響結果（例如「讀一下 /fleet_states_json」會被當成檔案路徑）。
5. **使用者輸入與工具回傳的 token 數是估算值**：只有 AI 回覆與整體上下文精確；夾雜大量程式碼或 URL 的內容誤差較大。`count_tokens()` 保留對 `ollama.tokenize()` 的偵測，日後套件提供時自動改用。
6. **背景壓縮是否真的平行取決於 Ollama 的 slot**：多模態模型目前被強制單 slot，同模型的背景摘要會讓下一次對話排隊；要平行需 `AGENT_SUMMARY_MODEL` 指定另一個模型。API 查不到 slot 數，程式無法自動判斷。
7. **融合摘要的長度只能靠 prompt 約束**：實測會超過目標約三成；`SUMMARY_MAX_PREDICT` 只是防失控的硬上限。
8. **（已移除）技能綁定記憶**：小模型判斷不了該不該把記憶綁到技能上（評測 6 次都寫全域），2026-10-01 整個移除，記憶只寫 `Memory.md`（2.7）。
9. **`/make_skill` 的草稿品質受模型限制**：步驟怎麼切、檢查條件寫得對不對、「跳到第幾步」指得準不準、哪些值該參數化，都是草擬模型從對話推論的；框架只保證引用的技能與腳本存在、佔位符有宣告（2.10），語意上的錯誤（例如 e4b 的檢查步驟指錯步驟、把讀錯的欄位名稱寫進指令）靠使用者看預覽、用修改意見糾正。實測 26b 明顯比 e4b 可靠，建議 `AGENT_SKILL_MODEL=gemma4:26b`。對話紀錄只存在這次啟動的記憶體裡，程式重新啟動之後就不能再用之前的對話做技能。
10. **JSON 協議下的空白回覆**：模型在字串裡用英文雙引號時會發生，屬機率性；框架自動重試一次並在提示詞禁用英文雙引號，重試仍空白時如實顯示。
11. **任務導向摘要受摘要模型與輸入上限限制**：擷取得對不對取決於 `SUMMARY_MODEL`（預設同主模型）；需要比較或計數的問題要靠腳本選項先算好（2.5「數值交給腳本算」），摘要模型自己數會錯；原始輸出超過 16000 字只讀頭尾，中間的內容只剩腳本自帶的統計（如 `ROS2_topic_echo` 的欄位變化）可依靠；主模型看不到原文，只能靠摘要裡的「未涵蓋」提示換參數重查。每次超過門檻多一次模型呼叫、同模型時與主對話序列執行，觀察型技能幾乎每次都會觸發。
12. **`result_grep` 是文字比對**：關鍵字要在原文裡出現才搜得到（同義詞靠 `a|b` 自己列），語意相近但字面不同的東西找不到；命中以行為單位，結構化內容用 `--block` 或 `result_view` 補整段。存檔依 200 檔／50 MB 輪替，太舊的會被刪。
13. **小模型會把「載入規格」當成「已執行」**：用 `docker_open <容器>`、`change_dir <路徑>` 這種帶參數的技能名稱載完規格後，直接當作容器已切換、目錄已切換而做下一步。規格載入的回傳現在會點名「你附的參數沒有被執行、狀態沒有改變」，18 情境實測後不再發生，但這是措辭層面的緩解，不是機制保證。
14. **同一 session 已載入某技能規格時，模型傾向重用它**：例如已載入 `list_dir` 後被問「專案裡檔名含 cmd 的檔案有幾個」，會用 `list_dir --filter` 在根目錄數（只看一層、得到 0）而不是再載 `find_file` 遞迴搜尋；索引描述改成只標明「一層／遞迴」時仍會答 0，改成腳本在 0 項時直接指示「如果問的是整個專案這個 0 不能當答案，請改用 `scripts/find_file_cmd.py` 遞迴搜尋」後實測會照做（腳本回傳裡的明確指示比索引描述有效）。摘要 session 在原始輸出沒有算好的數字時會自己數（實測 25 個 `.md` 數成 23），所以規格要求用 `--filter` 讓腳本算，摘要不比原文短時也改給原文。
15. **「您提供的」殘留**：工具結果的開頭與結尾都有框架句，18 情境仍偶爾（1～2 次）出現「根據您提供的…」；兩件事一起問時偶爾只答後一件。
16. **調度系統技能依賴 web_console 的版本**：`semantic_map` 需要 `/api/topology` 端點，舊版 web_console 會回 404；OverPending 的時序常數（`threshold_ovp_sec`、`threshold_recovery_sec`）以 distribute 的設定為準，規格裡的「約 10 秒」是預設值。
17. **自動追問與 `result_recall` 的關鍵字／理解品質仍受摘要模型限制**：自動追問跳到哪個 `suggested_questions` 全靠第一輪摘要自己給的 keywords，那組 keywords 想錯（例如答案其實在存檔別處、但 keywords 沒有覆蓋到）時，`result_grep` 會落空或抓到不相關內容，迴圈一路跳到上限後誠實回報「未涵蓋」——不會更糟，但也不會比人工下 `result_grep` 更準；跟既有限制 #11 同一類。`result_recall` 把整個問題交給獨立 session 理解，answer／facts 的正確性一樣取決於 `SUMMARY_MODEL`，需要比較或計數時一樣要看原始輸出裡腳本算好的數字，摘要模型自己數一樣會錯。兩者目前都只用 5.4 節同一套假 `ollama.chat` stub 方法驗證過，還沒有 18 情境等級的真模型回歸。
18. **工具使用檢索清單的「有沒有關」判斷靠小模型自行拿捏**：`index_hint` 由摘要模型產出（目標 60 字左右，不截斷），品質跟措辭是否有區分度直接影響之後 main session 認不認得出來；清單本身只給線索不給內容，main session 誤判「有關」時會多一次 `result_recall`（多一次模型呼叫，不會答錯，只是多繞一次），誤判「無關」時就是使用者得自己再問一次。第一版（清單列檔名、要模型改用 `result_ask`）在真實對話裡失敗過：問「隨便選一個腳本分析」時模型跑去 `result_list` 兩次再 `result_grep all error`，沒走到提煉——原因是四個 `result_*` 技能描述相似、`result_list` 的描述又寫「先看這個」；現在清單直接給 `result_recall` 語法、其他三個的描述改成「清單沒有相關項目時才用」。只用兩個情境的真模型測過（跨 session「之前列出來的那些腳本，隨便挑一個」→ `result_recall 1` 並帶使用者原話，提煉直接挑出一個腳本；同一段對話的同一句話兩次分別選了 `result_recall 1 "docker"` 與載入另一個技能的規格——「隨便選一個做內容分析」本身語意模糊，模型會自己補一個方向），還沒有 18 情境等級的回歸，跟既有限制 #17 同一類。提煉回來後模型有時會依延伸方向停下來問使用者要往哪一類深入，而不是直接對挑出的檔案動手（延伸方向清單的副作用，見 #17）。清單指到的原始檔也可能已經被 200 檔／50 MB 輪替清掉（見限制 #12），這種情況刻意不做同步清除，讓 `result_recall` 回 `[ERROR] 找不到結果` 並要模型如實告知。 2026-09-26 晚加上獨立 session 的 recall 建議後重測三個情境：摘要已經有答案的追問（預設模型與逾時、總共幾個檔案）都直接回答、沒有多 recall、也不再走 grep；「tools 裡的技能在 scripts 都有對應腳本嗎」會由摘要指出還需要上次的 scripts 清單、main session 照抄 `result_recall 2,1` 一次讀兩份後停下。但比對本身的品質仍受 4B 摘要模型限制：它答出「命名不完全一致（change_dir.md 對應 cd_cmd.py）」，沒有逐一列出哪些技能沒有對應腳本——要精確比對應該讓腳本算（同 2.5「數值交給腳本算」）。

76. **Orchestrator 挑的 Topic 仍有變化**：同一份數據跑幾次，派給 worker 說明的 Topic 可能有 2 種組合（第十一輪 overheat 的相關 Log 2 種）。
    第十一輪起事實不受影響（全部 Topic 都量），變的只是哪幾個 Topic 有 worker 的說明。
77. **主對話的「沒有執行卻宣稱做完」只認子句開頭或「我／我們」後面的說法**（`doc/archive/root_cause_reference/設計筆記_第1到9輪.md` 的 2.24 驗證第 5 點）：「已重新啟動 amcl」「我已經建立了」照樣提醒；
    前面有主詞的「nav2 已重新啟動」不再提醒（以前會，但同一條規則也把「指令已停止發布」這種描述數據的句子當成宣稱）。
78. **一次最多分析 3 分鐘（180 秒，以整秒算）**：程式量整段數據；更長的先用 mcap_slicer 切成 3 分鐘以內的片段（之後要分析更長的
    時間跨度，是多組 Orchestrator → Workers → Synthesizer 各管一段、再往上整合，還沒做）。事實裡每個項目的跳轉、切換列前 30 次與最後 10 次
    （次數是總數）、尖峰列 10 個、中斷列 20 次；時間線上同一個 Topic 反覆切換的事件只列前 5 個與最後 2 個（各 Topic 的結果寫總次數）。
79. **時間上的對照只看時間**（前後 1 秒、同時＝0.1 秒內）：對到不代表有關，對不到也不代表無關（例如逾時判斷的 Log 在停止發布 0.5 秒後）；
    出現超過 3 次的 Log 只拿第一次與最後一次對照；同一時間的事件很多時，「前後 1 秒內」那一欄很長。
80. **補派只在「相關的 Log 前後有事件、還沒有說明的 Topic」時問**：WARN 以上或規劃時挑的 Log，前後 1 秒內有事件、還沒有 worker 說明的
    Topic 才是候選；Log 前後沒有任何事件的不問（報告列在「前後沒有任何 Topic 變化的 Log」）。補派最多一輪、最多 2 個 Topic，
    不符合的（Topic 不在候選裡、Log 不是它前後的那幾則）直接不補。事實都已經量好，補派只是多一份說明。
81. **類別與發布方式是程式依量測結果判斷的**：尖峰是單獨幾筆跳出去又回來（跟前後 9 筆的中位數差超過殘差 MAD 的 6 倍、回到原來的水準、
    而且夠陡）：雜訊大的訊號不會被列成尖峰，但比雜訊小的真尖峰量不到；只有 4 種以下的值的數值列每次切換、不找尖峰。發布方式由時間與
    內容判斷：多個節點發布同一個 Topic、事件觸發的 Topic 是「不定期」，不判斷中斷與開始／停止（真的停了也不會標成中斷，只能從每一則的
    時間看）；固定頻率的週期是整段的中位數，頻率中途改變（例如 10 Hz 變 5 Hz、沒有超過週期 3 倍的間隔）不會被列成事件。
82. **JSON 字串的 Topic 沒有內容的事實**：amr_base_sw 有不少 Topic 是 JSON 字串（/robot_state、/amr_diagnostics、/current_station…），
    分析程式當成文字，只量訊息流（發布方式、每一則的時間）；裡面的欄位（例如 current_state.v）的變化不在事實裡。要看就用
    `mcap_analyzer --topic --key data --preview`。
83. **隨機情境產生器是模擬**（`evals/datagen/`）：感測器的數值是合成的、影像是全黑的小圖，RMF 的對外 domain 與機器人的本地 domain 放在
    同一份錄製；評分標準照分析程式的定義產生——分析程式的定義（門檻）改了，用 `refresh_truth.py` 重算評分標準（數據不變，不用重寫 bag）。
    實機的數據仍要用這台錄的 14 份與之後的實錄驗證。
84. **時間線的 Log 列有一部分跟著 Orchestrator**：WARN 以上的 Log、Topic 的事件每次相同；INFO 的 Log 只有被 Orchestrator 挑成相關的、
    或前後 1 秒內有事件的才列，挑法不同時間線就差那幾列（s3 的 gen_s3_016 兩次差一則 INFO）。報告的編號不受影響（E#、L# 在整理事實時就編好）。
85. **用詞表是字面的**：把欄位名稱翻成中文（active_reasons →「原因」）也會被當成寫了原因而交回（第十一輪 143 個 worker 裡 2 則）；
    換句話說的推測（例如「似乎」「看起來」，不在詞表裡）抓不到。

## 7. 未來方向

### 7.1 讓 AI 自己把檢索範圍縮小

`search_text`／`find_file`／`list_dir` 已是精準檢索的雛形，但大量結果的處理仍是「超過門檻就交給獨立 session 擷取」，擷取只會留下與當前目的相關的部分，撈得越多丟得越多。更根本的做法是在規格文件與 `AGENT.md` 裡要求模型先縮小路徑、關鍵字具體、必要時分批查詢；幾乎零成本，效果依賴模型是否遵守。

### 7.2 自我進化第二階段：需要新程式碼的技能

第一階段（2.10）只用既有腳本組成流程；需要新程式碼的能力，目前由使用者另外寫好腳本（例如跟 Claude 討論後建立），再產生對應的規格。之後可以讓較大的模型草擬腳本到 `drafts/`，harness 以對話紀錄與軌跡中的實際案例當測試 oracle 反覆執行、餵回錯誤讓它修正，通過且經使用者審核後才註冊；也可在 Plan 模式所有步驟完成時主動詢問「要做成技能嗎」。

### 7.3 滾動摘要也回到原始訊息重新抽取

工具回傳這一側的「回到原始輸出」已經做了（2.5 的存檔與 `result_grep`）。2026-09-27 起，被壓掉的對話片段也存成 `#編號`（2.11），`result_recall`／`result_grep` 都能取回；使用者原話也由程式逐字保留。還沒做的是讓滾動摘要本身「回到原始訊息重新抽取」：現在仍是「上一份摘要 + 新片段 → 新摘要」，細節會逐輪流失，只是原文不再消失。另一個延伸：存檔保留了 `ROS2_topic_echo` 的原始 YAML，可以對舊的擷取重跑 `--where` 門檻判斷，不必再等一次觀察。

### 7.4 `Memory.md` 的內化與整併

記憶目前只有 `Memory.md` 一處（技能綁定記憶已於 2026-10-01 移除）。尚未做的是：定期把條目重新分類（屬於某個技能用法的寫回那份規格，屬於規劃原則的內化進規劃 session 的 prompt），內化後刪除原條目，讓常駐的 `Memory.md` 不會無止盡增長。語料已備好：`logs/summary_*.json` 的 `results_and_errors`／`user_preferences`／`open_items` 欄位可供反思機制定期讀取、提議寫入。

### 7.5 補齊測試與可攜性

把 5.4 的驗證做法整理成專案內的 `tests/`（假 `ollama.chat`、`mock_server.py`、假 `docker`），並讓 CLI 的模型名稱也能由環境變數覆寫。評測（`evals/`）的情境可以繼續加：每修一個真實對話裡遇到的問題，就把那段對話變成一個情境，之後改 prompt 才知道有沒有退化。

### 7.6 claude_code 模式的下一步

- **會用工具的 subagent**：現在 claude_code 模式能委派的只有 `result_recall`（讀存檔、沒有工具）。Claude Code 的 subagent 是有自己工具迴圈的 agent；這裡可以做一個只准用唯讀技能、最多 N 步、結束只回報結論的子迴圈，讓模型把「大範圍探索」整包委派出去。
- **檢索清單不進 system prompt**：claude_code 模式沒有獨立 session 會洗掉 KV cache，檢索清單每多一筆就讓 system prompt 改變、整段歷史重算，實測是這個模式最主要的 cache 失效來源（2.11）。可以改成新的那幾筆先放動態區、壓縮時才併回 system prompt。
