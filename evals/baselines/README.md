## 怎麼比

- 自我測試：有沒過的就是 ❌；通過數比基準少（測試被拿掉、或環境少了東西而略過）列成要注意。
- 維運：只跑一次時，基準裡大多會過（≥ 3/4）的情境這次沒過才列；跑好幾次時，通過率比基準低超過 1/3 才列（模型有隨機性，單次的差別多半是波動）。
  另外列：有禁止動作的、秒數中位數超過基準的 2 倍而且多 30 秒以上的（2026-10-23 的 `--watch 300` 就是這樣被看到的）、總分低於基準最低分的。
- 主對話：通過率比基準低超過 1/3 的情境。
- 工作流沙盒：同維運的規則（通過率、禁止動作、變慢）。
- 提煉：找到的比基準少、多列的比基準多、回答說的數量不對。
- 數據分析回歸：每份數據的每個評分項目，通過次數的比例比基準低就列。

## 什麼時候更新

階段 commit 之後、確認要注意的項目都看過（是波動或已經處理），用那一次（或那幾次）的結果更新：

```bash
python3 evals/phase_check.py --save-baseline evals/results/<時間>_phase_check [其他的結果目錄…] --label "第 N 階段（<commit>）"
```

維運最好用 3 次以上的結果一起更新（`--save-baseline` 給好幾個 `_ops_` 目錄會合成一份）。

只更新其中幾項時加 `--only`，其他的基準不動：名稱是 summary.md 第一欄括號裡的 key（`skills`、`workflow_selftest`、`chat`、`ops`…），
有冒號的取冒號前面（`tools_live`、`analysis`、`extract`、`workflow`；跑的時候數據分析回歸叫 `analysis_regression`，這裡是 `analysis`）。

`--save-baseline` 只覆蓋維運的 `current`：要留下舊的基準當參考，先在 json 裡把 `current` 複製成另一個 key（`phase4_start`、`phase4` 就是這樣留的）。

第 4 階段更新了自我測試、主對話、工作流沙盒與維運（三次完整跑）；提煉、數據分析沒有改，沿用之前的。待辦 20、23（2026-10-25）更新了維運（三次完整跑）與 `skills`、`task_selftest`、`skills_sandbox`；工作流沙盒同時跑過一次（26b、e4b 都 14/14，跟基準一樣，沒有更新）。待辦 25（2026-10-25）更新了維運（三次完整跑；之前的 `current` 複製成 `todo20_23`）與 `task_selftest`（14）。
