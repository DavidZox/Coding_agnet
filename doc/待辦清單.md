# 待辦清單（已記錄、尚未開始）

2026-10-09 使用者指示：下面四項**先記錄、還沒有要開始做或測試**。依據是 [`benchmark_study/`](../benchmark_study/README.md) 的評測結果；要開始時，每一項都用固定版本重跑至少 3 次、以信賴區間比較改動前後（`benchmark_study/analysis/`）。

| # | 項目 | 為什麼 | 怎麼量 |
|---|---|---|---|
| 1 | **從規格抽出介面清單，做一致性檢查** | DevBench（只給規格的長任務）的失敗有 83% 是介面、名稱跟規格或測試不一致，而且多數名稱其實寫在規格裡 | DevBench 單元／驗收通過率；「介面不符」這類失敗的比例 |
| 2 | **長任務先由規格產生驗收測試，再開始實作**（test-first） | 測試看得到、能執行時，單元通過率 72～74%；只有規格時 10～24%——差距就是「有沒有可以執行的驗收標準」 | 同上；另外看產生的測試本身有多少跟官方測試一致 |
| 3 | **agent 執行的程式加上網路隔離** | 評測時 agent 為了驗證自己寫的下載功能，真的從網路下載了 268 MB；`code_run` 擋得住 `curl`／`wget`，擋不住程式自己連網路 | 安全性的回歸測試：程式嘗試連網路時要失敗並說明原因 |
| 4 | **用沒拿來開發過的資料驗證**：從 `~/fih_humanoid_amr/amr_base` 挑 10～20 個真實任務 | 自建情境是本專案自己寫的、DevBench 也被拿來找問題，結果偏樂觀；真實任務才知道日常使用的成功率 | 每個任務事先寫好驗收方式（測試或檢查清單），記錄成功率、時間、需要人介入的次數 |

## 第二次評測建議的下一步（也還沒開始，等使用者決定）

[`benchmark_study_2/`](../benchmark_study_2/README.md) 的評測（2026-10-10 完成）找到的問題，依優先順序排列。詳細的證據見那邊的《評估報告》第八節。

| # | 項目 | 為什麼 |
|---|---|---|
| A | **驗證要真的跑到測試**：0 個測試不能算通過；django 的測試標籤要對照 `tests/` 底下的目錄名稱；規劃時先試跑一次驗證指令 | v4.2 在 SWE-bench 有 16 題自認通過，只有 6 題真的解決；其中 3 題一個測試都沒跑到（已知限制 39） |
| B | **既有專案的回歸檢查**：修改前後各跑一次被改到的模組原本的測試；重現問題的測試要先確認在修正前會失敗 | 修好了卻弄壞原本的測試：v4.1 有 4 題、v4.2 有 3 題 |
| C | **規劃階段的 self-refine**：用程式檢查計畫（含 A、上面第 1 項的介面清單），把具體的問題交回規劃 session 改一次 | 文獻與這次的數據都支持「外部檢查＋交回」，不支持「請模型自己再想一次」 |
| D | **讓寫檔協議適用於不同模型**：worker 建立檔案後，決策的步驟看得到檔案大綱；要實作的函式已經存在時，不再呼叫內容通道 | Qwen2.5-Coder 當 worker 時 11～16% 的呼叫在空轉；v4.2 只改提示，次數沒有減少 |
| E | **列出計畫以外新建的檔案**，讓使用者決定要不要刪 | agent 會留下除錯、重現腳本（已知限制 40） |

量測時，每個條件至少跑 3 次。這次 v4.1 與 v4.2 各解決 7 題，只有 3 題相同；單次的變異大於改版的效果。
