## 2. 核心機制

### 2.1 兩種操作介面，共用同一顆大腦

- **CLI**：`python3 Agent_Runner.py`（入口只有幾行，REPL 在 `agent_core/cli.py`）；`--workflow <名稱> …` 是不用互動執行一份工作流的入口（2.18）。
- **Web Console**：`python3 web_console.py`（實作在 `web_app/`）。純標準庫（`http.server`，無 Flask／FastAPI），把同一套推理迴圈改寫成「每次 HTTP 請求處理一小段、以 NDJSON 串流逐筆回傳事件」：後端每完成一次推論或工具執行就立刻推一筆，前端邊收邊渲染。

核心（`SkillAgent`：對話狀態、技能載入、腳本執行、壓縮、token 門檻）都在 `agent_core/`（2026-09-26 從 `Agent_Runner.py`／`web_console.py` 拆出來，功能不變）。兩個介面只差在互動方式（終端機 vs. 兩欄式網頁），**不重新定義任何核心規則**，推理與工具執行邏輯完全一致。

### 2.2 回覆協議：固定 JSON，只有 `action` 會被執行

模型每一次回覆都是 `{"thought", "reply", "action"}`，由 `ask_ai()` 以 Ollama `format=AGENT_REPLY_SCHEMA` 強制結構。`reply` 是給人看的文字；`action` 是 `null` 或 `{"command": 技能名稱｜腳本路徑, "args": 參數字串}`。`parse_agent_reply()` 解析後，CLI 與 Web 顯示 `reply`（💭 thought 另外顯示，有 action 時附一行「▶ action」），`run_tool()` **只看 `action`**——`reply` 裡不論寫了什麼（解釋時抄的 `EXECUTE:` 範例、複述的整份規格）都不會被執行，「一次只做一步」也由單一 `action` 欄位天然保證。

- **非合法 JSON**：降級為顯示原文、該輪不執行，不退回文字比對。
- **空白回覆**（合法 JSON 但 `reply` 空、`action` `null`）：典型原因是模型在字串裡寫了英文雙引號，JSON 文法被迫提早結束。`ask_ai()` 帶著暫時提醒（不進歷史）自動重試一次；`AGENT.md` 要求 thought 精簡、thought／reply 不用英文雙引號。
- **兩階段完成率**：載入規格後回給模型的訊息是明確的下一步指令（「這一輪只是載入規格、還沒有執行任何東西：下一輪先把這個技能真正執行一次……不要向使用者解釋規格內容，也不要詢問是否要執行」），避免小模型停下來聊天，或跳過這一步直接做下一步（2.3）。
- `args` 刻意是字串：所有腳本都吃位置參數，規格裡 `EXECUTE: <路徑> <參數>` 的範例就對應 `command`＋`args`，含空白的參數用 `\"` 包住。

### 2.3 技能系統：索引 + 按需載入的規格 + 既有腳本

- **`skills_system/SKILLS.md`**：輕量索引，每個技能一行「名稱 + 描述」，永遠在系統提示詞裡；開頭另有共同慣例（`[PASS]`／`[ERROR]`、逾時、目標容器）。
- **`skills_system/tools/<name>.md`**：每個技能一份 OKF 規格（用途、語法、範例、回傳、異常；寫法見〈[技能撰寫規範](技能撰寫規範.md)〉），只在被用到時載入。
- **`skills_system/workflows/<name>.md`**：工作流（`type: Workflow`，2.18）：步驟呼叫既有技能的腳本、由程式推進；`SKILLS.md`〈工作流〉一節列出每一個的呼叫語法，執行一律 `workflow_run`。
- **`skills_system/scripts/<name>_cmd.py`**：實際執行的腳本。共用模組：`_path_common`（路徑）、`_shell_common`（外部指令）、`_docker_common`（容器與 ROS 2 環境）、`_rmf_common`（調度系統）、`_results_common`（存檔）、`_ros2_data_common`（數據技能）。

**兩階段派發（progressive disclosure）**：`run_tool()` 拿到 `action` 後，`command` 若對應到存在的 `tools/<name>.md`（或工作流的名稱），就把整份規格當系統回傳注入上下文、不執行（工作流附上 `workflow_run` 的呼叫語法；2026-10-23 以前 `/make_skill` 產生的 `type: Procedure` 流程技能仍讀得到，提醒照步驟一步一步做，第 6 階段清掉）；否則把 `command` 當腳本路徑執行。**沒有任何「技能名稱 → 腳本」對照表**，模型必須先讀規格拿到真實路徑才執行得了；猜錯檔名會收到可行動的 `[ERROR]`（檔名若含某個技能名稱，直接提示先載入該技能；`scripts/<技能>.py` 這種只差 `_cmd` 的寫法會被 `_normalize_script_name()` 補成正確檔名；填的是技能名稱、卻沒有這個技能時，明說它可能是舊摘要或記憶裡、已經移除的名稱，2.5）。載入規格的回傳開頭明說「這一輪只是載入規格、還沒有執行任何東西」，模型若在技能名稱後附了參數，還會點名那些參數沒有被執行、狀態沒有改變（實測 e4b 用 `docker_open <容器>`、`change_dir <路徑>` 載完規格就當作已切換，直接做下一步）。`action.args` 拆解時丟掉空字串、引號不成對時退回空白切分並去掉殘留引號（實測模型會送 `. ""`、`"""`）；原文另外經 `HARNESS_RAW_ARGS` 給要自己解析內容的技能（`file_ops`、`modify_memory`）。歷史訊息保存模型原始 JSON；壓縮摘要只取 `reply` 與 `[action]`，`thought` 不進摘要。

**手動載入**：Web Console 在輸入框打「/」的選單裡點技能（或 `/skill <名稱>`，CLI 同名指令），`manual_skill_block()` 產生的規格區塊（以 `[skill loaded]` 開頭）會附在下一則訊息後一起送出，省掉一輪「先載規格」；技能清單來自 `list_skills()` 解析 `SKILLS.md`。

**回傳慣例與逾時**：腳本一律由 stdout 回傳，成功以 `[PASS]` 開頭，失敗（含逾時）以 `[ERROR]` 開頭並附原因與下一步（〈技能撰寫規範〉）——`_content_for_context()` 靠這個前綴判定成功／失敗；狀態標記放在最後幾行（2.4）。沒有任何腳本自帶的門檻豁免：分析型輸出（`workpackage_status --watch`、`semantic_map`、`ROS2_topic_echo --duration`）也跟其他輸出一樣回傳完整資訊，超過門檻就交給提煉（舊版 `[PASS][digest]` 讓腳本自己的固定格式摘要放寬到 1500 tokens 直接進主對話，等於由不知道任務的腳本決定什麼重要，已移除）。每支會呼叫外部程序或網路的腳本都有自己的逾時上限（寫在規格裡），`run_tool` 另設 `TOOL_EXEC_TIMEOUT`（600 秒）當最後防線；腳本不讀標準輸入（`stdin=DEVNULL`），以非零 exit code 結束時補 `[ERROR]` 前綴、完全沒有輸出時給出明確訊息。

**工具結果如何進主對話**：以 user 角色、經 `tool_result_message()` 包裝——第一行 `[tool result]`（框架訊息判定、壓縮切點都認它），第二行【系統回傳】框架句明說「系統執行你上一輪 action（<腳本>）的結果，不是使用者提供的，不要感謝使用者」，CLI 三種模式、Web、捨棄通知都用同一個包裝。寫在每一則裡而不是只寫在 `AGENT.md`：實測 `AGENT.md` 已有 Harness Messages 規則，gemma4:e4b 仍會回「感謝您提供的語義地圖」；改用 Ollama 的 `tool` 角色也不行，gemma4 的模板會把 `tool` 訊息整個丟掉（模型完全看不到內容），這也是影像分析結果用同一招的原因。壓縮摘要渲染時框架句會被去掉，不佔摘要篇幅。

### 2.4 harness 替模型維護的狀態：工作目錄、目標容器、目前的數據

狀態放在 `SkillAgent`（`current_cwd`、`container_cwd`、`target_container`、`analysis_data`、`current_ros2_workspace`），顯示在動態區的 Current Agent State 與 Web 標題列，執行腳本時傳給腳本（cwd，環境變數 `TARGET_CONTAINER`、`CONTAINER_CWD`、`ANALYSIS_DATA`、`ROS2_WORKSPACE`）；腳本成功改變狀態時在輸出最後幾行印標記（`[CWD_CHANGED]`、`[CONTAINER_CWD]`、`[TARGET_CONTAINER]`、`[ANALYSIS_DATA]`、`[ROS2_WORKSPACE]`），`_sync_state_from_tool_output()` 只認輸出最後連續的標記行（容器的 log、指令的輸出裡剛好有同樣的字，不會改掉狀態）。`/clear` 不清這些狀態。

- **工作目錄**：`change_dir` 成功時印 `[CWD_CHANGED] 路徑`；之後所有腳本以它為 cwd，相對路徑自然生效。工作目錄不能用（被刪掉、沒有權限）時換回專案目錄並回 `[ERROR]`（2.16）。
- **目標容器**：預設空。容器技能省略容器名稱時用目標容器，沒有就回 `[ERROR]` 提示先 `docker_containers` 查、`docker_open` 選定；腳本成功操作某容器後印 `[TARGET_CONTAINER] <名稱>`（與目前目標相同時不印），所以目標容器＝最近一次成功操作的容器，`docker_open`／`docker_est` 是刻意選定或切換用。`AGENT.md`、`SKILLS.md` 要求模型直接用它、不再反問使用者要看哪個容器。第一個參數算不算容器名稱，各技能共用 `_docker_common.split_container_arg` 判斷（模型常忘記引號或省略名稱，3.2）；`docker_runcmd` 結束時的目錄印成 `[CONTAINER_CWD]`，指令裡的 cd 會保留到下一次。軌跡記錄也帶著它。
- **目前的數據**：數據技能成功操作的數據印 `[ANALYSIS_DATA]`，之後的數據技能可以省略路徑（2.15〈一〉）。

### 2.5 上下文管理：真實 token 尺度、雙水位線、滾動融合摘要

**Token 計量**：Ollama 沒有 tokenize API，所以 AI 回覆用 `eval_count`、整體上下文用 `prompt_eval_count`（精確），使用者輸入與工具回傳用「字元數 ÷ `chars_per_token`」估算，`chars_per_token` 每次呼叫後以 `prompt_eval_count` 重新校準（中文為主約 1.8～1.9）。所有門檻與 `num_ctx` 同一尺度；Web 標題列的 `ctx` 前有 `≈` 代表估算值。

| 常數 | 值 | 作用 |
| :--- | :--- | :--- |
| `NUM_CTX` | 32768（`AGENT_NUM_CTX`） | 每次請求給 Ollama 的 context 上限，主對話、壓縮摘要、工具摘要三種 session 共用；記憶體小的設備可設回 12288 |
| `TOKEN_THRESHOLD`（硬水位） | `NUM_CTX × 75%`（`AGENT_HARD_RATIO`） | `ask_ai()` 呼叫前若超過，一定**同步**壓縮（`ensure_context_budget()`），確保壓縮先於 Ollama 在 `num_ctx` 處的靜默截斷；背景壓縮進行中則先等它完成 |
| `SOFT_TOKEN_THRESHOLD`（軟水位） | `NUM_CTX × 60%`（`AGENT_SOFT_RATIO`） | 只在**回合結束後**檢查（`after_turn_compression()`）：答案已送出、模型閒著，切點落在任務邊界；`/parallel_cal on` 時在背景執行緒做 |
| `MIN_COMPRESS_TOKENS` | `max(1000, NUM_CTX ÷ 20)` | 軟水位的「值不值得」門檻：可壓的舊內容太少就不花一次模型呼叫 |
| `KEEP_RECENT_TOKENS` | `NUM_CTX × 15%` | 壓縮時保留最新這麼多 token 的原文，在訊息邊界切、不拆開指令與其 `[tool result]`（`_split_for_compression()`） |
| `SUMMARY_MAX_CHARS` / `SUMMARY_MAX_PREDICT` | 1500 字 / 2500 tokens | 融合摘要的長度目標（實測會超過約三成）與 `num_predict` 硬上限；被截斷時 JSON 解析失敗退回原文。使用者原話另外由程式逐字保留（2.11） |
| `SUMMARY_ARCHIVE_KEEP` | 30（`AGENT_SUMMARY_KEEP`） | `logs/` 只保留最近 N 份 `summary_*.md` 與同名 `.json` |
| `SUMMARY_MODEL` | 同主模型（`AGENT_SUMMARY_MODEL`） | 壓縮摘要與工具摘要用的模型；與主模型不同時背景壓縮才真的平行 |
| `TOOL_RESULT_TOKEN_THRESHOLD` | 500 | 單次工具回傳超過就交給提煉（2.16；`/summarize off` 時只給成功／失敗判定）；技能規格文件、已提煉過的結果、數據分析與工作流的報告例外（`is_exempt_result`）。完整內容仍顯示給使用者並標 ⚠️ |
| `EXTRACT_CHUNK_CHARS` / `EXTRACT_MAX_CHUNKS` | 8000 字 / 8 段（`AGENT_EXTRACT_CHUNK_CHARS`／`AGENT_EXTRACT_MAX_CHUNKS`） | 工具回傳的提煉每段多長、最多讀幾段（超過的依問題挑段落，沒讀的行號寫進未涵蓋）；放得進一段就一次寫完（2.16） |
| `EXTRACT_SUMMARY_MIN_CHARS` / `EXTRACT_SUMMARY_MAX_CHARS` | 400 / 1500 字 | 交給主對話的重點的長度目標：原文的四分之一，介於兩者之間（以前固定 400 字） |
| `EXTRACT_JOBS_KEEP` | 500（`AGENT_EXTRACT_JOBS_KEEP`） | `logs/extract_jobs/` 留最近幾次提煉的存檔 |
| `TOOL_USE_INDEX_SHOW` | 30（`AGENT_TOOL_USE_INDEX_SHOW`） | system prompt 尾端「工具使用檢索清單」顯示視窗筆數（工具回傳與附圖分析；對話片段另算）；設 0 關閉顯示（寫入不受影響） |
| `CONVERSATION_ARCHIVES_SHOW` / `CONVERSATION_SEGMENTS_KEEP` | 10 / 100（`AGENT_CONVERSATION_ARCHIVES_SHOW` / `AGENT_CONVERSATION_SEGMENTS_KEEP`） | 「過去的對話片段」一節顯示幾份／對話片段存檔保留幾份（跟工具回傳的 200 檔／50 MB 分開算） |
| `VISION_RESULTS_KEEP` | 100（`AGENT_VISION_RESULTS_KEEP`） | 附圖分析存檔保留幾份（跟工具回傳、對話片段分開算；原圖不保存，這份文字重跑不回來） |

Web Console 另有 `MAX_AUTO_ITERATIONS = 25`：Auto 模式連續執行工具超過此輪數強制中止本回合。所有 `ollama.chat()` 都帶 `num_ctx=NUM_CTX`（不帶時 Ollama 預設 4096 會在背後悄悄截斷）。

**滾動融合摘要**：`compress_context_to_file()` 切出保留區以外的舊訊息交給 `summarize_messages()`，摘要模型同時收到上一份 `rolling_summary` 與新片段（渲染成 `[user]`／`[assistant]`／`[harness …]` 純文字），輸出一份更新後的完整摘要取代上一份；結構由 `format=SUMMARY_SCHEMA`（overview／key_progress／results_and_errors／user_preferences／open_items）強制，`_render_summary_markdown()` 排成固定五段；另一個欄位 `segment_hint` 只描述被壓掉的這一段，寫進檢索清單（見下面「對話片段」）。每次壓縮寫 `logs/summary_<時間>.md` 與同名 `.json`，但 system prompt 只注入最新一份；啟動時從 `logs/` 最新一份載入，摘要跨 session 延續，`/clear` 不清，要完全重來請刪 `logs/`。以 `HARNESS_MARKERS`（`[tool result]`、`[vision result]`、`[skill loaded]`、`[PLAN_REQUEST]`…）開頭的訊息會被標成框架訊息，避免被記成使用者偏好。

**跨啟動接回的摘要可能過時（2026-09-27）**：滾動摘要啟動時從最新一份 `summary_*.json` 接回、`/clear` 也不清，很久以前的摘要會一直留在 system prompt（實際踩到：`plan_task` 移除後，舊摘要的未完成事項還寫著它，模型照著去叫）。三個處理：(1) `clean_summary`：注入前把提到「目前不存在的技能」的行拿掉（`stale_skill_names`：反引號包住、同一行有「技能」的 snake_case 名稱，或 `scripts/<x>_cmd.py`，在 `tools/` 與 `scripts/` 都找不到的），標題行留著，原本的摘要檔不改；**不點名**——第一版在 system prompt 寫「摘要裡提到的 plan_task 目前不是可用的技能」，e4b 3 次有 3 次反而先去叫它（小模型看到名稱就被提醒，否定句沒什麼用），改成整行拿掉後同一份舊摘要 6 次都沒叫。(2) 接回的摘要還沒被這次 session 壓縮過時（`summary_carried_from`），開頭註明是之前留下的、進度與未完成事項可能已經過時，使用者沒提起就不要主動接續。(3) `action.command` 填的技能既沒有規格也沒有腳本時，回「沒有這個技能……可能是舊摘要、舊對話或記憶裡提到、但已經移除的名稱」，不讓模型以為只是少載了規格。

**system prompt 成本**：`AGENT.md`、`SKILLS.md`、`Memory.md`、上下文模式的規則、滾動摘要、檢索清單每輪常駐（2026-10-24 以字數 ÷1.9 估：`AGENT.md` 約 7,500 字、`SKILLS.md` 約 7,300 字，各約 4k tokens；`Memory.md` 約 400 tokens）。新規則要精簡，技能專屬的引導放進 `tools/<name>.md`（載入時才進上下文）。`Memory.md` 裡「先載規格、等規格回來才照標明的腳本路徑執行」那一條刻意留著：2026-09-25 的 18 情境回歸裡，清空記憶的那一組 4B 模型會猜腳本檔名。

**`/parallel_cal on|off`（背景壓縮，預設關閉，`AGENT_PARALLEL_CAL=1` 改預設）**：軟水位壓縮改由 `start_background_compression()` 在背景執行緒進行，完成後 `_apply_compression()` 以物件身分把那幾則從 `messages` 原地移除，期間新加入的訊息不會遺失；通知放進 `pop_notices()`（CLI 下一次輸入後印出、Web 隨 stats 推送並每 4 秒輪詢）。**前提**：Ollama 要為模型配置 2 個以上 slot，或摘要模型與主模型不同——實測 Ollama 0.34 對多模態模型（gemma4）強制單 slot，同模型開背景壓縮時下一次對話會在 Ollama 內排隊；搭配 `AGENT_SUMMARY_MODEL=gemma4:26b` 之類的不同模型才有真正的平行，代價是第二個模型的記憶體與算力。算力弱的設備建議維持關閉。

**工具回傳的提煉（預設開啟；`/summarize off` 或 `AGENT_TOOL_SUMMARY=0` 關閉）**：超過門檻的工具回傳交給一次性、乾淨的獨立 session，依「使用者的目標」（`_build_task_anchor_text`：Objective、最新一句與前兩句使用者的話〔任務線：使用者回答追問時最新一句常只剩關鍵字〕、核准的計畫）與「這一步的目的」（`_last_assistant_step`：決策模型剛才的 thought／reply／action——在 agent 迴圈裡，比使用者的原話更精確的「當前問題」）從原文提煉：是資訊過濾，不是通用摘要；2026-10-23 起分段讀全文、程式核對行號（2.16）。主模型看不到原文，所以結尾附下一步建議（`_followup_guidance`，見下面）。CLI 印「🧠 獨立 session 任務導向摘要」、Web 以 🧠 卡片顯示，都是主對話實際收到的內容；摘要不比原文短時主對話直接收到原文（實測 700 tokens 左右的 `ros2 node info` 會被「展開」成 900 多）。提煉失敗或 `/summarize off` 時只給成功／失敗判定，附存檔編號要模型用 `result_recall`／`result_view` 回查、不要重跑。代價是每次超過門檻多幾次模型呼叫（同模型時與主對話序列執行）。

**數值交給腳本算，提煉只做過濾**：實測 gemma4:e4b 對「哪個檔案最新」「幾個 topic 含 costmap」這類比較／計數題 0/5 答對，開 `think=True` 也只有 2/5、一次 17 秒；26b 開推論才 3/3，但一次 35～60 秒。所以比較、計數、排序、門檻判斷全部放進腳本：`list_dir` 標頭給數量與「最新修改」、`--filter`／`--newest`；`find_file`／`search_text` 標頭給數量；`ROS2_topic_list`／`ROS2_node_list` 的 `--filter` 計數；`--where 欄位<值` 算出幾筆符合、第一筆符合的時間與值。提煉的 prompt 規定腳本算好的數字直接照抄、不得重數或推翻，寫的總數由程式核對（2.16）；各規格文件要求模型遇到這類問題改用對應選項。提煉 session 維持 `think=False`。

**工具結果存檔與回查（`result_list`／`result_grep`／`result_view`／`result_recall`）**：提煉會丟細節、原文進主對話會污染上下文，兩者都不選：每次腳本執行的完整原始輸出由 `_record_trajectory()` 順手存成 `logs/tool_results/<session>_<編號>_<腳本>.md`（簡單 key: value 檔頭：編號、時間、腳本、指令、cwd、容器、狀態、字數、當時的任務；不用 PyYAML），並在 `index.md` 記一行（提煉的回答回填到那一行）。編號＝軌跡 id，接在存檔目錄裡最大的編號後面（`_max_archived_id`；跨 session 唯一，純數字的 `#16` 在任何一次啟動都指到同一份——以前每次啟動從 1 起算，跨 session 檢索幾乎一定抓錯份），`/make_skill` 與稽核對得上。技能規格文件不存（它不是執行結果）。追問摘要沒寫到的內容一律 `result_recall <編號> "<使用者的話>"`（回原文依新問題提煉，不重跑工具）；`result_grep` 只用在找某個字串出現在哪幾行（正則長度上限 200、逐行比對帶 3 秒預算，防災難性回溯；路徑只取檔名鎖在存檔目錄）。保留最近 200 個檔且總量 50 MB（`AGENT_TOOL_RESULTS_KEEP`／`AGENT_TOOL_RESULTS_MAX_MB`），刪最舊的並同步索引；`logs/` 已 `.gitignore`（輸出可能含敏感內容）。CLI 印「📄 已存檔 #16」，Web 卡片標題帶編號並可點開 `/api/results/<編號>` 看原文。`result_recall` 是唯一沒有實體腳本的技能：要呼叫模型，`run_tool()` 在存在性檢查前攔下、在本程序內做，照樣記軌跡、產生新的存檔編號。

**工具使用檢索清單（Tool Use Index，2026-09-26）**：三段式的「動態檢索」——(1) `tools_use_index.md`（跟 `index.md` 不同檔）只在提煉真的跑過時記一筆：編號、時間、`session_id`、檔名，以及提煉 session 寫的 `index_hint`（約 60 字的完整一句「<使用者想知道什麼>：<這份原文有什麼>」，`TOOL_USE_INDEX_HINT_TARGET`）。描述**整句照存、不截斷**（`tidy_hint`）：以前截到 50 字，截掉的正好是後半段的名稱與結論，main session 認不出這筆跟現在的問題有關。這份**永遠只 append**，跨 session、跨重新啟動累加。(2) `get_system_prompt()` 每輪在尾端注入最近 `TOOL_USE_INDEX_SHOW`（30）筆，連同使用規則與 `result_recall` 的語法（`_tool_use_index_block`；原始檔已被輪替清掉的那幾筆不列，2.16）——這是「顯示視窗」不是資料上限；動態區另外提示最新一筆。(3) 主模型只做淺層判斷，依序：對話裡最近的工具回傳已經寫了那個具體名稱或數值 → 直接回答；在接續某一筆 → `result_recall <編號> "<這句話原文>"`（不必先載規格，也不要先 `result_list`／`result_grep`）；問「現在／目前」→ 重跑工具；都不像 → 當新問題。語意理解交給拿到完整原文的獨立 session：問題以 harness 自己記的任務線為主，模型給的參數只當「聚焦點」（實測小模型會把清單描述抄進參數當問題）。設計上刻意不要求模型自己比對清單去「想關鍵字」。

**下一步建議與對話片段（2026-09-26～27）**：
- **recall 建議**：提煉 session 也拿到檢索清單（排除正在處理的那筆，`_tool_use_catalog`），用 `related_records` 說使用者的問題「還需要」清單裡哪幾筆才答得完整（最多 2 筆；程式只留清單裡真的有的編號，`_validate_related`）。結尾的下一步建議依序：需要舊存檔 → 下一輪直接把「這一份＋那幾份」一起 `result_recall 2,1 "<問題>"`（最多 `RECALL_MAX_RECORDS`＝3 份，同一個整合才比得了——只能 recall 一份時，比較 tools 與 scripts 清單會來回跳：讀 #1 的說還需要 #2，讀 #2 的又說還需要 #1）；有沒讀到的段落或缺口 → 用自然的一句話問使用者，或用更具體的問題 recall；已經回答 → 直接回答。看過完整原文的是獨立 session，由它說夠不夠，主模型不必自己猜。
- **追問一律走 `result_recall`**：「之後可能想知道的」只列問題、不附關鍵字——以前附 `result_grep` 的關鍵字，模型把 `|` 改寫成 `OR` 又不加引號，grep 直接報錯（等於把主模型往「自己想關鍵字」推，跟「回原文依問題提煉」的方向相反）。附註、上下文模式的規則（`prompts/context_modes/`）、`SKILLS.md` 與規格文件都寫「追問存檔裡摘要沒寫到的內容 → `result_recall`」。
- **清單只收原始工具的結果**：`result_grep`／`result_view`／`result_list`／`result_recall` 的輸出（`DERIVED_RESULT_SCRIPTS`）不記進清單（會跟原本那筆重複佔位，recall 到它只拿得到摘要的摘要）；已經是提煉結果（`TOOL_SUMMARY_TAG` 開頭）的輸出不再提煉一次（`is_exempt_result`）。
- **對話片段有自己的描述與分區（2026-09-27）**：被壓掉的對話原文也存成 `#編號`（同一個序列，一個 `#編號` 只對應一份，`result_recall` 兩種都能用，小模型不必學新技能），描述是摘要 session 另外寫的 `segment_hint`——**只描述被壓掉的這一段**（以前拿整份滾動摘要的 overview，每份都差不多、又以「本次對話的重點是…」開頭）。system prompt 另有「過去的對話片段」一節（最近 `CONVERSATION_ARCHIVES_SHOW`＝10 份，附「問之前討論過／說過／決定過什麼就找這裡」的規則），不跟工具回傳搶 30 筆名額；保留上限也分開（對話沒辦法重跑拿回來，另外留 100 份，不被工具回傳的輪替刪掉）。取回對話片段時告訴獨立 session「這是過去的對話」，要它回答當時談了什麼、決定了什麼、使用者怎麼說。真模型實測（e4b／26b 各一次）：描述 50～86 字、都是完整一句，對話片段的描述是那一段的內容，不再是整段歷史。

**訊息則數視窗停用**：`SkillAgent(max_history=None)` 是預設，上下文大小只由 token 門檻決定，舊內容一律摘要歸檔而不是無聲丟棄；`max_history` 只保留為可選保險絲。

### 2.6 三種執行模式

- **Manual（預設）**：每次工具執行完都要人工確認是否把結果加入上下文（y／n／stop）。
- **Hybrid**（`/hybrid on`）：一樣詢問，但不論加入或捨棄都讓 AI 接續推論。
- **Auto**（`/auto on`）：工具結果自動帶入下一輪，直到沒有工具需要執行（Web 上限 25 輪）。

三種模式問的都是「要不要把結果加入上下文」，工具早就執行完了；會改變實體狀態的動作另外有執行**前**的確認（2.11 執行前關卡），三種模式都一樣。

### 2.7 記憶

- **全域記憶 `Memory.md`**：只有使用者明確要求（「記住這件事」等）才由 `modify_memory` 寫入，格式 `[問題種類] | [問題描述] | [解決方法或結論]`；`load_long_term_memory()` 每輪整份放進系統提示詞（2026-09-27 前只放最後 30 行，條目一多最舊、往往最基礎的規則會無聲消失；現在以條目計，超過 `MEMORY_MAX_CHARS` 才丟最舊的，並在提示詞與 UI 明說還有幾條沒載入）。開頭一句說明每條的時間是寫入時間、描述狀態的舊條目只代表當時；`AGENT.md` 的記憶協議也禁止把「系統整體健康」這類時間點狀態寫成記憶。
- **只有一個寫入去處**：記憶只寫 `Memory.md`，`modify_memory` 沒有任何選項（整個參數就是一個選項——例如舊的 `--skill`——時回 `[ERROR]`，不會把選項當成記憶內容寫進去），一條上限 300 字。2026-10-01 拿掉了技能綁定記憶（只在載入那個技能的規格時才進上下文）：評測裡 4B 模型 6 次都寫全域、判斷不了該不該綁，綁在技能上的規則在「選技能」的當下也看不到。某個技能的用法要固定下來，直接改那份規格；一段要照順序做、中間要問使用者的做法，用 `/make_skill` 做成工作流（2.10、2.18）。
- **滾動摘要**（`logs/summary_*.md` + `.json`）：見 2.5。
- **Sticky Objective**：`objective set|show|clear`（Web 為 `/objective set <內容>`），持續出現在系統提示詞裡直到清除。

### 2.8 Plan 模式：任務引擎的計畫審核（2026-09-27 改版；2026-10-24 併進任務引擎）

`/plan on|off`（CLI 打指令；Web Console 輸入框旁有 📝 Plan 切換鈕，點一下就是送出 `/plan on`／`/plan off`）。開啟後**下一個**新任務不直接執行，
先由任務引擎（2.19）規劃，使用者看過、改過、核准後才照計畫做。

1. **草稿**（`agent_core/plan.py`）：任務引擎規劃第一版（`task_plan`，mode＝plan；每一步的目標、技能或工作流、會不會改變狀態、做完怎麼檢查），
   草稿存在 `self.plan`（任務引擎的 job，`logs/task_jobs/<編號>/` 也有一份），**不進主對話**。也可以不開 `/plan on`，直接 `/plan add` 從空的草稿一條條列。
2. **修改**：使用者直接下 `/plan add／insert／edit／del／move／show`（完全不經過模型），或用說的——這時規劃 session 只輸出「要套用的操作」
   （`format=PLAN_OPS_SCHEMA`），由 harness 套在草稿上。**為什麼不讓模型重寫**（2026-09-27）：小模型每次重寫都不一樣——這次 3 條、下次 4 條、
   沒提到的步驟也被改掉。每一步照任務引擎同一套規則整理（技能存在、會不會改變狀態），有問題列在草稿下面。
3. **核准**：`y`＝計畫裡標明會改變狀態的步驟都核准了；使用者的任務進主對話，harness 不經過模型直接執行 `task_run --continue <工作>`
   （`take_task_continuation`；核准過的不會再問一次），任務引擎照這份計畫做（**不重排**：使用者核准的就是這一份；某一步失敗就停下來），
   報告進主對話後主對話依報告回答。規劃與修改階段從頭到尾不呼叫 `run_tool()`。
4. **2026-10-24 拿掉的**：核准後由主對話照計畫一步一步做（動態區的計畫、依執行紀錄自動推進、`/plan_exec_guard` 的執行前檢查與 `[PLAN_CONTINUE]`
   提醒、連續失敗退出）。理由：計畫的執行換成任務引擎（每一步一個乾淨的 worker、程式檢查、存檔），兩套執行路徑只留一套。

### 2.9 多模態影像：`vision/` library 與 📷 附圖

影像邏輯集中在頂層套件 `vision/`，三個使用者共用：Web Console 的 📷 附圖、`vision/sniper.py`（框選截圖 → 推論的單頁工具）、`image_inspect` 技能。

- `vision/capture.py`：伺服器端螢幕擷取，WSL → PowerShell、Linux X11 → Pillow `ImageGrab` + `xrandr`；都沒有時前端改用瀏覽器的 `getDisplayMedia`（頁面需以 `http://localhost` 或 https 開啟）。裁切在瀏覽器端以原始解析度完成。
- `vision/images.py`：檔案、bytes、data URL、截圖裁切統一成 `PIL.Image`。
- `vision/inference.py`：`analyze(images, prompt)` 呼叫多模態模型（`VISION_MODEL`、`VISION_TIMEOUT` 可調；`format=` 可指定結構化輸出），失敗一律 `VisionError`。
- `vision/extraction.py`：`extract(images, user_text, sources)`，Web 附圖時給決策 AI 用的結構化提取（見下面「視覺提取」），模型呼叫仍走 `analyze()`。
- `vision/session.py`：`VisionSession`，螢幕選單 → 擷取 → 框選裁切 → 影像清單的工作階段。
- `vision/web/`：前端共用的框選覆蓋層與螢幕選單（`snip.js`／`snip.css`）。

**附圖如何進入主對話**：獨立視覺 sub-session——影像加使用者訊息先交給 `vision.extract()`（見下面「視覺提取」），結果以【系統影像分析】區塊（`[vision result]`）附在使用者訊息後再進入 `run_turn()`。主對話永遠是純文字，壓縮與 token 計量不需知道影像存在；代價是主 Agent 看到的是描述，追問需重新附圖。與影像有關的稱呼只在真的附圖時才出現在上下文（曾寫進 `AGENT.md` 導致模型在純文字對話裡也說「影像分析結果」）。視覺分析不套用工具回傳的精簡；長度提醒另用每張 600 tokens 的門檻（`VISION_WARN_TOKENS_PER_IMAGE`，結構化提取一張通常 400～700 tokens，套 500 的工具門檻幾乎每次都誤報），超過時卡片標 ⚠️。影像只在送出一次新任務時消費。

**視覺提取（2026-09-28）**：以前視覺 sub-session 是一段五條規則的 system prompt，使用者打的字直接當問題，回一段自由文字。main session 拿到的資訊跟使用者的情境對不太上：它分不出哪些是畫面裡讀到的、哪些是模型猜的，也不知道哪些東西可以拿去查系統。改成跟工具回傳的任務導向擷取同一個想法——**提取的順序與格式由程式保證**（`format=extraction_schema(張數)`），不是靠模型遵守範本：
- **每張影像依序提取**：`kind`（什麼畫面）→ `texts`（文字逐字照抄，一行一項）→ `overview`（系統性描述：整體佈局，再依位置逐一說出每個物體與區塊；沒有文字時要完整，因為決策 AI 只能靠它）→ `entities`（每個明確的個體：`name`、`name_from`〔影像中的文字／使用者說明／外觀判斷〕、`details` 外觀／位置／看得出來的狀態）→ `background`（個體以外的環境）。全部做完再寫 `relations`（多張之間的關係）、`clues`（可以拿去查系統的線索：編號、容器、topic、路徑、錯誤訊息，照抄）、`unclear`、最後才是 `focus`（針對使用者說明的重點）。JSON 的欄位順序就是生成順序：重點放最後，讓它根據已經提取出來的內容回答，不是先下結論再找證據；排版（`render_extraction`）時才把重點移到最上面。
- **使用者說明的三個用途**：決定關注方向（相關的文字與細節優先、完整地提取）、告訴視覺模型畫面裡某個東西是什麼（「黃色那台是 amr_03」→ 照它命名並標〔使用者說明〕，決策 AI 分得出這不是影像裡讀到的）、補充屬性；說法跟畫面明顯矛盾時照畫面寫並列進無法判斷；說明裡要系統做的事（「幫我重新派工」）不是給視覺模型的。只附圖沒打字時，視覺模型拿到的是「沒有說明：依順序完整提取」，而不是那句預設提示詞。影像來源（螢幕框選的區域／上傳的檔名、尺寸）一起告訴它（`VisionSession.take_all_items`、`describe_sources`）。
- **交給 main session 時附上用法**：「文字」「線索」照抄、可以直接當技能參數；〔使用者說明〕的名稱不是影像裡讀到的；「無法判斷」的不要自己補；影像只是某一刻的畫面，要現況就用技能重查。這幾句只在附圖時出現（同上，影像相關的稱呼不寫進 `AGENT.md`）。
- **長度上限由 schema 硬性規定**：實測 e4b 遇到沒有文字的影像時 `texts` 會一直輸出空字串直到 `num_predict` 用完（兩張圖、沒打字的情境 2/2 發生），JSON 斷掉、七千字的殘骸差點交給 main session。Ollama 的結構化輸出會照 `minItems`／`maxItems`／`maxLength` 生成（實測確認），所以 `images` 剛好等於附上的張數、每個陣列與字串都有上限——一定是合法的 JSON；字串上限放寬到正常內容碰不到，真的碰到時排版退回最後一個完整句子，照抄的單行被切會標「後面未抄錄」。另外兩個實測到的小毛病在排版時處理：同一段推論重複寫兩三次（去掉重複的句子）、prompt 寫了「不超過 60 字」之後模型在欄位裡寫「(總字數：59/60字，符合要求)」（拿掉數字限制，並移除這類註記）。JSON 仍解析不了時改用純文字格式再問一次（`FALLBACK_SYSTEM_PROMPT`），不讓斷掉的 JSON 進主對話。
- **實測（e4b，四個情境：終端機錯誤＋問題、無文字場景＋命名提示、兩張圖沒打字、中文介面＋要系統做事）**：最終版 3 輪 12 次 JSON 全部合法；終端機 6 行文字每次都完整照抄（舊版漏第一行、抄錯括號），線索抓得出 `/scan`、`amr_03`、任務編號，〔使用者說明〕與〔影像中的文字〕分得出來。改成「依位置逐一說出每個物體」之後，兩張圖沒打字的情境 3/3 都看到擋在路上的黑色箱子（改之前 0/2）；但給了「黃色是 amr_03、藍色是貨架」的命名提示時 e4b 只有 1/3（注意力收斂到使用者提到的東西），26b 2/2，中文「異常：雷達逾時」也讀對（e4b 一直讀成「電逐漸時」）。漏看小物體與小字讀錯是 e4b 的視覺能力，prompt 救不回來；對影像依賴高的場景可以只把 `VISION_MODEL` 換成 26b（主模型不變）。端到端（e4b 當 main session）新舊格式選的技能沒有可量測的差異（要不要查、查什麼主要由問題決定），效益在提取本身的完整度與可追溯性。

**附圖分析存成 #編號、記進檢索清單（2026-09-28）**：分析成功就存成一份存檔（`archive_vision_result`，腳本欄 `vision_extract`，同一套編號與目錄），訊息被壓縮或換了 session 之後，一樣能從檢索清單認出、用 `result_recall` 取回。描述是視覺模型在同一次輸出裡寫的 `index_hint`（schema 最後一個欄位；純文字退路時用使用者的說明＋重點組一句），放在工具使用檢索清單那一區、前面標〔附圖分析〕——它跟工具回傳一樣是「之前看到的資料」，不是過去的對話，小模型少一區要判斷；種類看檔名（`result_kind`）。原圖不存，recall 時獨立 session 被告知只能根據當時的分析文字回答、沒寫到的要請使用者重新附圖；因為重跑不回來，保留上限另外算（`VISION_RESULTS_KEEP`＝100）。不記進操作軌跡（不是執行腳本）。真模型實測（e4b，附終端機截圖問「amr_03 為什麼停下來」後換一個新 session）：問「上次那張截圖裡被重新指派的任務編號」3/3 第一步就 `result_recall` 那筆、答出不在清單描述裡的 `wp_20260928_0142`（從存檔的逐字文字取回）；問分析裡沒有的「視窗標題列」2/2 照實說資料裡沒有提到。

### 2.10 自建技能：`/make_skill` 把做對的對話整理成工作流

把一件事做對之後（不論是否用 Plan 模式），輸入 `/make_skill <名稱> [範圍]`，就把這段過程整理成一份**工作流**（`skills_system/workflows/<名稱>.md`，`type: Workflow`；之後由 `workflow_run` 照步驟執行，見 2.18）。不產生任何腳本：步驟只呼叫既有技能的腳本，新的腳本由使用者另外寫好（例如跟 Claude 討論後建立），再產生對應的規格。分工：**harness 記錄對話與軌跡、挑範圍、驗證、用範本排版、寫入索引；模型讀對話寫內容；使用者在預覽後核准**。

**為什麼讀整段對話**（2026-10-01 重構）：舊版只把操作軌跡（執行了哪些腳本、什麼參數）交給模型填表，產生一支依序執行的組合腳本。可是很多步驟跟當時的對話有關——要先跟使用者確認的地方、要看某個回傳的某個欄位再決定怎麼走、使用者中途補充或糾正的做法，這些都不在軌跡裡。所以草擬模型拿到的是**整段對話與工具回傳**。2026-10-23（第 3 階段）起產出的是工作流；以前產出的 `type: Procedure` 流程技能（主對話自己照步驟做）不再產生，舊的仍讀得到，第 6 階段清掉。

1. **對話紀錄**（`SkillAgent.transcript`，`trajectory.py`）：這個 session 每一則訊息的副本——使用者的話、AI 的想法／回覆／action、當時進上下文的工具回傳——只增不減，存在 `messages` 之外。訊息會被壓縮刪掉、被 `/clear` 清掉、被 claude_code 清成佔位，所以在這些事之前抄（`_sync_transcript`：呼叫主模型前、記軌跡時、壓縮刪除前、`/clear` 前、`/make_skill` 前）；claude_code 換成佔位時新的 dict 標成已記過（`_transcript_replaced`），對話紀錄留的是清除前的原文。**起點**（`transcript_starts`）：`/clear` 與 make_skill 落在當下的尾端；計畫核准落在那則任務訊息，並記下計畫內容（計畫的步驟在動態區，不在 `messages`）。操作軌跡（`trajectory`）每一步另外記下它在對話紀錄的位置（`transcript_pos`）。
2. **挑範圍**（`transcript_scope`）：預設「上一個起點之後」；`all`＝整個 session；`3-7`、`3,5,8`＝這幾個軌跡步驟，對話從第一步之前使用者的那句話開始、到最後一步之後使用者的下一句話之前。
3. **草擬**（`draft_skill_from_conversation`）：獨立一次性 session，`format=MAKE_SKILL_SCHEMA`（陣列與字串都有上限）。輸入：可用技能清單（`SKILLS.md`）、這段用到的技能的「# 語法」、操作軌跡（成功／失敗＋輸出開頭）、**使用者在這段說的話**（程式另外列成清單）、核准的計畫、整段對話紀錄（超過 `MAKE_SKILL_TRANSCRIPT_TOKENS` 時先把工具回傳縮成頭尾，還不夠才從最舊的訊息省略並註明）。輸出依序：用途 → **使用者的要求**（`requirements`：每一項照抄使用者的原話、寫明怎麼遵守、落實在第幾步）→ 需要的資訊（`{名稱}`：說明、從哪裡取得、對話裡的實際值）→ 步驟（執行／確認／檢查／告知）→ 成功判準 → 注意事項 → 最後才是標題與描述。先列使用者的要求是實測來的（2026-10-01，評測的假工具）：沒有 `requirements` 時 e4b 與 26b 都漏掉使用者說過的條件（「低於 20% 的車先不要派任務」「派之前先跟我確認」），先逐條列要求、程式另外附上使用者的原話之後，兩個模型都把要求落到步驟。模型由 `AGENT_SKILL_MODEL` 指定（預設同摘要模型），建議 `gemma4:26b`：步驟對應與注意事項明顯比 e4b 好，e4b 的檢查步驟會指錯步驟。
4. **驗證**（`_normalize_skill_draft`）：執行步驟的指令必須是 `scripts/` 裡真的有的 `*_cmd.py`（或 `result_recall` 偽技能），否則是**錯誤、不能註冊**；技能名稱跟腳本對不上就改正並提醒；非執行步驟帶了指令就忽略並提醒；要求指到不存在的步驟改列為注意事項；用到這段對話裡沒實際執行過的技能也提醒。命令裡不是「需要的資訊」的 `{名稱}`（前面步驟的輸出才知道的值）執行時交給判斷點，列在提醒裡給使用者確認。排好的文件再交給工作流的解析與驗證（分支只能往後、腳本存在、`changes_state` 跟步驟一致），有問題一樣擋下註冊。
5. **排版與核准**：`render_skill_doc` 排成工作流的格式，草稿先寫到 `skills_system/drafts/<名稱>/`（規格與 `draft.json`）。CLI（`_run_make_skill_flow()`）與 Web（`handle_skill_draft_response()`）共用狀態機 `start/revise/approve/cancel_skill_draft`：預覽列出讀了多少對話、需要修正的問題、提醒與完整規格；`y` 註冊（有錯誤時不註冊、草稿保留）；`n` 取消；其他文字＝修改意見，帶著上一版與意見、用同一段對話重擬。註冊寫進 `workflows/` 與 `SKILLS.md`〈工作流〉，記一個新起點。
6. **引導建議**：一個工作流只做一件事；引導時把要確認的地方、條件、偏好說出來（這些會變成「使用者的要求」）；會變的值用真實值引導；只有一句話的做法用 `modify_memory` 記住就好。

### 2.11 2026-09-27：對照前沿 harness 的修改與兩種上下文模式

起因是一次對照 Claude Code、Manus 與 Anthropic〈Effective context engineering for AI agents〉的檢討，列出幾個「不是規模不同能解釋」的問題（程式怎麼組織見〈架構說明〉1.1、3.4～3.6、6、12 節）。

- **長期記憶不再無聲截斷，也有「會過期」的概念**：見 2.7。評測 `memory_stale_state`（記憶裡有「系統整體健康」、問現在健不健康）harness 模式原本 0/3：模型去翻存檔、找不到就反問——「問現在的狀態就重新執行工具」只寫在檢索清單裡，沒有舊存檔時清單不出現，這句也跟著不見。移到 `prompts/context_modes/harness.md` 第 0 條（一直都在）、記憶說明也點名要執行哪類技能之後 3/3。
- **壓縮時使用者原話由程式保留、被壓掉的對話也存檔**：摘要目標 1500 字；使用者原話逐字保留在「使用者說過的話」一節（`USER_WORDS_MAX_CHARS`）；被壓掉的片段存成 `#編號`、可 `result_recall`（2.5）。這是 Claude Code 壓縮時「摘要裡列出使用者每一則訊息、並附完整對話紀錄路徑」的做法，也就是工具回傳那套可還原壓縮用在對話本身。
- **prompt 排列顧 KV cache**：system prompt 只放不常變的；Current Agent State、Objective、已核准的計畫移到每次接在最後一則訊息後面的動態區（不寫進歷史）。檢索清單留在 system prompt：一千多 tokens 放在每次都要重算的尾端不划算，而它只在跑完獨立 session 時才多一筆（同一個模型時那一刻 cache 本來就被洗掉）；動態區只加一行最新一筆（對話一長，system prompt 尾端落在上下文中間，模型容易忽略）。`logs/perf.jsonl` 記每次呼叫的 `prompt_eval_duration`（`prompt_eval_count` 在 cache 命中時仍是完整長度，看不出命中），`evals/chat/perf_report.py` 分組比較。實測（RTX 5090、Ollama 0.34.4、e4b）：沒變時每 1000 tokens 7.3～7.5 毫秒，system prompt 變了 37～50 毫秒——cache 失效約慢 5～7 倍，這台一次約多 0.3 秒，較慢的設備等比例放大；claude_code 模式沒有獨立 session 洗 cache，檢索清單每多一筆造成的 system prompt 變動（評測裡 22 次）成了主要的失效來源（7.6）。
- **會改變實體狀態的動作，執行前由程式確認**（`guard.py`）：以前 manual／hybrid 問的是「要不要把結果加入上下文」，工具早就執行完了；「派工單前先問」只是 `Memory.md` 的一條記憶。現在跟 Plan 模式同一個原則：由程式路徑保證，`run_tool` 沒有 `approved=True` 就不執行被擋的技能，auto 模式也一樣會停。各技能的查詢用法放行（`docker_runcmd` 的唯讀指令、`--dry-run`…），判斷不了的一律問；參數一律照腳本自己的解析判斷（`_guard_parse`，2.16）。
- **評測**（`evals/chat/`）：真模型、假的外部工具、每次在臨時副本裡跑，同一組情境跑兩種上下文模式（`evals/README.md`）。

**兩種上下文模式**：`/context_mode harness|claude_code`，差別與實作見〈架構說明〉1.1、3.4。最終評測（當時 14 個情境 ×3）：harness 42/42、claude_code 28/42。claude_code 沒過的是大量回傳要找的東西落在被截掉的中段（`fleet_battery`、`fleet_followup`、`followup_in_context` 各 0/3）、比較兩份舊存檔 1/3，以及後來拿掉的 `plan_multistep` 0/3：回傳被截成頭尾（`RAW_RESULT_MAX_TOKENS`＝3000）時，e4b 只看頭尾就回答「資料裡沒有 tb6」，不會回存檔查——截斷提示寫明「中間第 94～217 行省略，看不到不代表不存在，先查存檔再回答」也一樣；上限調到 6000（整份放得下）時前三個 9/9。4B 模型讀得懂原文，缺的是「知道自己沒看到」並主動去查的能力：Claude Code 靠的是被訓練成會查的強模型，小模型換成 harness 替它找比較可靠。claude_code 模式留著當對照組與實驗場（限制 19）。harness 的 42/42 偏樂觀：這些情境同時被拿來找問題、修問題，要持續把真實對話裡遇到的問題加成新的情境。

### 2.15 數據分析：只做事實報告，全部由程式做（2026-10-14 起；2026-10-23 改成全部由程式做）

**目標**（2026-10-16 跟使用者討論後定的）：只要有 .mcap 就能用、穩定度非常高的事實報告——量到什麼、什麼時候、Log 說了什麼；不判斷原因。
原因要對照源碼另外分析：「系統的反應照不照設計」「為什麼一直維持」只有 MCAP 回答不了。2026-10-23 起報告全部由程式產生，模型在主對話
依報告回答、討論（〈九〉）；更長的時間跨度是程式切段量測、跨段整合（待辦 1）。程式怎麼跑、報告長什麼樣見〈架構說明〉第 13 節。
第一～九輪（2026-10-14～16）的源碼脈絡、觀測角度、因果推論與根因的評分在 `doc/archive/root_cause_reference/`（那時的程式在 git 的 62e0534）。

**為什麼不判斷原因**（第八、九輪的數據）：事實層已經穩——第九輪 140 次分析，報告裡 3084 個時間全部對得上數據；錯誤與補丁集中在「為什麼」——
第八輪 110 次分析，交回修正的 27 次在因果推論那一步、扣分的 11 個錯誤全部在因果推論，核對因果只能一條條加片語規則，越補越多。rosbag2 也沒有
記錄誰發布、誰訂閱，只有 MCAP 時不知道 Topic 之間的上下游。MCAP 裡每一則 Log 都帶 file、function、line（例如 `system_health_monitor_node.cpp:165 logEvent`），
報告照列，之後做根因或改 code 從這裡接。

**一、數據技能（`_ros2_data_common.py` 與五支腳本）**
- **送進容器的方法**：腳本連同共用模組打包成 tar.gz＋base64，經 `docker exec -i` 的 stdin 送進容器的暫存目錄，執行完刪掉（`run_in_container`；
  以前放在 `bash -c` 的參數裡，單一參數有 128 KB 的上限）。主機不需要 ROS 2。
- **自訂訊息型別**：環境跟其他 ROS 2 技能同一套（`_docker_common.ros2_env_prefix`）：/opt/ros → ROS2_workspace_env 確認過的 Workspace（屬於這個容器時；
  沒有才找 `/workspace/install`、`/workspace/*/install` 這類常見位置）→ 執行中節點的 ROS_DOMAIN_ID。讀不到的 Topic 標成無法解碼，說明要先確認 Workspace。
- **路徑**：主機路徑依容器的 bind mount 換成容器路徑（`/home/david/ros2-web-app/app/…` ＝ `/workspace/app/…`），實驗名稱與 `latest` 相對於數據根目錄
  （沒設定時在容器的 /workspace 底下 4 層內找 `experiment_logs`）。成功操作的數據在輸出末行印 `[ANALYSIS_DATA]`，之後的技能可以省略路徑（2.4）。
  給的路徑在主機上存在、卻不是錄製數據時，主機端先回 [ERROR] 並指到 `search_text`／`view_file`（`not_recording`，2.16）。
- **Key 的類別**（`describe_keys`，每個 Topic 抽樣 120 筆判斷）：數值、向量（2～4 個浮點分量的訊息或固定長度陣列）、矩陣（covariance）、陣列、
  狀態（uint8／bool／octet、相異值少的字串、短的整數或字串序列＝集合）、鍵值（KeyValue）、文字、時間。toolkit 用子字串 `int` 判斷整數型別，
  `builtin_interfaces/Time` 也會中而被當成狀態跳轉；`sequence<…/ActionParam>` 被當成 scalar——都改成依 ROS 型別字串解析。
  **字串分兩種**：很多字串其實是列舉（`mode`＝PROTECTIVE_STOP／NORMAL、`primary_reaction`＝INIT／NONE），它們的跳轉正是要看的；所以相異值 ≤8
  （或 ≤12 而且都很短）的字串當「狀態」，其餘是「文字」（只量訊息流）；內容是 JSON 物件的字串展開成 Key（2.16）。DiagnosticArray 這種「有 name 欄位的
  訊息序列」依名稱展開（`status.level` 每個 status 一項），只列有變化的。空的序列要看宣告的型別：訊息的序列是「沒有項目」，基本型別的序列
  （`stop_reasons=[]`）是「空集合」這個狀態值（第一版把 28 個空的 values 當成假項目）。分類規則改了就把 `INDEX_VERSION` 加一，舊的快取自動重建。
- **Log 的來源**：預設用 bag 裡的 /rosout（時間＝MCAP log_time，跟其他 Topic 同一個時鐘；範例數據 bag 裡 31 則、rosout.log 只有 11 則——
  `ros2 topic echo` 比錄製晚開始），沒有才用 rosout.log；只差在數字的訊息算同一句；rosbag2 自己的 Log（Subscribed to topic…，範例裡 31 則佔 22 則）
  預設不列。編號 L# 在篩選之前編好，mcap_slicer --signal 與 analysis_run 用同一套。
- **寬鬆的寫法**（實測驅動）：e4b 把時間窗寫成 `0.00s_30.54s`、`0.00,30.54`、`+0.00s,+30.54s`（當時的 worker，四次量測白費），主對話也會加不存在的
  `--measure max`。現在時間接受 `+秒`、尾巴的 `s`、`～`／`~`／`_`／`to` 分隔，小於 10 億的數字當距離數據開頭的秒數（不可能是 epoch）；主機端不認識的
  參數照認得的做完、輸出最後說明忽略了什麼（都是唯讀工具，比回錯誤讓模型重送一次省一輪）。

**二、事實那一層（`analysis_job.py`；2026-10-22 第十一輪起程式量全部，2026-10-23 起重點也由程式寫）**
- **同步的偽技能，不是背景服務**：只讀不改、約 2 秒、不需要核准，所以照 ops_run 的做法在主對話的回合裡同步執行；進度經 `progress_callback`
  推到 Web 右欄，產物寫在 job 資料夾（`logs/analysis_jobs/<編號>/`）給面板讀。
- **一次分析整段數據，最多 3 分鐘**（`ANALYSIS_MAX_SECONDS`，以整秒算：錄 3 分鐘常是 180.05 秒）。第九輪以前用 Log 訊號前後 5 秒的時間窗，事實要靠
  模型挑對 Log（漏挑時，時間窗外的變化根本量不到）；量整段之後，「沒有描述」就是「沒有變化」。更長的數據先用 mcap_slicer 切。
- **事實由程式量全部**：`mcap_analyzer --facts` 一次讀完整份數據，**每個可以解碼的 Topic 量全部的 Key**（數值、向量、狀態、鍵值、陣列；header 與
  共變異數除外）與訊息流，快取在 bag 資料夾的 `topic_facts.json`；`build_facts` 整理成有編號的事實：T#＝Topic（類別、發布、變化、到最後的值、沒有變化的
  項目）、E#＝事件（同一則訊息裡一起改變的項目算一個事件，項目全部列）、L#＝Log。時間線、前後 1 秒內的對照、同時發生、前後沒有任何變化的 Log、
  沒有量的 Topic 都從這裡算，同一份數據每次一樣；所有輸出的 +秒 都是距離數據開頭。第十輪以前 Key 由模型挑：同一個 Topic 每次量的 Key 不同，
  沒派到的 Topic 就沒有事實（〈四〉）。
- **發布方式由內容與時間判斷**（`publish_pattern`，取代「10 則以上才判斷中斷」的則數門檻）：一半以上的訊息帶著狀態改變＝狀態改變時才發布
  （隔很久沒有訊息＝狀態沒變）；四分之三以上的間隔在中位數週期的 0.5～1.5 倍＝固定頻率；不到 3 則、其他＝只有一兩則、不定期。**只有固定頻率
  的 Topic 判斷訊息中斷與中途開始／停止發布**；其他的列出每一則的時間，第一則在錄製開始 5 秒之後的列成事件「第一則在中途」。
- **尖峰是「跳出去又回來」**（`find_spikes`，Hampel）：跟前後 9 筆的中位數差超過殘差 MAD 的 6 倍、前後回到原來的水準、而且夠陡（跳進去與跳出來
  都超過前後一步的典型值的 6 倍）。舊版「離均值 2.5σ」在 3 分鐘的感測器數據裡每個 Key 都量得到幾百個；斜坡換成定值（RobotState 的
  sequence.timestamp 歸零）、平滑的山頂（旋轉時四元數的 z）都不是尖峰。只有 ≤4 種值的數值（速度指令）列每次切換，不找尖峰；陣列只量長度與元素平均。
- **對照只看時間，對不上的照實寫**：Log 與 Topic 的事件前後 1 秒內就列在一起（只寫早或晚幾秒），不說誰造成誰；事件沒有 Log 就標
  「沒有對應的 Log」，Log 前後沒有任何事件就標「沒有任何 Topic 的事件」——不硬對齊。
- **重要的時間點是程式給的清單**（`_moments`）：時間線上的事件（狀態改變、開始／停止、中斷、恢復、第一則在中途）與 WARN 以上的 Log，1 秒內的算
  一個時間點（M#）；只由反覆切換的 Topic 組成的時間點不算（計數抖動總是單獨出現；跟別的事件同時變的照算）。重點每個時間點一則（〈九〉）。
- **只有 Log 的錄製照樣出報告**：沒有可以解碼的 Topic、只有 /rosout 時（例如只錄到 bridge 的本地 domain），照樣整理去重後的 Log、WARN 以上的
  時間線與重點；有 Topic 卻一個都解不開才回錯誤（要先確認 Workspace）。第一版一律回「沒有可以分析的 Topic」，產生器的 s3 有 4 份這種錄製。
- **主對話依報告的回答由程式核對**（`turn_guard.analysis_reply_check`）：回答裡有報告沒有的因果動詞（導致、造成、引起、引發、觸發、使得、歸因、根因；
  同一個子句前面有否定或條件的不算），或寫的變化與值跟事實對不上（`agent_core/claims.py`，〈七〉）就提醒一次、畫面附 ⚠️。報告最後一行的回答規則
  本身有這些字，核對時不算（實測第一版就因此漏抓）。
- **設定只存跟預設不同的值**（`save_analysis_settings`）：以前存全部的值，預設改了，存過設定的人仍是舊的預設。設定檔現在只有數據根目錄與
  預設容器；舊版的鍵（各角色的模型、worker 上限、源碼目錄、時間窗…）讀的時候略過。

**四、第十一輪（2026-10-22）：結構化的修正**

使用者的要求：不找補丁（改門檻值這類），盡量用結構化的資訊輸出，讓以後的使用沒有副作用（例如不靠文字的上限），同時保持一定程度的說明。
第十輪（2026-10-17）留下九個問題——worker 上限 4 不夠（沒派到的 Topic 就沒有時間線）、摘要被截斷在半句、整段持續發布被寫成開始與停止、
同一個 Topic 的 Key 每次不同、5 則的狀態 Topic 被算成訊息中斷、存過的設定蓋掉新的預設、主對話的回答沒有核對、補量的檢查從來沒有觸發——
結構上的原因都是「事實要靠模型挑、靠文字的長度、靠則數猜」。修正：程式先量全部 Topic 的全部 Key、發布方式由時間與內容判斷、尖峰改成跳出去
又回來、同一則訊息裡一起改變的項目合成一個事件、設定只存跟預設不同的值、主對話的回答由程式核對（〈二〉）。當時模型（Orchestrator → Workers →
Synthesizer）只「選」和「說明」，說明與重點改成一則一則、有編號的 `{refs, text}`，時間與引用的事件由程式補——這一層 2026-10-23 拿掉（〈九〉）。

**五、大量數據的產生器（`evals/datagen/`，2026-10-22）**

使用者要的：隨機情境的錄製產生器，正確答案由注入的事件自動產生，評分直接套用；數據的類型照目前在開發的六個套件
（amr_base_hw、amr_base_sw、diagnostics_package、fih_rmf_system、VSLAM_package、fih_amr_bridge），因為之後的數據主要是這些。
- **照源碼與文件整理目錄再模擬**：先由六份目錄（Topic、型別、頻率、QoS、每一則 Log 的原文與 file／function／line、狀態機、情境）整理出每個套件
  的行為，再寫成離散事件的模擬：diagnostics 的 MON／GATE 照矩陣與閂鎖反應、底盤 62.5 Hz 的迴圈與 FC17h 失敗時哪些 Topic 停、導航的狀態 Topic

**怎麼做（`agent_core/extract.py`，`summarize_tool_result` 與 `result_recall` 共用）**：
- **程式切段**（`_results_common.chunk_lines`）：依原文的結構切——章節（`## 標題`、以全形冒號結尾的一行）、一筆一筆的紀錄（`--- #序號`、`- `、`▸`、

  每條附行號；問題要找的是一類東西時，這一段裡符合的每一個都要列。段數超過 `EXTRACT_MAX_CHUNKS`（8）時，依問題裡的名稱、數字出現在哪幾段挑著讀，
  沒讀的行號由程式寫進「未涵蓋」——不假裝讀過。worker 同時送出 `EXTRACT_PARALLEL`（2）個（同一個模型只是重疊排隊）。
- **整合**（`prompts/extract/synthesizer.md`）：各段核對過的事實＋那幾行的原文（程式附上，`EXTRACT_EVIDENCE_CHARS` 以內）＋原文的開頭與大綱 →
  回答、相關事實（附行號）、錯誤、未涵蓋、之後可能想知道的、檢索清單的描述、還需要的舊存檔。長度目標是原文的四分之一、介於 400～1500 字
  （以前固定 400 字，十幾台車、幾十個錯誤只寫得下幾條）。
- **程式核對（`missing_tokens`）**：每一條寫的數字與名稱（含底線、斜線、點、冒號的英數字；或字母加數字、原文別處有同樣寫法的，例如 tb6）要在
  它引用的那幾行裡——前後 2 行（不跨到別的紀錄）、縮排的上層（YAML 的名字常在上面幾行）、縮排更深的下層（引用一筆紀錄的開頭時）。寫了行號卻
  對不上＝寫錯對象或數值，不在別的地方幫它找（tb6 的電量寫成 tb7 會被擋）；沒寫行號才在範圍裡找出現那些字的行補上。使用者問題裡的數字（「低於
  40%」）、10 以下的整數、模型寫進句子的行號不核對；一般的詞（ROS2）不核對。總數（「共 N 台」）不管大小都核對：原文要有這個數字，或等於程式
  數的事實條數——實測 26b 列了 7 台卻寫「共有 6 台」。worker 對不上的事實不交給整合；整合對不上的拿掉，回答寫了原文沒有的字就帶著問題請它修
  一次，還是不行就在回答下面標明哪幾個字找不到。整合失敗（回覆不是 JSON）時程式把各段的事實排成清單，不丟掉 worker 的結果；模型完全沒有回應時
  照實說「提煉失敗」，下一步建議不會再寫成「已經回答」。
- **存檔**（`agent_core/jobstore.py`，數據分析也改用同一套）：每一次提煉一個資料夾 `logs/extract_jobs/<編號>/`——`job.json`（切段、每段的結果、
  拿掉的事實與原因、整合、修正、最後的重點）、`calls.jsonl`（每次模型呼叫的 system／user prompt 與原文回覆、耗時）、`events.jsonl`（進度；
  Web 右欄的「⏳ 執行進度」看得到，開頭是 📑）。只留最近 `EXTRACT_JOBS_KEEP`（500）次。`perf.jsonl` 的分類多了 `tool_summary_worker`、
  `tool_summary_synth`、`tool_summary_repair`（recall 同理），並記 job 與第幾段。
- **自動追問拿掉了**：全文都讀了，缺口就是原文沒有（或那幾段沒讀到，「未涵蓋」會寫行號）；要細節時 main session 用更具體的問題
  `result_recall`（會依新的問題重新挑段落）或 `result_view` 看那幾行。`TOOL_SUMMARY_INPUT_MAX_CHARS`、`TOOL_SUMMARY_MAX_FOLLOWUP_HOPS`、
  `GREP_NO_HIT_RE` 一起拿掉。

**行號統一成原文的行號**：以前 `result_view`／`result_grep` 用的是存檔檔案的行號（含 13 行檔頭），claude_code 模式的截斷說明寫的卻是原文的行號，
照它給的 `result_view --from` 會差 13 行。現在一律是原文的行號（工具輸出的第 1 行＝行 1），寫成 `120→內容`（不用 L120：數據分析的報告裡
L# 是 Log 訊號）。提煉結果每條事實附「（行 40-42）」，好幾份時「（#12 行 40）」；下一步建議附 `result_view <編號> --from <行號>`。
`result_view --outline` 列出原文的章節與行號；claude_code 模式截斷時也寫明中間有哪幾節（`_results_common.outline`）。

**`result_recall` 與存檔回查的其他修正**：好幾份一起讀時，每一份各自切段、同一個整合看全部（以前把 16000 字的額度平均分給每一份）；找不到存檔時
分清楚是編號抄錯（說目前最大的編號）、還是超過保留上限被清掉（以前一律說被清掉）、還是參數順序錯；檢索清單不再列原始檔已經被清掉的那幾筆（清單
檔本身照樣只 append），也只讀檔案最後 256 KB；刪舊存檔照（session、編號）排（檔名的文字排序在同一個 session 裡 #1000 排在 #999 前面）；寫
`index.md`、`tools_use_index.md` 上鎖（背景壓縮與主對話會同時寫）；新編號接在存檔目錄裡最大的編號後面（CLI 與 Web 同時開著時不會配到同一個）；
`result_recall` 在本程序裡解析編號時用目前的 session（以前環境變數只有腳本拿得到）。Web 上 recall 的回傳不再顯示兩張一樣的卡片。

**dispatch 的兩個修正**：狀態標記只認輸出最後連續的那幾行（容器的 log、指令的輸出裡剛好有 `[TARGET_CONTAINER] x` 不會改掉目標容器）；工作目錄
不能用（被刪掉、切到沒有權限的目錄）時換回專案目錄並回 `[ERROR]`——以前切到 `/root` 之後每一支腳本都失敗、錯誤還沒有 `[ERROR]` 開頭，只能重開
程式。腳本不讀標準輸入（`stdin=DEVNULL`）、輸出用 `errors="replace"` 解碼；未預期的例外一律 `[ERROR]` 開頭並附下一步。

**數據技能互相借用**（使用者提的：「MCAP 的數據解析已經有量測每個欄位的功能，TOPIC ECHO 是否也要使用」）：
- **ROS2_topic_echo 用跟 mcap_feature_measure 一樣的量測**：以前在主機解析 `ros2 topic echo` 的 YAML，欄位只有 min→max 與幾種值；而 harness 的
  Python 環境沒有 PyYAML，`--duration` 的欄位統計其實整個不見、還回 `[PASS]`。現在在目標容器內用 rclpy 直接訂閱（`run_in_container`，跟數據技能
  同一套環境：/opt/ros、Workspace overlay、執行中節點的 ROS_DOMAIN_ID），型別從 ROS 圖查、QoS 依 publisher 配（全部 TRANSIENT_LOCAL 才用
  TRANSIENT_LOCAL，拿得到只在狀態改變時才發布的最後一則）；Key 目錄、量測、輸出都是 `_ros2_data_common` 那一套：發布方式與中斷、狀態跳轉的時間
  與前後的值與占比、數值的極值（與時間）／平均／斜率／尖峰、依名稱展開的項目（DiagnosticArray 的 `status.level[motor_left]`）、字串裡的 JSON。
  前 60 則判斷 Key 的類別，之後每一則直接取值、不留整則訊息（高頻、大的訊息也不會吃光記憶體）；原始訊息只留前後幾則（`--raw`）。單筆模式也改用
  rclpy，字串不截斷（以前 CLI 把 JSON 狀態截在 128 字）。實測：單筆約 1 秒；10 Hz 的 JSON 狀態 15 秒測到 IDLE→RUNNING→IDLE 的時間與占比、錯誤
  清單的增減（+E_LOW）、電量的趨勢，`--where data.mode==RUNNING` 第一筆符合 #35 +3.45s、符合 7.0 秒；topic 名稱打錯時列出相近的。
- **字串裡的 JSON 展開成 Key**（從 ROS2_topic_echo 借來）：以前數據技能把整個字串當「文字」，只量訊息流；amr_base_sw 的 `/robot_state`、
  `/amr_diagnostics`、`/current_station` 都是 JSON 字串，裡面的狀態變了也看不到。現在抽樣的字串八成以上是 JSON 物件就展開欄位（`data.status`、
  `data.robots.battery` 依 name 展開成對照表、key-value 清單是鍵值、空的清單變成集合狀態），量測、事實、報告都一樣處理（索引與事實的版本各加一，
  舊的快取自動重建）。產生器 s1 有 22 個 Topic 多了 JSON 欄位的變化，例如 `/robot_state` 的 `data.sequence.state：standby → running（+3.17s）
  → fail（+42.07s）`——任務失敗以前完全看不到。
- **`--where` 變成共用的量測**（從 ROS2_topic_echo 借來）：`condition_features`／`where_on_series`——幾筆符合、第一筆符合的時間與值、它的前一筆、
  符合的時段與總共幾秒；`==` 可以比文字與 true／false（以前 `data==true` 跟 Python 的 `True` 比，永遠 0 筆）、陣列任一個元素符合就算、數字的
  字串也比得了。`mcap_feature_measure` 也有 `--where`（可以不寫 `--key`，條件用到的 Key 自動量；欄位不存在回 [ERROR] 列出相近的 Key）。
- **容器的 log 也能去重**：`parse_log_lines` 認得 ROS 的格式加上 docker logs -t 的時間、ros2 launch 的程序名稱、顏色碼，Python traceback 合成一則
  ERROR（訊息是例外那一行）；`dedup_events` 跟 rosout_parser 同一套。（`docker_ctl logs` 用它，見下面的技能整理。）
- 第十一、十二輪 analysis worker 用的時間窗環境變數（`ANALYSIS_WINDOWS`／`ANALYSIS_TOPIC`、`W1` 編號、讀切片）從數據技能拿掉；`mcap_analyzer`
  的輸出不再寫「worker 可分析」。

### 2.18 2026-10-23：工作流（架構整合的第 3 階段）

維運裡有一類事會一再發生、做法固定（工作包卡住的處理、照手冊改設定、派工作包並確認跑完、重啟容器並確認、改派）。之前不是主對話
一個技能一個技能做，就是交給 ops_run 每次重新規劃；「做完了沒」也是模型說的。工作流把做法寫成規格，**步驟由程式照文本推進，模型只在
判斷點出手**（寫法見〈[工作流撰寫規範](工作流撰寫規範.md)〉，程式見〈架構說明〉第 14 節）。

**設計**

- **規格**：`skills_system/workflows/<名稱>.md`，跟技能同一套 OKF（`type: Workflow`）；四種步驟——【執行】（一行一個 `EXECUTE:`，可加
  「檢查：輸出有「A」或「B」」）、【檢查】（分支「…」→ 第 N 步／結束；其他 → …）、【確認】（停下來等使用者）、【告知】（列進報告）。
  程式驗證：連號、腳本存在、分支只能往後（沒有迴圈）、「看第 N 步」只能看前面的【執行】、`dependencies` 與 `changes_state` 跟步驟一致。
- **判斷點只有兩種**：命令用到「需要的資訊」以外的 `{名稱}` 時，模型只填那幾個值（schema 只有那幾個名稱；前面填過的同名值沿用）；
  分支程式比對不出來、又沒有「其他」時，模型選一個。技能回 `[ERROR]`、而且值是模型填的，帶著錯誤改一次；其他失敗就停在那一步。
- **「做完了沒」由程式判斷**：每一步的檢查、最後的成功判準（`第 N 步的輸出有「X」`、唯讀命令的輸出）都是程式比對；狀態
  done／unverified／ended／failed／paused／cancelled。存檔：`logs/workflow_jobs/<編號>/`（job.json、判斷點的 calls.jsonl、events.jsonl），
  每一步的輸出照常存成 #編號。
- **確認**：開始時列出到第一個【確認】之前會改變狀態的步驟（值代進去、選填沒給會略過的不列），核准一次；【確認】停下來，
  `--continue` 時再確認一次那一段。
- **主對話怎麼用**：SKILLS.md〈工作流〉一節列每一個的呼叫語法；AGENT.md 一條規則（有對應的就用 `workflow_run`，不要自己一步一步做、
  也不要 ops_run；只查原因、「先不要修改」時不用）。報告以 `WORKFLOW_REPORT_HEADS` 開頭，跟數據分析的報告一樣不再提煉。
  ops_run 的計畫先不放 workflow_run（兩層確認、確認畫面看不到工作流的步驟），第 4 階段的任務引擎再合起來。
- **`/make_skill` 產生的是工作流**：草稿排成同一格式、交給同一套驗證（往回跳、腳本不存在都擋下註冊），前面步驟的輸出才知道的值交給判斷點。
- **5 個工作流**（從維運評測的複雜情境來）：`stuck_package_fix`、`config_edit`、`dispatch_and_confirm`、`container_restart_verify`、`reassign_package`。
- **使用者直接指定**：`/workflow`（CLI 與 Web 共用 `agent_core/workflow_cmd.py`；列出、看步驟、直接執行——不經過模型選擇，確認關卡照常，
  報告進主對話後 AI 依報告回答）；不用互動的入口 `python3 Agent_Runner.py --workflow <名稱> 名稱=值 … [--yes]`——之後「心跳定期跑固定的
  工作流」直接呼叫的入口（待辦 11）：沒有人在旁邊確認，會改變狀態的沒給 `--yes` 不執行；結束碼 0 完成／提早結束、1 沒有完成、2 停在
  【確認】、3 要核准、4 沒有執行。工作流的沙盒測試走的就是這個入口，每個階段的 phase_check 都會驗證。

## 6. 已知限制

1. **小型本地模型的工具呼叫可靠度**：`gemma4:e4b` 偶爾會不下 `action`、直接「腦補」一份假的執行結果，或在未設目標容器且多個容器在跑時自行挑第一個。Plan 模式的確認關卡與 JSON 協議的「只看 action」消除了誤觸發，但擋不住模型自己編造結果；規格文件只能用文字要求「多個容器時請使用者指定」。
2. **`stt_engine` 的麥克風模式要有人在旁邊**：2026-10-23 起可以 `--file` 轉音檔（不需要人）；麥克風模式在 WSL 用 ffmpeg.exe、Linux 用 arecord，沒有實測（這台機器沒有裝 faster-whisper，測試用假的套件）。
3. **CLI 與 Web Console 不完全對等**：CLI 的 `objective set` 是多行輸入，Web 簡化成單行 `/objective set <內容>`；CLI 沒有 Auto 模式的輪數上限（有人在終端機前可 Ctrl+C）。
4. **測試還沒有整理成 pytest 的 `tests/`**：每一組有不用模型的自我測試（假的 `ollama.chat` 或直接執行腳本），`evals/phase_check.py` 一次跑全部、跟基準逐項比（2.17、5.4）。主對話的評測情境 14 個（另有 5 個穩健性情境）、外部世界是假資料，通過不代表真實現場一定沒問題；情境本身的問法也會影響結果（例如「讀一下 /fleet_states_json」會被當成檔案路徑）。
5. **使用者輸入與工具回傳的 token 數是估算值**：只有 AI 回覆與整體上下文精確；夾雜大量程式碼或 URL 的內容誤差較大。`count_tokens()` 保留對 `ollama.tokenize()` 的偵測，日後套件提供時自動改用。
6. **背景壓縮是否真的平行取決於 Ollama 的 slot**：多模態模型目前被強制單 slot，同模型的背景摘要會讓下一次對話排隊；要平行需 `AGENT_SUMMARY_MODEL` 指定另一個模型。API 查不到 slot 數，程式無法自動判斷。
7. **融合摘要的長度只能靠 prompt 約束**：實測會超過目標約三成；`SUMMARY_MAX_PREDICT` 只是防失控的硬上限。
<!-- -->
9. **`/make_skill` 的草稿品質受模型限制**：步驟怎麼切、【檢查】的分支條件寫得對不對、哪些值是使用者要給的、哪些交給判斷點，都是草擬模型從對話推論的；程式只保證引用的腳本存在、分支只往後、`changes_state` 跟步驟一致（2.10、2.18），語意上的錯誤（例如 e4b 的檢查步驟指錯步驟、把讀錯的欄位名稱寫進指令）靠使用者看預覽、用修改意見糾正。建議 `AGENT_SKILL_MODEL=gemma4:26b`。對話紀錄只存在這次啟動的記憶體裡，程式重新啟動之後就不能再用之前的對話做技能。
10. **JSON 協議下的空白回覆**：模型在字串裡用英文雙引號時會發生，屬機率性；框架自動重試一次並在提示詞禁用英文雙引號，重試仍空白時如實顯示。
11. **工具回傳的提煉受提煉模型與段數限制**：擷取得對不對取決於 `SUMMARY_MODEL`（預設同主模型）；名稱與數值由程式核對引用的行（2.16），但核對是字面的——不懂單位換算、不核對中文名稱、10 以下的整數不核對；需要比較或計數的問題仍要靠腳本選項先算好（2.5「數值交給腳本算」）。原文超過 8 段（約 6.4 萬字）時只讀依問題挑到的段落，沒讀的行號寫在「未涵蓋」；長的輸出多花「段數＋1」次模型呼叫，同一個模型時一個一個排隊（worker 同時送出 `EXTRACT_PARALLEL`＝2 個也只是重疊排隊），也跟主對話序列執行（實測 120 台車 2.2 萬字：26b 18 秒、e4b 12 秒），觀察型技能幾乎每次都會觸發。
12. **`result_grep` 是文字比對**：關鍵字要在原文裡出現才搜得到（同義詞靠 `a|b` 自己列），語意相近但字面不同的東西找不到；命中以行為單位，結構化內容用 `--block` 或 `result_view` 補整段。存檔依 200 檔／50 MB 輪替，太舊的會被刪。
13. **小模型會把「載入規格」當成「已執行」**：用 `docker_open <容器>`、`change_dir <路徑>` 這種帶參數的技能名稱載完規格後，直接當作容器已切換、目錄已切換而做下一步。規格載入的回傳現在會點名「你附的參數沒有被執行、狀態沒有改變」，18 情境實測後不再發生，但這是措辭層面的緩解，不是機制保證。
14. **同一 session 已載入某技能規格時，模型傾向重用它**：例如已載入 `list_dir` 後被問「專案裡檔名含 cmd 的檔案有幾個」，會用 `list_dir --filter` 在根目錄數（只看一層、得到 0），而不是再載 `find_file` 遞迴搜尋。索引描述標明「一層／遞迴」也沒用；改成腳本在 0 項時直接指示「如果問的是整個專案，這個 0 不能當答案，請改用 find_file 遞迴搜尋」之後實測會照做——腳本回傳裡的明確指示比索引描述有效。
15. **「您提供的」殘留**：工具結果的開頭與結尾都有框架句，18 情境仍偶爾（1～2 次）出現「根據您提供的…」；兩件事一起問時偶爾只答後一件。
16. **調度系統技能依賴 web_console 的版本**：`semantic_map` 需要 `/api/topology` 端點，舊版 web_console 會回 404；OverPending 的時序常數（`threshold_ovp_sec`、`threshold_recovery_sec`）以 distribute 的設定為準，規格裡的「約 10 秒」是預設值。
17. **`result_recall` 的理解品質仍受提煉模型限制**（2026-10-23 起沒有自動追問：全文都讀，缺口就是原文沒有或那幾段沒讀到）：answer／facts 的正確性取決於 `SUMMARY_MODEL`，事實的名稱與數值由程式核對，但「哪些跟問題有關」仍是模型判斷；需要比較或計數時一樣要看原始輸出裡腳本算好的數字（總數由程式核對：原文沒有、也不等於列出的條數就退回）。
18. **工具使用檢索清單的「有沒有關」判斷靠小模型自行拿捏**：`index_hint` 由提煉模型寫（約 60 字，不截斷），措辭有沒有區分度直接影響之後認不認得出來；清單只給線索不給內容，誤判「有關」時多一次 `result_recall`（多一次模型呼叫，不會答錯），誤判「無關」時使用者得自己再問一次。第一版清單列檔名、四個 `result_*` 技能的描述又很像，模型跑去 `result_list` 兩次再 `result_grep`，沒走到提煉；現在清單直接給 `result_recall` 的語法，其他三個寫明「清單沒有相關項目時才用」。主對話評測有跨 session 取回、無關的問題、比較兩份舊存檔的情境（2.11），但比對本身（例如「tools 裡的技能在 scripts 都有對應腳本嗎」）的品質仍受提煉模型限制，要精確就讓腳本算（2.5「數值交給腳本算」）。

19. **claude_code 模式下，4B 模型不會回存檔查被截掉的中段**：評測中要找的東西落在省略的中段時 0/3，就算截斷提示寫明行號與「看不到不代表不存在」也一樣（2.11）；`AGENT_RAW_RESULT_MAX_TOKENS` 調到常見輸出放得下時才可靠，代價是上下文漲得快。這個模式目前定位是對照組與實驗場。
20. **執行前關卡的唯讀判斷是白名單啟發式**：看不懂的指令一律要確認（寧可多問），所以容器內較複雜的唯讀指令（`awk`、`sed`、`python3 -c`…）也會跳確認；反過來，白名單裡的指令若有沒想到的寫入方式，就會被放行。指令含 `{…}`（看不出實際的指令）時一律要確認。`/guard off` 只影響目前 session。
21. **動態區每次呼叫都要重算**：Current Agent State、已核准的計畫、檢索清單最新一筆通常幾百 tokens，放在最後面換來 cache 穩定，但它本身每次都不在 cache 裡。
22. **使用者原話的保留有上限**：`USER_WORDS_MAX_CHARS`（2000 字）以內逐字保留，超過丟最舊的並註明則數；丟掉的原話仍在對話片段存檔裡，但要靠模型想到去 recall。

31. **主對話的兩個把關是啟發式的**：「同樣的動作得到同樣的結果」在等待狀態改變時（例如反覆查一個還在跑的工作）也會在第四次停下——這是刻意的（不要空轉），要繼續就再說一次。評測（2026-10-08 的 E6、E7，見 2.12）顯示把關主要省下模型呼叫，沒有提高成功率。「宣稱做完」用字面比對（「已重新啟動」「已建立」…），沒列到的說法抓不到，每個回合最多提醒一次；2026-10-16 起只認子句開頭或「我／我們」後面的說法（見限制 77）。

    `analysis_reply_check`，提醒一次；執行報告的那一回合核對整個回答，之後的回合核對寫到報告的那幾行——沒有寫到報告的編號、Topic、+秒的那幾行
    不核對）。換句話說的推測（例如「似乎」）、換句話說的因果（「…之後就跟著…」）、中文主詞的說法（「安全閘恢復正常」）抓不到，提醒之後模型仍可能照寫。
47. **Key 的類別是抽樣判斷的**：每個 Topic 抽 120 筆；只在錄製後段才出現的列舉值、只偶爾有值的序列可能判斷錯（量測時仍依實際的值算）。
<!-- -->
49. **Log 與數據的時鐘**：rosout.log 的 stamp 跟 MCAP log_time 假設是同一台機器的時鐘（toolkit 也這樣假設）；用 sim time 或跨機器錄製時，
    時間點會落在數據範圍外——切片會回錯誤、事實報告裡 Log 與 Topic 的對照也會錯開。bag 裡有 /rosout 時預設用它（時間就是 log_time），沒有這個問題。
50. **`--all` 錄不到中途才出現的 Topic 的第一則**：rosbag2 的 `-a` 要先發現 publisher 才訂閱（實測 /cmd_vel_raw 少了第一則、比 gate 的反應晚 0.1 秒）；要完整錄到請用 `--topics` 明確列出。
<!-- -->
52. **回歸評分只評事實**（`evals/analysis/regression.py`）：時間線該有的事件用「時間 ± 容許誤差＋關鍵字」比對，Topic 的類別看該有、不該有的，
    用詞用詞表與每份數據的禁用說法，重點寫的時間對照報告裡程式整理的事實，重點涵蓋看標成 key 的事件有沒有一則重點引用它；全部由程式判，
    不需要人工標註。2026-10-23 起報告全部由程式產生，用詞、時間有根據、重點涵蓋檢查的是程式本身（每個時間點都有一則，涵蓋一定滿分）；
    主對話依報告的回答不在回歸評分裡（`evals/chat/` 的路由情境、Web 端到端看）。
<!-- -->
54. **8 GB 顯卡上換大一點的模型要調上下文**：deepseek-r1:8b 用預設的 32k 上下文時 KV cache 約 4.8 GB，四成跑到 CPU（10.6 token/s）；上下文設 12288
    後 7.2 GB 中 6.3 GB 在 GPU（26.7 token/s）。用 `AGENT_NUM_CTX` 調。同一台 8 GB 筆電（RTX 5060 Laptop，2026-10-14）：e4b 可以跑；gemma4:26b 放不下
    （18.7 GB，大部分在 CPU），要在顯示記憶體 ≥24 GB 的機器上用。
<!-- -->
77. **主對話的「沒有執行卻宣稱做完」只認子句開頭或「我／我們」後面的說法**（`doc/archive/root_cause_reference/設計筆記_第1到9輪.md` 的 2.24 驗證第 5 點）：「已重新啟動 amcl」「我已經建立了」照樣提醒；
    前面有主詞的「nav2 已重新啟動」不再提醒（以前會，但同一條規則也把「指令已停止發布」這種描述數據的句子當成宣稱）。
78. **一次最多分析 3 分鐘（180 秒，以整秒算）**：程式量整段數據；更長的先用 mcap_slicer 切成 3 分鐘以內的片段（之後要分析更長的
    時間跨度，是程式切段量測、跨段整合，還沒做，待辦 1）。事實裡每個項目的跳轉、切換列前 30 次與最後 10 次
    （次數是總數）、尖峰列 10 個、中斷列 20 次；時間線上同一個 Topic 反覆切換的事件只列前 5 個與最後 2 個（各 Topic 的結果寫總次數）。
79. **時間上的對照只看時間**（前後 1 秒、同時＝0.1 秒內）：對到不代表有關，對不到也不代表無關（例如逾時判斷的 Log 在停止發布 0.5 秒後）；
    出現超過 3 次的 Log 只拿第一次與最後一次對照；同一時間的事件很多時，「前後 1 秒內」那一欄很長。
<!-- -->
81. **類別與發布方式是程式依量測結果判斷的**：尖峰是單獨幾筆跳出去又回來（跟前後 9 筆的中位數差超過殘差 MAD 的 6 倍、回到原來的水準、
    而且夠陡）：雜訊大的訊號不會被列成尖峰，但比雜訊小的真尖峰量不到；只有 4 種以下的值的數值列每次切換、不找尖峰。發布方式由時間與
    內容判斷：多個節點發布同一個 Topic、事件觸發的 Topic 是「不定期」，不判斷中斷與開始／停止（真的停了也不會標成中斷，只能從每一則的
    時間看）；固定頻率的週期是整段的中位數，頻率中途改變（例如 10 Hz 變 5 Hz、沒有超過週期 3 倍的間隔）不會被列成事件。
82. **JSON 字串的 Topic**（2026-10-23 起內容也量了，2.16）：抽樣的字串八成以上是 JSON 物件才展開；混著好幾種格式的字串、JSON 裡的自由文字（很多種值的長字串）照樣只是「文字」，不量內容。
83. **隨機情境產生器是模擬**（`evals/datagen/`）：感測器的數值是合成的、影像是全黑的小圖，RMF 的對外 domain 與機器人的本地 domain 放在
    同一份錄製；評分標準照分析程式的定義產生——分析程式的定義（門檻）改了，用 `refresh_truth.py` 重算評分標準（數據不變，不用重寫 bag）。
    實機的數據仍要用這台錄的 14 份與之後的實錄驗證。
84. **時間線的 INFO Log 只列前後 1 秒內有事件的**：WARN 以上的 Log 全部列；前後沒有任何事件的 INFO 不在時間線、也不在重點裡（去重後的完整 Log
    在 log_digest.md，要看用 rosout_parser）。
85. **用詞表是字面的**：主對話回答的因果詞（`turn_guard._CAUSAL_WORDS`）、回歸評分的用詞表（`analysis_job._NOT_FACT_WORDS` 加上每份數據的禁用說法）
    都是字面比對；換句話說的推測（「似乎」「看起來」，不在詞表裡）、換句話說的因果抓不到。
86. **句子意思的核對是字面的**（`agent_core/claims.py`，規則見〈架構說明〉13.3；2026-10-23 起核對的是主對話依報告的回答）：要寫得出主詞——Key 名稱、Topic 名稱、句子裡的 T#，或引用的
    編號——才核對；中文的主詞（「安全閘恢復正常」「狀態層級回到 0」）、部分的說法、疑問與條件句、值後面接中文描述的、核對不了的欄位
    （文字、陣列）不核對。主詞跨子句靠開頭的字判斷（「最後、之後、沒有、以上…」沿用前一個子句），判斷錯了會漏抓或核錯對象；一句寫了好幾個
    Topic 時取前面最近的那個，寫法倒過來（「data=10 是 /target_station 的」）會取錯。值可以寫 .msg 的常數名稱，沒寫在 .msg 裡的對照
    （文件寫的代碼意思）不認得。Log 的則數（「同一時間 4 則 Log」）、數值的範圍不核對。否定的「沒有回到初始」不核對（其實回到了也抓不到）；
    寫明了例外的句子（「…回到開頭的值，但 X 仍是 V」）只核對例外以外的項目，「沒有變化」整句不核對。設計上寧可漏抓、不誤擋：第十二輪實測的誤擋
    都已經改成認得或不核對（`test_data/tools/meaning_review.py` 用來重看被交回的句子）。

## 7. 未來方向

已經記下來、還沒做的事項（架構整合第 4～6 階段等）在〈[待辦清單](待辦清單.md)〉；這一節是比較遠的方向。

### 7.1 讓 AI 自己把檢索範圍縮小

`search_text`／`find_file`／`list_dir` 已是精準檢索的雛形，但大量結果的處理仍是「超過門檻就交給獨立 session 擷取」，擷取只會留下與當前目的相關的部分，撈得越多丟得越多。更根本的做法是在規格文件與 `AGENT.md` 裡要求模型先縮小路徑、關鍵字具體、必要時分批查詢；幾乎零成本，效果依賴模型是否遵守。

### 7.2 自我進化第二階段：需要新程式碼的技能

第一階段（2.10）只用既有腳本組成工作流；需要新程式碼的能力，目前由使用者另外寫好腳本（例如跟 Claude 討論後建立），再產生對應的規格。之後可以讓較大的模型草擬腳本到 `drafts/`，harness 以對話紀錄與軌跡中的實際案例當測試 oracle 反覆執行、餵回錯誤讓它修正，通過且經使用者審核後才註冊；也可在多步驟的任務做完時主動詢問「要做成工作流嗎」。

### 7.3 滾動摘要也回到原始訊息重新抽取

工具回傳這一側的「回到原始輸出」已經做了（2.5 的存檔與 `result_recall`）。被壓掉的對話片段也存成 `#編號`（2.5、2.11），`result_recall`／`result_grep` 都能取回；使用者原話也由程式逐字保留。還沒做的是讓滾動摘要本身「回到原始訊息重新抽取」：現在仍是「上一份摘要 + 新片段 → 新摘要」，細節會逐輪流失，只是原文不再消失。

### 7.4 `Memory.md` 的內化與整併

記憶目前只有 `Memory.md` 一處（2.7）。尚未做的是：定期把條目重新分類（屬於某個技能用法的寫回那份規格，屬於規劃原則的內化進規劃 session 的 prompt），內化後刪除原條目，讓常駐的 `Memory.md` 不會無止盡增長。語料已備好：`logs/summary_*.json` 的 `results_and_errors`／`user_preferences`／`open_items` 欄位可供反思機制定期讀取、提議寫入。

### 7.5 補齊測試與可攜性

把自我測試整理成 pytest 的 `tests/`（現在是各組的 `selftest.py` 與 `phase_check.py`，5.4），並讓 CLI 的模型名稱也能由環境變數覆寫（現在寫在 `agent_core/cli.py`）。評測的情境可以繼續加：每修一個真實對話裡遇到的問題，就把那段對話變成一個情境，之後改 prompt 才知道有沒有退化。

### 7.6 claude_code 模式的下一步

- **會用工具的 subagent**：現在 claude_code 模式能委派的只有 `result_recall`（讀存檔、沒有工具）。Claude Code 的 subagent 是有自己工具迴圈的 agent；這裡可以做一個只准用唯讀技能、最多 N 步、結束只回報結論的子迴圈，讓模型把「大範圍探索」整包委派出去。
- **檢索清單不進 system prompt**：claude_code 模式沒有獨立 session 會洗掉 KV cache，檢索清單每多一筆就讓 system prompt 改變、整段歷史重算，實測是這個模式最主要的 cache 失效來源（2.11）。可以改成新的那幾筆先放動態區、壓縮時才併回 system prompt。
