# 技能撰寫規範（規格文件與腳本）

給寫技能、改技能的人看（主對話的模型看不到這份）。目標：**主對話的 AI 自己就能用每一個技能**——看規格就知道怎麼下參數，出錯時看
`[ERROR]` 的訊息與規格的「異常」就知道要換參數重試、改用別的技能，還是用一句話問使用者；之後常駐的工作（心跳）也照同一套用。

## 1. 規格文件（`skills_system/tools/<名稱>.md`，OKF 格式）

```markdown
---
type: Tool
title: 一句話的標題
description: 什麼時候用（主對話選技能時看這一句）
version: x.y.z
dependencies: ["docker", "ros2"]
---

# 用途      做什麼、跟相近的技能怎麼分（一兩段）
# 語法      `EXECUTE: scripts/<腳本>.py <參數>`，每個參數一行：意思、預設值、上限
# 範例      兩三個，涵蓋常見的用法
# 回傳      [PASS] 的第一行寫什麼、有哪幾節；[ERROR] 的寫法
# 異常      每一種會發生的錯誤 → 下一步（換什麼參數、先用哪個技能查、或問使用者什麼）
```

- 規格要精簡（800 字左右為原則）：每次載入都會進主對話的上下文。
- 參數的預設值、上限、逾時都要寫；腳本裡的數字改了，規格一起改。
- 會改變狀態的技能（建、刪、改、重啟、發布、送出）寫明「會先請使用者確認」，並加進 `agent_core/config.py` 的 `_GUARDED_DEFAULT`
  （`GUARDED_SKILLS` 的預設清單）；同一個技能有唯讀的用法（`docker_ctl status`、`ROS2_param get`）時，
  在 `agent_core/guard.py` 加分支放行那些用法（照腳本自己的參數解析判斷，不另外解析）。
- `SKILLS.md` 的一行描述是給主對話選技能用的：寫「什麼時候用」，不要寫實作。

### 1.1 給程式看的欄位（第一版領域的技能都有）

frontmatter 另外幾行是給程式看的（`parameters`、`receipt`、`narrow`、`listing`），值寫成**一行 JSON**（JSON 也是 YAML，程式不用 PyYAML 就讀得到；
`agent_core/skill_spec.py`）。載入規格給模型看時這幾行會拿掉，模型讀到的跟沒有這幾行時一模一樣，所以不佔上下文、也不用為它重跑真模型評測。

```markdown
parameters: [{"name": "keyword", "required": true, "ask": "要搜的字"}, {"name": "path", "required": false, "default": ".", "fetch": "find_file <目錄名稱>"}]
receipt: {"counts": ["hits", "files"], "items": ["path", "line"], "fields": ["per_file", "pattern", "timed_out"]}
```

- `parameters`：每個參數怎麼取得。必填的參數一定寫 `fetch`（用哪個技能查：`<技能> <參數的寫法>`）或 `ask`（要使用者決定什麼），只寫一個；
  選填的寫 `default`，可以另外寫 `fetch`。名稱用英文（給程式用）。
- `receipt`：腳本收據（下面 2.1）的欄位：`counts` 的鍵、`items` 每一項的鍵、其他欄位（`fields`）；後面加 `?` 的是不一定有的。
  共通的欄位（`status`、`error_kind`、`counts`、`items`、`truncated`、`tool`、`version`、`cwd`）不用列。
  `evals/skills/receipt_test.py` 核對規格跟腳本實際寫的一致（規格沒寫的不能有、沒有 `?` 的一定要有）。
  決策圖從前一個節點的收據帶入參數時，帶的就是 `items` 的鍵（`{"from": 節點, "field": "path"}`；低階執行器檢查欄位真的在這裡）。
- `narrow`（選填）：逾時、還沒有任何結果時，第 1 級可以怎麼縮小範圍再試一次（D5 的低 3）。鍵是腳本 `parse_args` 結果的鍵，值是
  `{"rule": "inside"（路徑換成原本路徑裡面的）或 "added"（清單多加幾項）, "arg": 給模型看的參數名稱}`。低階執行器核對修正只改了這些、
  而且照規則改；沒寫的工具逾時就往上報。例：search_text `{"paths": {"rule": "inside", "arg": "路徑"}, "include": {"rule": "added", "arg": "--include"}}`。
- `listing`（選填，寫 `true`）：輸出是程式整理好的清單——每一行一筆、附路徑或行號，標頭的總數也是程式算的（search_text、py_refs、find_file、
  code_defs、list_dir、result_grep）。這種輸出超過工具回傳門檻、但放得進一段（`EXTRACT_CHUNK_CHARS`）時直接給原文、不提煉——提煉只能從清單挑，
  挑的時候會漏（`agent_core/turn.py` 的 `listing_raw`，照存檔的收據寫的技能認；設計筆記 2.68）。看檔案內容的（view_file、result_view、
  code_ast_reader）與存檔清單（result_list）不寫。`receipt_test.py` 核對寫了的只有這幾個。

寫收據的腳本還要有**純函式 `parse_args(argv)`**：只解析、不執行任何動作，回傳的最後一個值是錯誤的文字（`[ERROR] …`，沒有錯是 None）。
低階執行器執行前用它檢查參數（不花模型呼叫；確認關卡也這樣讀會改狀態的技能的參數）。`receipt_test.py` 檢查每一支都有、
錯的選項會回 `[ERROR]`、`narrow` 的鍵真的在解析的結果裡。

### 1.2 有骨架的技能（`skills_system/<領域>/<名稱>.md`；領域 session 選用、`agent_core/composite.py` 照骨架執行）

一個領域一個資料夾（`skills_system/repo_analysis/`）：`SKILLS.md` 是領域的索引（第一行 `# 名稱：一句話`、接著給領域 session 選領域時看的說明——
做什麼、**不包含**什麼；`## 複合技能` 列 `- [名稱](名稱.md) — 跟規格的 description 一樣的一句話`；`## 工具` 列這個領域能用的單步工具
`- [名稱](../tools/名稱.md)`；`## 做法` 是現在的做法（選了這個領域時列在技能清單裡）；還沒有有骨架的技能的領域 `## 複合技能` 是空的，領域
session 直接用 `## 工具`——凍結的工具登記成的四個領域就是這樣）。有骨架的技能是寫好的做法：要跑哪些工具、怎麼接、出錯時換什麼做法；
骨架只放程式做的步驟（工具節點），**沒有判斷節點**：讀交給提煉，下一步交給領域 session（看了結果再選技能或參數）。格式：

```markdown
---
type: Skill
title: 標題
description: 一句話（跟 SKILLS.md 那一行一樣；領域 session 的技能清單列它）
version: 1.0.0
answers: ["位置", "數量"]
topology: {"depends_on": [], "sub_skills": ["search_text", "code_ast_reader"]}
parameters: [{"name": "name", "type": "name", "required": true, "desc": "要查的名稱", "ask": "要查哪一個？"}, {"name": "path", "type": "path", "default": ".", "desc": "範圍", "fetch": {"tool": "find_file", "args": ["{value}", "."]}}]
---

# 什麼時候用        給領域 session（技能清單列它）：正面寫這個技能做什麼（問題長什麼樣子），跟相近的技能怎麼分；不要寫成「其他都歸我」
# 骨架              一個 ```json 區塊：圖的樣板（給程式；只有工具節點）
# 回退              一個 ```json 區塊：照收據換做法（給程式）
# 策略與 SOP        做法的道理（給人看）
```

- `answers`：這個技能答得了問題要的哪幾種（位置、數量、內容）。
- `topology`：`sub_skills` 是骨架能用的工具（要在領域的〈工具〉裡）；`depends_on`（硬性前置的複合技能）目前的技能用不到，要是空的。
- `parameters`：每個參數 `name`（英文）、`type`、`desc`（給模型看的意思）。必填的不能有預設值（沒寫時程式交回領域 session：還缺這個參數）；
  選填的可以寫 `default`。路徑可以寫 `fetch`（工作目錄找不到原文寫的路徑時查一次：`{value}` 換成原文的最後一段、`{stem}` 是它去掉副檔名；
  路徑結尾跟原文一樣，或檔名就是查的那個名稱而且原文前面的目錄照順序都在路徑裡，剛好一個就自己補——「X 規格書」寫 `{stem}.md`，
  名稱只是含 X.md 的 test_X.md 不算；好幾個或找不到時交回領域 session，附候選）。
  `type` 決定程式怎麼核對領域 session 抄的原文（要在問題、子目標、項目或前面的結果裡）與值：
  - `name`：一個識別字，要原樣在原文裡；
  - `path`：每一段（/ 分開）是原文裡的名稱（「a 的 b/」就是 a/b），原文沒有的上層目錄不能補；之後還要在工作目錄找得到；
  - `text`、`glob`（檔案名稱的寫法）：值裡的每一段英數字或中文都要在原文裡（`Python 檔` → `*.py` 可以，`設定檔` → `*.yaml` 不行）；
  - `names`：名稱清單（目錄名稱），每一個要原樣在原文裡；
  - `words`：搜尋的字（名稱或短詞，英文的詞組可以有空白，不能有括號與 `|`），每一個要原樣在原文裡；幾個字常在原文不同的地方，
    抄的原文可以是用「、」分開的幾段（每一段一字不改）。名稱清單與搜尋的字的原文都可以這樣抄。
- **骨架**：`{"nodes": [...]}`，節點的寫法同低階執行器（`tool`、`args`、`depends_on`、`expect`、`complete`、`why`，帶入寫
  `{"from": 節點, "field": 收據項目的鍵}`），另外：
  - 參數寫成 `{名稱}`；可能沒有值的參數要放在 `{"if": "參數", "args": ["--include", "{參數}"]}` 裡（有值才放；名稱清單一項一組），
    或整個節點寫 `"if": "參數"`（沒有值就不排，依賴它的也不排）；搜尋的字要整個參數只寫 `{名稱}`（程式用 `|` 接成一個關鍵字，
    search_text 的同義詞寫法）；
  - `"report": "小標題"`：這個節點的結果交給領域 session 時的小標題（沒寫就用 `why`）；每個節點的結果原文照舊存成 #編號，太長的提煉。
- **回退**：`[{"id", "when", "change", "say"}]`，照列的順序比對，每一個最多用一次：
  - `when`：`node`（骨架或回退加的節點）加至少一個條件：`state`（節點的狀態）、`capped`（帶入的實例超過低階的上限）、
    或收據的欄位（`status`、`truncated`、`timed_out`…：那個節點某一個實例最後一次嘗試的收據相等就算）；
  - `change`：`{"add": [節點…]}`（在圖上加節點，交給低階接著跑；加的節點全都跑過就是不收斂、不重排）、
    `{"ask": "參數", "from": 節點}`（交回領域 session 決定這個參數，附那個節點收據裡各子目錄的筆數；它改了參數再用一次），或
    `{"switch": "同一個領域的技能", "params": {"換過去的參數": "這個技能的參數"}}`（換技能：參數照對應帶過去，名稱可以換成清單；
    算一次重排）；
  - `say`：給領域 session 與報告看的一句話。
- 載入領域時檢查規格（`composite.validate_skill`：欄位、參數的引用、只能有工具節點、回退，最後用假的參數排一次圖交給低階的檢查；
  換技能的對象與參數的對應在載入整個領域時核對），寫錯的整個領域不能用；`evals/domain/selftest.py` 跑有骨架的技能與回退。
- 有骨架的技能是模型會讀的文字（〈什麼時候用〉、description、參數的 desc）：改了要跑真實專案評測（`evals/repo/run.py`）；範例不要用評測世界的名稱。

## 2. 腳本的輸出（`skills_system/scripts/<名稱>_cmd.py`）

輸出是給模型看的文字，一行一行，長的輸出會由系統依結構切段、交給幾個獨立 session 提煉（`agent_core/extract.py`），所以要有固定的結構：

1. **第一行**：`[PASS]` 或 `[ERROR]` 開頭，一句話的結論與程式算好的數量（共 N 個、列出前 M 個、略過幾個、沒有權限的幾個）。
2. **分節**：長的輸出每一節一行 `## 標題（N 項）`，節裡一行一筆；表格的欄名接在節標題的下一行（切段時會把欄名帶到下一段）。
   多行的一筆（一則訊息、一段 traceback、一個區塊）以 `--- #序號` 開頭（`result_grep --block` 依它取整筆）。統計、結論在前，原始資料在後。
3. **有截掉就說**：只列前 N 個、只看最後 N 行、單行太長截斷時，寫在第一行或那一節，並寫怎麼看其他的（換參數、`--filter`、`--from`）。
   不要默默地截。
4. **數字由程式算**：數量、統計、比較、門檻判斷、排序都在腳本裡算好寫出來（「共 12 個」「第一則符合 #49」），模型照抄、不自己數。
5. **時間**：寫明時區或基準（`+秒`＝距離數據或觀察開頭）。
6. **狀態標記**（`[TARGET_CONTAINER]`、`[ANALYSIS_DATA]`、`[CWD_CHANGED]`…）只放在輸出的最後幾行：系統只認最後連續的標記行，
   原文（容器的 log、指令的輸出）裡剛好出現同樣的字不會被當成標記。

### 2.1 收據（第一版領域的技能：search_text、find_file、list_dir、view_file、code_ast_reader、code_defs、py_refs、result_list／grep／view）

給模型的文字之外，腳本另外寫一份給程式讀的結構化結果（`skills_system/scripts/_receipt_common.py`）。harness 執行腳本時用環境變數
`AGENT_RECEIPT_PATH` 指定檔案，執行完讀回 `last_receipt`、跟存檔放在一起（`<存檔>.receipt.json`）；沒有設定就不寫（在終端機直接跑時不寫收據）。
**給模型的文字一個字都不變**（測試會用有、沒有收據各跑一次比對）。

- 寫法：`execute(argv)` 回傳給模型的文字。錯誤的出口 `return fail(text, "<種類>")`（`_path_common.resolve` 回的錯誤已經帶種類，`fail(err)` 就好）；
  成功的出口先 `result("pass" 或 "empty", counts=…, items=…, truncated=…, 其他欄位)` 再回傳文字；進入點 `main(execute, "<技能>")`。
- `status`：pass（有結果）、empty（成功、但是空的：0 筆、空目錄、空檔案）、error。`error_kind`：args（輸入不對：參數、選項、路徑、
  檔案的種類或格式——換參數或換工具修得好）、env（沒有權限、找不到指令、裝置讀不到——換參數修不好）、timeout（逾時而且沒有任何結果；
  有部分結果時是 pass、`truncated` 為真）、parse（腳本自己的例外、沒有記收據——要修程式）。
- 收據要比文字完整：文字只列前幾筆（每個檔案 20 筆、200 行…），收據記全部（每個檔案的筆數、所有命中的行、全部的定義），上限
  `ITEMS_MAX` 筆，超過時 `truncated`。路徑一律是絕對路徑。
- 沒記收據、或記的跟回傳的文字對不上（回 `[ERROR]` 卻記成 pass）時，進入點寫成 `parse`；測試會擋。

## 3. 錯誤

- 可預期的錯誤（參數錯、找不到、沒有權限、逾時、服務沒回應）：印 `[ERROR] 原因。下一步：…` 到 stdout，exit code 0。
  下一步要具體：「先用 docker_containers 確認名稱」「--duration 縮短到 10 秒」「請使用者確認要用哪一台車」。
- 參數錯時附上正確的用法（`USAGE`），USAGE 裡的腳本路徑要跟規格一致（大小寫一樣）。
- 不認得的參數、多出來的參數：回 `[ERROR]` 或在輸出最後一行明說略過了什麼（`CliParser.ignored_note`），不要默默忽略。
- 工具自己的錯誤訊息（stderr）原文附在後面（太長截尾），不要只寫「失敗」。
- 未預期的例外：`[ERROR] <技能> 未預期的例外：<型別>: <訊息>`，exit code 1。

## 4. 可以自己用（不需要人在旁邊）

- **不讀標準輸入**（`stdin=subprocess.DEVNULL`），不開互動式程式（編輯器、分頁器、`sudo` 問密碼）；`docker exec` 不用 `-t`。
- **每個外部指令都有逾時**，各技能的上限低於系統的 600 秒；逾時要結束整個程序群組（`start_new_session=True` ＋ `os.killpg`），
  不留背景程序；逾時時回傳已經拿到的部分並說明（「60 秒內只收到前 30 行」）。
- **不會自己結束的指令**（`tail -f`、`ros2 topic echo` 不加 `--once`、`ros2 topic hz`）：改用有時長的技能（`ROS2_topic_echo --duration`），
  或一定要帶 `timeout N`。
- 輸出用 `errors="replace"` 解碼（容器的 log、二進位檔不會讓腳本當掉）。
- 路徑：`~` 要展開；相對路徑相對於目前的工作目錄（harness 執行腳本時的 cwd）；容器內路徑與主機路徑分清楚（數據技能會依 bind mount 換算）。
- 寫檔只寫到參數指定的地方或 `logs/`，不要寫進使用者的工作目錄。

## 5. 測試

- 不用模型的測試在 `evals/skills/`（`python3 evals/skills/selftest.py`）：每個技能至少有一個 `[PASS]` 的情況與每一種 `[ERROR]` 的情況，
  檢查第一行的格式、下一步的提示、截斷的說明；需要容器的情況在沙盒（`evals/ops` 的 Docker-in-Docker）裡跑，沒有沙盒就略過並註明。
