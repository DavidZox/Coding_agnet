### 2.18 2026-10-14：數據解析 agent——依 toolkit 重寫的數據技能，與 Orchestrator → Workers → Synthesizer

**起點**。拆分前的四個數據技能（mcap_recorder／rosout_parser／mcap_slicer／mcap_analyzer）跟使用者手動用的 `diagnostics_package/toolkit` 比，
少了最有用的三件事：Log 去重（toolkit 的 mcap_slicer 步驟 3）、欄位的型別與維度（metadata.yaml 的 available_keys）、特徵量測
（mcap_feature_measure.py）。另外 recorder 把 `ros2 topic echo /rosout` 的原始 YAML 直接存成 rosout.log（沒有經過 rosout_formatter），parser
逐行解析不了；slicer 要求 MCAP log_time 的奈秒值（模型要抄 19 位數）；analyzer 只回原始值。使用者的架構文件要的是：全域 Metadata 預先建立、
按需量測（Lazy Evaluation）、String／Log 只給 Orchestrator、Orchestrator 把不同的 Topic 分給不同的 worker、worker 自己選 Key、
Frontmatter Markdown 的產物、Synthesizer 做因果拼圖。

**一、數據技能（`_ros2_data_common.py` 與五支腳本）**
- **送進容器的方法**：原本每支腳本把自己 base64 後放在 `bash -c` 的參數裡；單一參數有 128 KB 的上限，共用模組又要一起送。改成 tar.gz＋base64
  經 `docker exec -i` 的 stdin 送進容器的暫存目錄（`_docker_common.docker_exec` 加了 `input_text`），執行完刪掉。主機不需要 ROS 2。
- **自訂訊息型別**：`ROS2_ENV_FALLBACK` 加上 `/workspace/install`、`/workspace/*/install`（這台的 ros2_web_container 是 `/workspace/app/install`），
  harness 用 ROS2_workspace_env 確認過的 Workspace（屬於這個容器時）另外載入。讀不到的 Topic 角色標成 undecodable，說明要先確認 Workspace。
- **路徑**：主機路徑依容器的 bind mount 換成容器路徑（`/home/david/ros2-web-app/app/…` ＝ `/workspace/app/…`），實驗名稱與 `latest` 相對於數據根目錄
  （沒設定時在容器的 /workspace 底下 4 層內找 `experiment_logs`）。成功操作的數據在輸出末行印 `[ANALYSIS_DATA]`，harness 同步成「目前分析的數據」
  （比照目標容器），之後的技能可以省略路徑。
- **Key 的類別**（`describe_keys`，每個 Topic 抽樣 120 筆判斷）：數值、向量（2～4 個浮點分量的訊息或固定長度陣列）、矩陣（covariance）、陣列、
  狀態（uint8／bool／octet、相異值少的字串、短的整數或字串序列＝集合）、鍵值（KeyValue）、文字、時間。toolkit 用子字串 `int` 判斷整數型別，
  `builtin_interfaces/Time` 也會中而被當成狀態跳轉；`sequence<…/ActionParam>` 被當成 scalar——都改成依 ROS 型別字串解析。
  **字串分兩種**：使用者的設計是「String 只給 Orchestrator」，但實際的數據裡很多字串其實是列舉（`mode`＝PROTECTIVE_STOP／NORMAL、
  `primary_reaction`＝INIT／NONE），它們的跳轉正是 worker 該看的；所以相異值 ≤8（或 ≤12 而且都很短）的字串當「狀態」，其餘是「文字」
  （worker 不量測）。DiagnosticArray 這種「有 name 欄位的訊息序列」依名稱展開（`status.level` 每個 status 一項），只列有變化的。
  空的序列要看宣告的型別：訊息的序列是「沒有項目」，基本型別的序列（`stop_reasons=[]`）是「空集合」這個狀態值（第一版把 28 個空的 values
  當成假項目）。分類規則改了就把 `INDEX_VERSION` 加一，舊的快取自動重建。
- **Log 的來源**：預設用 bag 裡的 /rosout（時間＝MCAP log_time，跟其他 Topic 同一個時鐘；範例數據 bag 裡 31 則、rosout.log 只有 11 則——
  `ros2 topic echo` 比錄製晚開始），沒有才用 rosout.log；只差在數字的訊息算同一句；rosbag2 自己的 Log（Subscribed to topic…，範例裡 31 則佔 22 則）
  預設不列、不交給 Orchestrator。編號 L# 在篩選之前編好，mcap_slicer --signal 與 analysis_run 用同一套。
- **寬鬆的寫法**（實測驅動）：e4b 的 worker 把時間窗寫成 `0.00s_30.54s`、`0.00,30.54`、`+0.00s,+30.54s`，四次量測白費；主對話自己加了不存在的
  `--measure max`。現在時間接受 `+秒`、尾巴的 `s`、`～`／`~`／`_`／`to` 分隔，小於 10 億的數字當距離數據開頭的秒數（不可能是 epoch）；
  主機端不認識的參數照認得的做完、輸出最後說明忽略了什麼（都是唯讀工具，比回錯誤讓模型重送一次省一輪）。

**二、多 agent 協同（`analysis_job.py`）**
- **同步的偽技能，不是背景服務**：coding orchestrator 是背景服務（job 要跑幾十分鐘、中途要核准）；數據診斷只讀不改、通常一到幾分鐘、
  不需要核准，所以照 ops_run 的做法在主對話的回合裡同步執行，架構跟原本一樣；進度經 `progress_callback` 推到 Web 右欄（ops_run 也一起受惠），
  產物寫在 job 資料夾給面板讀。
- **時間戳由程式換算**：Orchestrator 只填 L#，程式依去重後的時間戳算時間窗；worker 用 `W1` 這種編號。所有輸出的 `[+秒]` 都是距離數據開頭
  ——第一版量測工具的相對時間是對時間窗的錨點，worker 照抄、Synthesizer 當成距離開頭，時間線差了 0.75 秒。
- **計畫由程式檢查**：L#、Topic 要存在、角色是 worker、不重複、不超過上限；問題具體列出交回修一次，還是沒有可用的指派就依「跟相關 Log 共用的詞」
  補指派。
- **worker 的範圍由程式守**：`--topic` 固定、只准量測技能、看不到 Log 字串；局部報告的 frontmatter 由程式用 `--json` 再量一次填數字，
  模型寫的 analyzed_keys 只留真的量過的。e4b 常把動作的 JSON 寫進 `reply`、`action` 留 null：worker 的工具都是唯讀的，所以照做
  （主對話仍維持 reply 不執行）；一個 Key 都沒量時推回去一次，還是沒量就由系統代選（狀態優先），frontmatter 標 `key_selection: fallback`。
- **「數據範圍」的程式檢查**（`_coverage_gaps`）：相關的（與 WARN 以上的）Log 裡「某個輸入沒有／逾時／遺失」的原因代碼（`NO_X`、`X_TIMEOUT`、
  `LOST_X`…），X 對不上任何有訊息的 Topic 名稱時，程式把它列給 Synthesizer、保證寫進「尚未確認」、信心最多 medium——e4b 三次都拿
  名稱相近的輸出 Topic 當證據，只靠 prompt 的規則擋不住。`NO_SAFETY_COMMAND_YET` 去掉 `_YET` 後對得上 `/system/safety_command`，不算缺。
  時間線也由程式依 +秒 排序。
- **Synthesizer 拿到數據裡全部的 Topic 名稱**，規則要求 Log 提到、數據裡卻沒有的 Topic 寫進「尚未確認」；模型寫的 LaTeX 箭頭
  （`$\rightarrow$`，JSON 裡的 `\r` 會變成換行字元）由程式換成 →。

7. **實機從錄製到解析**（2026-10-15，Web Console、auto 模式、e4b；容器裡的 diagnostics 節點穩定運作中）：使用者說「錄 30 秒、全部 Topic」，主模型卻選了 `--preset core`（它的想法寫著「要求錄製所有 Topic，我會使用 --preset core」），/system/safety_gate_status 沒錄到——規格只解釋了 core。規格與 AGENT.md 改成明寫「全部／所有 → `--all`、核心 → `--preset core`、點名 → `--topics`」之後，同一句話選對 `--all`。這 30 秒系統沒有任何事件，/rosout 的 17 則全是 rosbag2 自己的 Log：交給 Orchestrator 的文字原本寫成「沒有 Log：這份數據沒有 /rosout」，報告因此說「沒有 Log 內容、無法判斷」——改成明說「Log 共 N 則、全部是錄製工具自己的訊息，不是缺少 Log」，給人看的 log_digest.md 也列出 rosbag2 的 Log 並標明。修正後分析 50 秒、14 次模型呼叫、4 個 worker，結論「穩定、沒有異常」正確；但報告沒有解釋 mode=NORMAL 時 stop_reasons 一直是 [NO_CMD_VEL_RAW]（＝沒有速度輸入、系統閒置），/cmd_vel 也因為 worker 上限 4 個沒被指派。
8. **實機事件測試**（2026-10-15，同上的環境；資料、ground truth 與每次分析的對照在 `test_data/README.md`）：錄製期間在容器裡製造事件，分析問題一律中性。
   - **事件一：/cmd_vel_raw 發 0.1 m/s、8 秒**。第一次分析的根因是錯的（判定 NO_CMD_VEL_RAW 的 Log 是誤報），原因在量測工具：
     - 只看相鄰訊息的間隔，回報 /cmd_vel_raw「沒有訊息中斷」——看不到它在 +21.28s 之後就停了。
     - gate 的 stop_reasons 只在狀態改變時發布（TRANSIENT_LOCAL），時間窗開頭沒有沿用之前的狀態，少算一次跳轉。
     改成：列第一筆／最後一筆的時間、固定頻率的 Topic 標「中途才開始／中途停止發布」、狀態沿用時間窗之前的最後一則（mcap 反向讀）、只有幾種值的數值列每次切換（/cmd_vel 的 0 → 0.1 → 0）。修完之後時間線全對，但模型把「指令結束」說成「間歇性丟失」，還把 0.5 秒的逾時當成時間對不上；worker 與 Synthesizer 的 prompt 加了規則（中途開始＋中途停止＝一段連續的發布；停止後才出現的 NO_X 是逾時判斷的結果），之後因果鏈正確（high），但仍沒有主動說這是正常的操作序列。錄製時「資料夾名稱用 X」被送成 `--out-root X`、錄到數據根目錄之外，`mcap_recorder` 改成沒有斜線的名稱當 `--name`。
   - **事件二：lifecycle manager 重啟 system_health_monitor**（重啟後 monitor 初始化，gate 因 MON_INITIALIZING 保護停止 15.1 秒）。第一次的時間線把 L17 寫成時間窗開頭的 +8.71s（實際 +18.71s），主模型照抄——程式改成來源是單一 L# 的時間照 Log 的時間戳校正。之後根因一度變成「NO_CMD_VEL_RAW 觸發停止」：它前後都在，但覆蓋缺口的提醒把注意力引到它身上。程式改成：缺口代碼若在 worker 量到的清單狀態每次跳轉前後都在，就當背景條件（不列進尚未確認、根因沒用到它就不限制信心）；Synthesizer 也加了「清單型狀態看新增與移除」的規則。最終版的根因正確（重啟 → MON_INITIALIZING → 保護停止 → 初始化完成恢復，並說明 NO_CMD_VEL_RAW 是背景條件）。
9. **第三輪：動態時間切片、真的故障、自動評分**（2026-10-15 下午；錄製、ground truth、評分表在 `test_data/README.md`、`evals/results/`）。

     `--with-state` 帶上每個 Topic 在時間窗之前的最後一則），worker 只讀切片。180 秒的長錄製（故障在 +150s）：切片 0.9 秒、1,185 則＋5 則
     狀態快照（整份 8,682 則），worker 只讀約 14%；讀切片量到的跟讀原本的數據逐字相同（`analysis_tools_live.py` 的檢查）。
     worker 自己抄的時間窗有四捨五入（+140.82s,+175.31s），量測工具換成指派的那個才讀得到切片。
   - **真的故障**：SIGSTOP 凍結 diagnostic_aggregator 10 秒（health monitor 只在收到 /diagnostics_agg 時發布安全指令 → gate 0.5 秒後
     SAFETY_COMMAND_TIMEOUT → 保護停止 → 恢復）。第一次看：程式量到 /system/safety_command、/diagnostics_toplevel_state 中斷 10 秒，
     worker 卻以「狀態沒變」判沒有異常。改成：訊息流中斷（停發、中途開始／停止）由程式列進證據、強制算異常；交給 Synthesizer 的
     「訊息流」整理列出同一時間一起中斷的 Topic（共同的上游）；時間線缺的中斷事件程式補上。
   - **背景條件的更正**：結論或根因拿「每次跳轉前後都在」的原因代碼當原因時，程式在後面附更正（點名跳轉時真正新增／移除的項目），
     不只壓信心。「拿它當原因」看句子：排除（背景、而非、不是…）、讓步子句（雖然…但）、只說沒被量測的不算。
   - **一段連續的發布寫成一句**：中途開始又中途停止、中間沒有中斷時，量測寫「只在 +13.47s～+21.28s 連續發布 7.81 秒」（分開的兩個指標

     中途才開始，反而變成「速度指令缺失」的證據——回歸評分的第一批結果抓到的退步，修完重跑）。

     推理模型沒有比較好：一樣拿 NO_CMD_VEL_RAW 當原因（8 次，e4b 5 次），真故障也很少追到共同的上游。這台 8 GB 筆電三個角色都用 e4b；
     DGX Spark／5090 上換 26b 時用同一套 `analysis_regression.py --model gemma4:26b` 比較。

## 已知限制（根因、源碼相關，原編號）

57. **源碼要跟錄製時的版本一樣**（2.19）：Log 的 file:line 對回源碼的那一行附近不是 Log 呼叫、或函式名稱對不上時標「源碼可能跟錄製時的版本不同」，
    但只檢查得到有 Log 的地方；源碼改過、行號沒變的邏輯差異看不出來。建議源碼目錄用錄製當時建置的那一份（這台是同一份）。
58. **源碼索引是靜態的、字面的**：Topic 名稱要寫成字串常值（或模組層的常數）才認得；launch 的 remap、參數決定的 Topic 名稱、不在根 namespace 的節點、
    composition（同一個行程多個節點）、action、跨行程的服務呼叫、diagnostic_updater 這類由函式庫發布的 Topic（/diagnostics）都沒追；C++ 沒有用編譯器解析，
    巨集或樣板很複雜的檔案可能切錯函式範圍。「依賴的輸入」看成員變數的讀寫，經過別的物件（core_.onDiagnostics）傳遞的只追一層呼叫者。
59. **在執行的節點是推的**：Log 的節點、數據裡的 `/<節點>/transition_event`、同一個 launch 檔一起啟動的節點、只有一個節點會發布的 Topic；
    沒有 Log、也沒有 lifecycle Topic、launch 檔又不在源碼目錄的系統可能找不到（源碼脈絡就少了節點）；同一個 launch 檔裡實際沒啟動的節點會被當成在執行。
    錄製時順便存下 `ros2 node info`（真正的發布／訂閱）會更準，還沒做。外部套件（diagnostic_aggregator）沒有源碼，只列名字。
60. **源碼解決不了判斷類的問題**（2.19 第 2 點）：「一次指令的開始與結束是正常的操作」「Log 的 reasons 哪一個才是觸發」只給源碼時仍會寫錯，
    要靠程式的判斷提示（`program_hints`）；源碼脈絡也會改變 Orchestrator 挑的訊號（第 3 點），所以分兩步（2.20）：挑訊號那一步只在 Topic Metadata 帶源碼。
61. **回歸評分是關鍵字比對，新寫法可能被誤判**（2.19 第 5 點）：第四～六輪靠人工複核；2.22 起照人工判定的先例補了說法，
    `test_data/tools/scorer_check.py` 核對 1243 項人工判定全部一致（第八輪）——之後出現沒看過的寫法仍可能判錯，新的一輪要抽看幾份、不一致的補進
    `rubric7_labels.json`。`cmdvel_confusion.py` 也把「NO_CMD_VEL_RAW 不在 PROTECTIVE_REASONS 裡、/cmd_vel 為 0」這類有源碼根據的句子算進去，要人看。
62. **「拿某個代碼當原因」的判斷是逐句找詞**（2.20 第 5 點）：`_relies_on` 與回歸評分看提到代碼的句子；2.22 改成排除的字要對著那個代碼、
    清單狀態的引用與「一直存在／恢復後輸出為 0／無法確認是否」不算，第四～六輪的 14 次誤判都對了——但仍是找詞，沒看過的句型可能判錯；
    要根本解決得讓因果的輸出變成欄位（因果鏈的每一環＋出處），程式就不必從文字猜。
63. **觀測角度只核對得到在執行的節點**（2.21）：外部節點（diagnostic_aggregator…）、源碼裡沒有發布者或訂閱者的 Topic 不查；
    核對的是「節點有沒有發布／訂閱這個 Topic」，不是子任務的文字——角度對、子任務仍寫成驗證輸入的情況程式看不出來（實測 0 次）。
64. **補推理鏈只補「還沒分析的 Topic」**（2.21 第 4 點）：同一組時間窗、不換時間範圍、不重量分析過的 Topic；補派的 worker 讀原本的數據（不在切片裡）。
    缺口是「沒錄到」或「節點內部的狀態」時補不了——這 7 份數據幾乎都是這種，所以大多一輪就結束。
65. **系統提示的措辭會改變判斷**（2.21 第 3 點）：「只根據事實、不要用推測補」讓 Synthesizer 不寫「正常的操作」（27/27 → 20/27），
    要另外說明「事實能完整解釋的就照事實定性」。改系統提示要用只重跑一個角色的對照（同一份輸入）量。
66. **「輸入為什麼停」數據看不出來**（2.22 第 4 點、2.23 做法第 8 點）：/cmd_vel_raw 停之前沒有送 0，「正常做完」與「上游掛掉」的數據一樣。
    第八輪起評分把「指令／輸入正常結束、自然停止」算越過事實的說法；判斷提示的措辭改成「為什麼開始、停止看不出來」之後 4/10 → 0/10。
    評分只認「指令、輸入、源頭…」當主詞的寫法（系統照設計「正常停止輸出」不算），換個主詞的說法可能漏掉。
68. **因果推論集中在一步，輸入大**（2.23）：Log、完整源碼脈絡、事實整合與各 worker 的事實一起給 Orchestrator（約 25～30k 字），26b 一次約 6.6 秒，
    整體比第七輪慢約 6 秒。結論與根因寫得比較精簡、細節（代碼、L#、源碼位置）在因果鏈——讀報告、評分都要看因果鏈。
69. **補分析只往上游，而且只認得源碼裡的節點**（2.23 做法第 4 點、2.24 做法第 3 點）：第九輪起只准量那一項提到的 Topic、發布它的節點的
    輸入與其他輸出；上游只往回看一層，那一項要寫出 Topic 或節點的名稱才認得。外部套件的節點（diagnostic_aggregator）的輸入、輸出
    認不出來——例如要補「/diagnostics_agg 為什麼停」，只能補量它本身。
70. **判定的依據只看 Log 的層級與量到的訊息中斷**（2.23 做法第 3 點）：錯誤碼、保護類原因如果只在 Topic 裡、沒有 WARN 以上的 Log，判定「有異常」

71. **事實整合的「不寫因果」靠詞表**（2.23 做法第 1 點）：導致、因為、證實、排除…擋得住大部分，換句話說的因果（「隨後因此…」「使得」）可能漏掉。
