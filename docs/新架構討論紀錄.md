## 1. 構想的摘要（我的理解；第 2 輪使用者沒有更正）

**三層**

| 層 | 讀的知識檔 | 做什麼 | 出錯時（三級回退） |
|---|---|---|---|
| 高階：Orchestrator | `DOMAIN.md`：每個領域的邊界、說明、入口技能 | 判斷問題屬於哪個領域，寫出第一層的子目標，連同使用者的原始問題交給那個領域 | **第 3 級**：領域判錯或越界時，清掉那個領域的上下文，帶著「不是這個領域」重新分流。全部用完時停下來，寫失敗報告給人 |
| 中階：Domain Worker | 領域的 `SKILLS.md`；複合技能的規格（合約、`topology` 的 `depends_on`／`sub_skills`、SOP 與替代做法） | 挑技能，做合約檢查：必填參數先從上下文找，能自己查的自己查，查不到或要使用者決定的才問。補上漏掉的前置依賴，排出決策圖（DAG／EDG）交給低階 | **第 2 級**：收到低階「結果沒有用」時，照 SOP 換替代做法重排。重排太多次就熔斷，把摘要往上報 |
| 低階：EDG Executor | 工具規格：字面參數、`# 語法`、`# 回傳`、`# 異常` | 照圖一個一個執行腳本。執行前用程式檢查參數，不花模型呼叫；照收據決定下一步 | **第 1 級**：參數錯、逾時這類技術錯誤在原地修正重試。結果沒有用（例如只有 `/rosout`）時往上交給中階 |

**跨層的機制**
- **子目標往下傳**：每一層交下去時都寫一個這一層的子目標，同時附上使用者的原始問題。下一層照子目標從原文挑要的參數。
- **子工作階段隔離**：試錯留在子工作階段裡，只把整理好的結果交回主對話。
- **執行狀態跟圖分開存**：收據、事件、帳本另外存。重排時不用重寫整張圖。
- **12 種異常**分到三層（低階 4、中階 4、高階 4），每一種都有對策。

### 跟業界做法的對照（2026-11-19 使用者問，第 5 步 5-2 的評測期間）

使用者問了兩件事：(1) 改成「階層技能書＋有向圖（DAG）」是不是比較好？之前主對話直接執行很不穩、任務引擎出錯時反應很差，是不是技能書用錯了，
業界有沒有在用？(2) 是不是沒有人分這麼多層？分層是觀察到「一步一步做每次都不穩、出錯也不能穩定糾錯」，加上讀了很多論文才這樣做的，這樣不好嗎？

下面的出處是公開的文章、論文與框架（這一輪沒有重新上網查原文，細節以原文為準）；數字是我們自己的評測。

**結論**：以我們的條件（本地小模型、離線、長任務要穩），這個方向比之前好，評測數字支持；每一塊都有對應的公開做法，分層本身是很標準的做法，
不是缺點。沒有一個現成框架跟這個組合完全一樣：每一層都由程式核對、最底層是照收據執行的決策圖、整套為小模型設計，這是它的特色。

**之前不穩，不是技能書用錯**
- 技能書（索引＋用到才載入規格）就是現在的主流做法：Anthropic 的 Agent Skills（2025）也是先只給名稱與一句說明、用到才載入全文
  （progressive disclosure），Claude Code 的 skills 也是。
- 不穩的原因在別處：一個小模型在一條越來越長的對話裡，同時負責規劃、執行、判斷做完沒、記住出錯的原因；試錯都留在主對話；任務引擎把計畫
  一次排好，出錯時沒有帶著原因重新規劃，「做完了沒」也是模型說了算（第 6 節的 29：沒做完卻回報完成）。

**各層對應的公開做法**

| 這個架構 | 一般的叫法 | 公開的例子 |
|---|---|---|
| 高階：交給領域（DOMAIN.md） | routing、handoff | Anthropic〈Building effective agents〉（2024）的 routing、orchestrator-workers；OpenAI Agents SDK 的 handoffs；Google ADK 的階層式多代理 |
| 技能書分層、用到才載入 | progressive disclosure | Anthropic Agent Skills、Claude Code skills |
| 中階：複合技能（SOP）→ 合約 → 排圖 | workflow／SOP、plan-and-execute | MetaGPT（把 SOP 寫進流程）、LangGraph、LangChain 的 plan-and-execute |
| 低階：照 DAG 執行、照收據守門 | 先規劃成 DAG 再執行 | LLMCompiler、ReWOO、HarnessMM（EDG＋收據） |
| 子工作階段：自己的對話，只交回報告 | subagent、context isolation | Anthropic 的多代理研究系統（2025）、Claude Code 的 subagents |
| 程式核對事實與做完沒、schema 限制輸出 | structured outputs、guardrails | JSON schema 輸出（Ollama、OpenAI）、OpenAI Agents SDK 的 guardrails |
| 三級回退、帶著上一次的經過重新規劃 | replanning、reflection | LLMCompiler 的 replan、Reflexion |

〈Building effective agents〉的核心建議跟這個方向一致：做法固定的寫成固定流程（workflow），只有需要彈性的地方才交給模型判斷。

**分這麼多層的例子**（分層的理由——把責任切開、每一層就近發現與修正錯誤——是這類系統分層的標準理由）
- **機器人的三層架構**：3T（Bonasso 等，1997）與 Gat〈On Three-Layer Architectures〉（1998）把系統分成規劃（deliberative）、排程序（sequencer，
  用 RAP 這種寫好的程序）、技能（reactive skills，執行與監控）。對應這裡的高階（分流）、中階（複合技能＝寫好的程序）、低階（照圖執行、看收據）。
- **Nav2 的 behavior tree 與 recovery**：出錯先在原地修（清 costmap、原地轉、後退），修不好重新規劃路徑，再不行才放棄、交給上層——就是三級回退的想法。
- **HTN 規劃**（hierarchical task network）：任務照「方法」拆成子任務、最後是基本動作；複合技能就是「方法」。
- **LLM 的 agent**：Microsoft Magentic-One（2024：Orchestrator 記 task ledger 與 progress ledger，卡住時帶著新的事實重新規劃、換人做）、Agent S
  （2024：manager 拆子任務、worker 執行並反思）、HuggingGPT（2023：規劃 → 選模型 → 執行 → 回答）、Voyager（2023：技能庫、執行錯誤回饋、自我驗證）、
  Google ADK 的多層 agent。

**為什麼小模型更需要結構**：小模型最弱的是長流程裡自由發揮；把每一步縮成「從清單選一個」「填 schema 的幾個欄位」最穩。大模型的系統常把核對、
重試交給模型自己，結構可以比較輕；小模型做不到，就要由程式補上。

| 中 1 結果沒有用（成功但內容空） | 照 SOP 換替代做法 | 程式＋排圖：排圖時在節點上寫預期（例如「至少 1 筆」），程式照收據判斷。問「X 有沒有人用」時 0 筆就是答案，預期寫「0 筆也算答案」 | 做 |
| 中 2 不是這個領域 | 停下來，把查到的結論往上交 | 模型：worker 回報「不在這個領域」與理由 | 做 |
| 中 3 漏了前置依賴 | 改圖，補上前置節點 | 程式：排圖時照 `depends_on`；執行時收據的錯誤種類對到規格寫的前置技能 | 做 |
| 中 4 重排不收斂 | 熔斷，摘要往上報（圖上的例子是 3 次） | 程式：重排的次數上限；另外，同一個工具＋同樣參數的節點不重跑（直接用之前的收據），重排只排出跑過的節點就是不收斂 | 做 |
| 高 1 分流錯 | 清掉那個領域的上下文，帶著排除條件重新分流 | 模型：Orchestrator 照中階的回報 | 做：每個領域最多進一次；沒有可分的領域就是高 4 |
| 高 2 意圖漂移 | 對照原始問題，漂移就重排（漂移分數 > 0.65） | **跟圖不同**：分數不可靠，也是門檻值 | 改成結構：分流時把原始問題拆成要回答的項目（結構化輸出），往下傳；最後由程式檢查每一項都有核對過出處的答案，或明寫查不到與原因。沒答到的項目只補那幾項，不重排整張圖 |
| 高 3 跨領域資源衝突 | 照優先權仲裁 | — | 第一版唯讀，不做。會改狀態的領域回來時再談（確認關卡、鎖） |
| 高 4 全部用完 | 停下來，寫診斷報告引導人工介入 | 程式 | 做：寫做了什麼、哪裡失敗、收據的 `#編號` |

- 次數（第 1 級一次、重排的上限）是預算，不是調來讓某一題過的門檻；收斂與否另外由「不重跑同樣的節點」判斷。
- **「返回前一個成功的節點」**（對照報告的寫法）：唯讀的步驟不需要。會改狀態的步驟就算退回節點，狀態也不會改回來，要另外設計（停下來問人，或明寫的復原步驟）。第一版不做。

### D6 合約檢查的自動補參數
- **架構圖**：背景工具或歷史上下文找得到的（檔案路徑、容器名稱）自己補，不吵使用者；主觀意圖、敏感憑證、本地完全找不到的才停下來問（`validate_contract` 的 `can_auto_fetch`）。
- **定案**：「能不能自己補」寫在規格裡，由程式判斷，不讓模型臨時決定。
  - 工具規格的每個必填參數寫明怎麼找：`fetch`（用哪個工具、怎麼帶參數，例如路徑用 find_file、容器用 docker_containers）或 `ask`（要使用者決定：意圖、要改哪一台、憑證）。
  - 補的順序：
    1. 原始問題、子目標或歷史裡有（附出處）：直接用。
    2. 有 `fetch`：查一次。剛好一個就補上；好幾個時選哪一個是使用者的意圖，把候選列給使用者選（子目標寫明「全部」時，每個候選各排一個節點）；一個都沒有就問使用者，或回報找不到。
    3. `ask`：問使用者。
  - 不往下展開：查參數用的工具，它自己的參數必須已經確定。
  - 自己補的值寫進圖與收據，最後的回答列出「自己補的」，補錯時看得出來。
  - 憑證一律不自己找（第一版的領域也用不到）。

### D7 層與層之間傳什麼
- **架構圖**：每一層往下都帶使用者的原始問題與這一層的子目標，下一層照子目標從原文挑參數；試錯留在子工作階段，往上只交整理好的結論。
- **定案**：各層之間都用有長度上限的 schema。
  - **高 → 中**：原始問題（原文；使用者貼的長內容先存成 `#編號`，傳引用）、子目標、要回答的項目（D5 高 2）、引用的 `#編號` 與核對過的事實、已經排除的領域。
  - **中 → 低**：決策圖（節點的工具、字面參數、依賴、預期）。判斷節點另外帶子目標、原始問題與它要看的收據。
  - **低 → 中**：每個節點的收據（狀態、錯誤種類、數量、項目）與完整輸出的 `#編號`。
  - **中 → 高**：
    - 狀態：做完、死路、不在這個領域（附理由）、要問人（附問題）、失敗。
    - 每條結論附出處（`#編號:行號`），由程式核對；沿用提煉的核對（`extract.missing_tokens`）。
    - 沒答到的項目、自己補的參數。不交原始輸出。
  - **要問人時**：中階的狀態（圖、收據）存在 JobStore，主對話把問題轉給使用者；使用者回答後由程式接回同一個 worker 的同一個節點，不重排，也不靠模型記得要接著做（第 6 節：接著問確認的是 harness，不是模型）。
  - **執行狀態跟圖分開存**：`logs/<種類>_jobs/<編號>/` 存圖、每個節點的收據與事件；重排時只改圖。

### D8 每一層用哪個模型
- **架構圖**：沒有指定。
- **現在**：預設 `gemma4:e4b`，提煉也用同一個模型（摘要可以另外指定）；維運評測用 `gemma4:26b`。
  Ollama 讓 gemma4 一次只跑一個 slot（`config.py` 的說明），用兩個模型就要同時放在顯示卡上，或來回載入。
- **定案**：
  - 每一層（分流、排圖、判斷節點、提煉）的模型都可以分開設定。
  - 第一版全部用主對話的模型。
  - 評測用 26b、e4b 各跑，再決定排圖要不要用比較大的模型。

### D9 知識檔放哪裡
- **架構圖**：`knowledge_base/DOMAIN.md`、`knowledge_base/<領域>/SKILLS.md`、`<領域>/<複合技能>.md`、`<領域>/tools/*.md`；技能與工具的規格都寫 `domain`。
- **定案**：裡面的結構照圖，資料夾名稱沿用 `skills_system/`。
  - 新增 `skills_system/DOMAIN.md`；每個領域一個資料夾：`skills_system/<領域>/SKILLS.md`，複合技能也放在裡面。
  - **跟圖不同**：工具規格留在共用的 `skills_system/tools/`，不放進各領域。一個腳本一份規格，好幾個領域會用同一個工具（例如 result_* 每個領域都用）。
    - 領域的 `SKILLS.md` 列出它能用的工具；完整性檢查確認每個工具至少屬於一個領域、列出的工具都存在。
    - 工具屬於哪些領域只寫在這裡，工具規格不另外寫 `domain`（第 3 節已跟著改）。
  - 名稱沿用的理由：`skills_system` 也是 Python 套件，程式用 `from skills_system.scripts import …` 讀共用層（`agent_core` 的 guard、dispatch、extract 等；程式與評測共 23 個 .py 檔提到這個路徑）。
    改名會讓程式碼變成 `knowledge_base.scripts`，評測複製專案的清單也要改。文件寫明「`skills_system/` 就是架構圖的 `knowledge_base/`」。

### 第 3 步：中階（2026-11-18 定案；3a 做好）

照 D3（模型只填參數、在列出的分支裡選）、D5 的中階、D6、D7、D9，對照架構圖中階規格的範例（`topology` 的 `depends_on`／`sub_skills`＋〈策略與 SOP〉）。
使用者照建議定了草案的五點（下面 G）；3a 實作時跟草案不同的地方在 H。寫法的細節見〈技能撰寫規範〉1.2，程式與實測見設計筆記 2.30。

**A. 檔案**（D9：資料夾沿用 `skills_system/`，工具規格留在共用的 `tools/`）
- `skills_system/repo_analysis/SKILLS.md`：這個領域的索引。領域的說明（做什麼、不包含什麼）、列複合技能（名稱、一句話）與能用的工具；挑技能的模型讀它。
- `skills_system/repo_analysis/<複合技能>.md`：複合技能的規格（下面 B）。

**B. 複合技能的規格**（照架構圖的格式，加上給程式看的部分）
- frontmatter：
  - `type: Skill`、`title`、`description`、`version`；
  - `answers`：答得了問題要的哪幾種（位置、數量、內容；H4）；
  - `topology`（一行 JSON）：`depends_on`（硬性前置，D5 中 3；第一版的領域用不到，H1）、`sub_skills`（骨架能用的工具，程式核對）；
  - `parameters`：每個參數的 `type`（名稱、文字、路徑、檔案名稱的寫法、名稱清單：決定程式怎麼核對原文）、`desc`；必填的寫 `ask`；
    路徑可以寫 `fetch`（`{"tool", "args"}`，H7）。
  - `domain` 不寫（D9：屬於哪個領域寫在領域的 SKILLS.md）；架構圖的 `parent_category` 用不到。
- 正文：〈什麼時候用〉（給挑技能的模型）、〈骨架〉（決策圖的樣板，一個 JSON 區塊）、〈回退〉（第 2 級的做法，一個 JSON 區塊）、〈策略與 SOP〉。
- 給程式看的部分（frontmatter 的 JSON、骨架、回退）交給模型時拿掉，同工具規格。

**C. 中階的流程**（一個子工作階段，存在 `logs/mid_jobs/<編號>/`；要問人時存檔、接回同一步，D7）

| 步驟 | 誰做 | 做什麼 |
|---|---|---|
| 1 挑技能 | 模型（一次） | 輸入：原始問題、子目標、領域的說明與每個技能的「什麼時候用」「答得了」。先寫理解，再寫問題要的是哪幾種（位置、數量、內容），再選一個複合技能，或說 none（這個領域沒有技能做得到）、out_of_domain（中 2，往上交）。程式核對選的在清單裡、答得了問題要的每一種（H4） |
| 2 合約 | 程式為主 | 模型從原始問題與子目標抽參數，每個附一字不改的原文，程式照參數的種類核對；沒過的與漏了的必填參數交回修一次（H5）。缺的：有預設值用預設值；路徑在工作目錄找不到就照 `fetch` 查一次（剛好一個就補上、記成「自己補的」；好幾個或沒有就問使用者）；必填的問使用者（`ask`） |
| 3 排圖 | 程式 | 骨架代入參數（`{"if": 參數}` 有值才放），交給低階。模型不寫節點 |
| 4 執行 | 低階（第 2 步） | 照圖執行、守門、第 1 級 |
| 5 第 2 級 | 程式 | 照收據比對〈回退〉的條件，照列的順序取第一個還沒用過的（H2）：`add` 加節點，低階接著跑同一個工作（跑過的不重跑）；`ask` 問使用者（附各子目錄的筆數），回答之後照新的參數重排。重排最多 3 次，再要就熔斷；加的節點全都跑過＝不收斂，不重排 |
| 6 判斷節點 | 模型 | 3b 跟第一個用到它的技能一起做（H1） |
| 7 往上交 | 程式 | 狀態（做完、死路、熔斷、沒有適合的技能、不在這個領域、要問人、失敗）與報告：照收據整理的事實（附 `#編號`）、用了哪些回退、沒做完的節點、自己補的參數（H3） |

**D. 範例：`py_usage`（程式裡的名稱用在哪裡）**——對準第 0 步的錯：漏了同一個檔案裡的呼叫、把 import 當成呼叫、讀規格書代替讀程式。
code_ast_reader 加了 `--refs <名稱>`：用 AST 列出這個名稱的每一處（定義、呼叫、import、指定、其他用到）與所在的函式，
註解與字串裡的本來就不算（D3：程式節點先不做，需要時在工具加參數）。完整的規格在 `skills_system/repo_analysis/py_usage.md`，骨架與回退是：

```json
{"nodes": [
  {"id": "hits", "tool": "search_text", "args": ["{name}", "{path}", "-w", "--include", "*.py", {"if": "exclude", "args": ["--exclude-dir", "{exclude}"]}],
   "expect": ["pass", "empty"], "complete": true},
  {"id": "refs", "tool": "code_ast_reader", "args": [{"from": "hits", "field": "path"}, "--refs", "{name}"], "depends_on": ["hits"],
   "expect": ["pass", "empty"], "complete": true, "report": "名稱的每一處"}]}

[{"id": "outside_scope", "when": {"node": "hits", "status": "empty"}, "change": {"add": [{"id": "wider", "tool": "search_text", "args": ["{name}", ".", "-w", "--include", "*.py"], "report": "範圍外提到這個名稱的檔案"}]}},
 {"id": "too_many_lines", "when": {"node": "hits", "truncated": true}, "change": {"ask": "path", "from": "hits"}},
 {"id": "too_many_files", "when": {"node": "refs", "capped": true}, "change": {"ask": "path", "from": "hits"}}]
```

（`refs` 的 0 處也是答案：只在註解或字串裡提到的檔案。）這個技能沒有判斷節點：定義與呼叫由收據直接列出，模型只負責挑技能、抽名稱與範圍。

**E. repo_analysis 第一版的複合技能**（D2 的五類，對到第 0 步沒過的原因）

| 複合技能 | 骨架 | 對到的錯 | 做了沒 |
|---|---|---|---|
| `py_usage` | 搜尋 → 每個檔案 `code_ast_reader --refs` | 漏了呼叫、import 當成呼叫、讀規格書代替程式 | 3a ✅ |
| `count_in_scope` | 照範圍搜尋（`--include`、不含的子目錄）與找檔案 → 數量由程式從收據算 | 照抄工具的總數（範圍外的命中） | 3a ✅ |
| `doc_lookup` | 找文件 → 在文件裡搜關鍵字 → 每一處看前後（view_file 加 `--around <行號>`）→ 判斷節點，附編號與行號 | 長文件只讀前段、引用錯分支 | 3b ✅ |
| `cpp_symbol` | 搜尋 `.cpp`／`.h` → 每一處看前後 → 判斷節點分出宣告與定義 | 答了標頭檔的宣告 | 3b ✅ |
| `config_trace` | 找 launch 與 yaml → 搜參數 → 看前後 → 判斷節點：誰設定、值多少、程式哪裡讀 | 跨檔案沒打開設定檔 | 3b ✅ |

**C. 一個問題怎麼走**

| 步驟 | 誰 | 做什麼 |
|---|---|---|
| 1 分流 | 主模型 | 看對話與「領域」一節決定怎麼做：<br>• 打招呼、問 agent 能做什麼、答案已經在對話裡：直接回答（D1）；<br>• 凍結的工具的事：照現在的方式做（第 5 步之前）；<br>• 這個領域的問題：填「交給領域」，寫哪個領域、這一層的子目標、要回答的項目。子目標照原文寫，可以帶對話裡的名稱與 `#編號`；項目是把問題拆成一項一項，最多 6 項（D5 高 2） |
| 2 核對 | 程式 | 檢查四件事：領域在 `DOMAIN.md` 裡、這個問題沒有排除過這個領域（第 3 級）、項目有 1～6 項、交給領域的次數還沒用完（G5）。沒過的回 `[ERROR]`，附下一步 |
| 3 中階 | 程式 | 執行 `mid.Worker(agent, 領域).start(原始問題, 子目標)`，項目一起傳。中階的 prompt 先不改：項目存進 job、放在報告開頭（4-2 用資料再看要不要給挑技能與判斷看）。進度推到 Web 的右欄與 CLI，第一行就附決策圖的連結 |
| 4 問使用者 | 程式 | 中階停下來要問（參數、確認關卡）時，程式把問題與候選直接給使用者（G6）。使用者的下一句話（或按的按鈕）就是回答：`check_answer` 核對，`resume` 接回同一個工作；不合法就說原因再問一次；選取消就結束這一題，主模型收到「使用者取消」 |
| 5 報告進對話 | 程式 | 中階的報告存成 `#編號`。跟數據分析的報告一樣不提煉（`is_exempt_result`）。連同狀態、項目、決策圖的連結交給主模型 |
| 6 依報告回答 | 主模型 | 用「依報告回答」的格式（G4）：每一項寫答到或查不到、回答、出處。出處是報告裡的 `檔案:行號` 或 `#編號`；查不到要寫原因 |
| 7 核對回答 | 程式 | 檢查四件事：<br>• 每一項都有；<br>• 答到的，出處在報告裡；<br>• 回答裡的數字、路徑、名稱在出處的那幾行裡（沿用提煉的 `missing_tokens`）；<br>• 查不到的有寫原因。<br>沒過的交回修一次，只列沒過的項目；還是沒過的，那一項顯示成「沒有通過核對」，附報告的出處 |
| 8 補沒答到的 | 主模型＋程式 | 報告沒答到的項目（中階死路、熔斷、挑的行不夠），主模型可以再交給領域一次，只帶那幾項（不重排整張圖，D5 高 2）。次數用完就照實寫查不到 |
| 9 第 3 級 | 程式＋主模型 | 中階回「不屬於這個領域」（附理由）時，程式記下排除的領域，交回主模型。主模型可以換別的領域：排除過的程式會擋，每個領域最多進一次（D5 高 1）；也可以照現在的方式用凍結的工具。沒有領域可以交、或次數用完，程式寫高 4 的報告 |
| 10 顯示 | 程式 | 回答照項目排：每一項的回答與出處（`檔案:行號`）、查不到的原因、決策圖的連結。高 4 的報告寫做了什麼、停在哪裡、`#編號` |

**D. 走一遍**（第 3 節的例子；檔名是示意）
1. 使用者：「amr_base_sw 裡哪些 Python 檔用到 use_sim_time？各在哪個函式？」
2. 主模型交給領域：

```json
{"thought": "問程式碼裡一個名稱用在哪，交給 repo_analysis", "reply": "交給 repo_analysis 查。",
 "action": {"domain": "repo_analysis", "goal": "在 amr_base_sw 的 .py 裡找 use_sim_time，列出檔案與所在的函式",
            "items": ["哪些 Python 檔用到 use_sim_time", "各在哪個函式"]}}
```

3. 程式核對過，執行中階。中階挑 `py_usage`，合約是 `name=use_sim_time`、`path=amr_base_sw`；低階跑完，報告存成 `#812`，列出每一處的檔案:行號與所在的函式。
4. 主模型依報告回答：

```json
{"thought": "報告列了 3 個檔案與函式", "reply": "amr_base_sw 裡有 3 個 Python 檔用到 use_sim_time。",
 "answers": [{"item": 1, "status": "answered", "text": "a.py、b.py、c.py", "refs": ["#812"]},
             {"item": 2, "status": "answered", "text": "a.py 的 declare_params（第 31 行）；…", "refs": ["src/a.py:31", "…"]}],
 "action": null}
```

5. 程式核對：`src/a.py:31` 在報告裡，`declare_params` 與 `31` 在那一行。使用者看到的是：

```
amr_base_sw 裡有 3 個 Python 檔用到 use_sim_time。
1. 哪些 Python 檔用到 use_sim_time：a.py、b.py、c.py（#812）
2. 各在哪個函式：a.py 的 declare_params（第 31 行）；…（src/a.py:31、…）
🔗 決策圖：/topology?src=logs&ref=<中階的工作>
```

**E. 主對話還能直接用哪些工具**（G2）

  （4-1 之後調整：list_dir、find_file 改列共用的工具，見 K2；讀內容的三個照舊。）
- 例外：這個問題交給領域之後，中階回「沒有適合的複合技能」（`no_skill`），這一回合就可以照現在的方式一步一步用這些工具。這是過渡的做法，
  第 5 步之後改成在子工作階段裡做。現在沒有複合技能的例子：「列出目前目錄」「比較兩個設定檔」。
- `result_*`（回顧存檔）、`change_dir`、`modify_memory` 與凍結的工具照舊。追問先看對話與 `#編號`（D1）。

  - 同時要看檔案與容器的調查（維運的 inv_*，例如「工作區的 maps/ 裡有哪些地圖」加上容器的狀態），檔案那一半要交給領域；

**F. 評測**
- 離線（假模型）：
  - 交給領域的核對：沒有的領域、排除過的、項目數、次數用完；
  - 報告進對話與存檔、決策圖的連結；

  - 回答的核對：少一項、出處不在報告、數字不在出處、查不到沒寫原因、修一次；

- 真模型：
  - 真實專案評測（主對話，30 題）：26b、e4b 各跑 3 次，存基準（新架構接上主對話的第一版）。另外量分流（交給了沒、領域對不對、項目數）、

  - 主對話（11 個情境）、維運的「檔案與調查」（23 個情境）、提煉：看有沒有退步。

1. **分流**：主模型在回覆裡填「交給領域」（領域、子目標、項目），程式核對；不另外叫一次分流的模型。
   （另一個做法：每一回合先叫一次分流的模型。多一次模型呼叫，追問時還要另外把對話給它。）
2. **這個領域的五個工具**：從主對話的索引拿掉，中階回 `no_skill` 才在那一題放行（過渡，E）。4-1 之後調整：`list_dir`、`find_file` 改列共用的工具，主對話直接用（K2）。
   （另一個做法：照舊給主對話用，只在 prompt 寫「先交給領域」。評測量得到繞過幾次，但不是 D1 的「所有問題都走三層」；
   第 5 步全部登記成領域時再拿掉。）
3. **`DOMAIN.md`**：每個領域一行，連到領域的 `SKILLS.md`；分流看到的說明與入口技能由程式從 `SKILLS.md` 組。
   跟圖不同：圖把 title、description、entry_skills 寫在 `DOMAIN.md`，會跟 `SKILLS.md` 重複，改了一邊容易忘了另一邊。
4. **依報告回答用結構化的格式**：每一項寫答到或查不到、回答、出處，程式核對；使用者看到的回答由程式照項目排。
   （另一個做法：照現在自由寫，程式只核對數字與 `檔案:行號` 在報告裡。這樣程式看不出每一項有沒有答到。）
5. **每個問題最多交給領域 3 次**：補項目與第 3 級換領域都算，是資源的上限。用完就照實寫查不到。
6. **問使用者由程式轉、程式接回**：Web 用按鈕、CLI 用編號，可以取消；不經過主模型（D7）。
7. **第 3 級**：排除過的領域由程式擋。第 5 步之前沒有其他領域，「不屬於這個領域」就回到主對話照現在的方式做；沒有可交的領域、或次數用完，寫高 4 的報告。
8. **分兩段做**：
   - 4-1 接上：G1～3、6、7，加上報告進對話、決策圖連結。回答先照現在自由寫，程式核對數字與 `檔案:行號` 在報告裡。做完真實專案評測各跑 1 次。
   - 4-2 要回答的項目與再交給領域：G4、5 與下面 I。做完 30 題各跑 3 次，存基準。

- 模型：分流與依報告回答都用主模型（D8 第一版），不另外設定。

**I. 照使用者的目標補的**（4-2；帶著上一次出錯的原因回到前一步重新規劃）

三層各自怎麼做到「下一次就修正、帶著原因重新規劃」：
- 第 1 級（低階，第 2 步做好）：參數錯、逾時，修正的模型拿到錯誤的原文，同一個節點修一次，程式核對修正。
- 第 2 級（中階，第 3 步做好）：回退照收據的條件換做法；判斷看得到之前挑的行與找過的字，選的路不會有新的結果就交回重選。
- 高階（第 4 步補）：中階沒做完時（死路、熔斷、沒有適合的技能、不屬於這個領域、項目沒答到），下一次交給領域要帶著上一次的原因：
  1. 程式附「上一次的經過」：領域、技能、參數、找過的字、結果的狀態、停下來的原因、沒答到的項目、決策圖的連結（結構化的欄位，
     由程式從中階的 job 取，不讓模型重寫）。
  2. 中階從挑技能、合約重新規劃：挑技能與合約看得到這一節（`prompts/mid/` 加一則），判斷看得到上一次找過的字。
  3. 程式擋掉一樣的做法：同一個領域、同一個技能、同樣的參數，再跑一次結果也一樣（D5 中 4 的不收斂，同判斷的「找過的字」）：
     合約交回修一次並附原因，還是一樣就停，寫明跟第幾次一樣。
  4. 同一個問題的幾次交給領域串在一起存（第幾次、為什麼再交、上一次的工作），拓撲圖從上一次的工作連到下一次。
  5. （4-1 的實測補的）使用者看到的回答由程式照項目排時，每一項附出處那一行的原文（程式從報告取，不讓模型重寫）：e4b 照報告改寫時會漏字、
     改意思（報告寫「不變：重發 yes，不重新計時」，回答漏了「不重新計時」；設計筆記 2.33）。

**J. 4-1 實作時跟上面不同的地方**（理由與實測見設計筆記 2.33）
1. **不設「每個問題最多交給領域 3 次」**（G5 的次數）：長任務一個回合裡會交好幾個不同的子目標給同一個領域（看原本的值 → 改 → 確認改好了），
   限 3 次會把長任務切斷。改成：跟這一回合交過的一樣（領域、子目標、項目都一樣）程式就擋（再交一次結果也一樣：不收斂）；「不屬於這個領域」
   的排除照 G7；資源的上限沿用回合本來的步數上限（Web 25 步、評測 20～25 步）。G5 的 3 次留給 4-2 的「同樣的項目再交一次」。
2. **中階失敗（failed）也放行**：跟沒有適合的做法一樣，這一回合放行這個領域的工具（模型沒有回覆、排出的圖沒過檢查時，主對話照現在的方式做，
   不會因為新的一層出錯就做不了）。
3. **中階多一個結果的狀態「使用者取消」**（cancelled）：使用者不回答中階的問題時，中階的紀錄與拓撲圖寫明是使用者取消，報告寫做到哪裡。
4. **報告開頭多列子目標與要回答的項目**：主模型照項目回答時看得到；中階的評測沒有傳子目標與項目，報告不變。
5. **決策圖的連結放在進度裡**：中階的工作一建好就推一行「🔗 決策圖：/topology?…」，頁面把網址變成連結；CLI 印出同一行。
6. **評測的 worker**：中階要問使用者時取消（評測裡沒有人回答，記下問了什麼）；交給領域記一筆，領域裡用到的工具也各記一筆（`via`），
   情境的「用了哪個工具」條件不用改。
7. **主對話與提煉的自我測試拿掉 `DOMAIN.md`**：它們測主迴圈本身（直接執行 ls、cat），分領域在新的高階自我測試（`evals/orch/selftest.py`）測。
8. **中階沒有做完、也沒有報告時，這一回合照現在的方式做**（G7「回到主對話照現在的方式做」照字面做）：不屬於這個領域、使用者取消、
   沒有適合的做法、失敗，四種都放行這個領域的工具；有報告的（做完、死路、熔斷）照舊擋，照報告回答（再交一次帶著原因是 4-2）。
   第一次實作只在沒有適合的做法、失敗時放行，維運評測的兩個情境因此退步（下面 9），對照 HEAD 重跑確認之後改。
9. **第一次真模型評測找到的退步**（新程式 4 次對 HEAD 3 次）：
