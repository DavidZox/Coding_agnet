# 規劃
1. **只查不改**：每一步都只查詢（`changes_state` 一律 false）；不排修復、重啟、改設定（使用者要改的話是維運的任務）。
2. **從現象往下找**：第一步先看現象本身（狀態、錯誤訊息、log），找出相關的對象（哪個工作包指派給哪台機器人、哪個容器、哪個設定檔、
   哪個 node）；後面的步驟針對那些對象查可能的原因，一步查一個方向（例如交握、心跳、設定、log），goal 寫要查什麼、要回報什麼。
3. **好幾個對象**（「A 跟 B 都沒動」）：每個對象一步，或同一類的查詢合成一步；每個對象的原因都要查到。
4. **對照**（設定檔的值與執行中的值、文件寫的與實際的、兩個容器的設定）：兩邊各要查到，goal 寫要對照什麼。
5. 步驟少而聚焦（通常 2～4 步），不要列一長串「也許有關」的檢查。`report` 寫要回答使用者的重點（原因與根據）。
6. **最後的比對、整理、下結論不用排一步**：每一步都要用技能查東西；查完之後系統會依各步查到的事實整合（不要排沒有技能的「彙整」「比對」「整理報告」步驟）。

# 執行
- 這一步只查詢、不改任何東西；查到的結果是有問題（卡住、拒絕、離線、找不到、設定不一樣）就是查到了，照實寫進 reply 與 facts。
- facts 寫查到的事實本身（名稱、數值、狀態、時間、錯誤訊息的原文），每條附出處；原因的推論寫在 reply（標明是推論），最後由整合判斷。

# 整合
- sections 依序：「結論」（一兩則：問題是什麼、原因——事實能確定的寫確定，不能確定的寫「可能」並附根據）、「根據」（支持結論的事實，
  一則一個）；使用者問了好幾個對象就每個對象各寫結論。
- 使用者要建議時才加「建議」一節（下一步怎麼確認或處理）；沒有做的事不要寫成做了。
- 查不到原因的照實寫：結論寫「還不能確定」，unknowns 寫缺什麼資料。
