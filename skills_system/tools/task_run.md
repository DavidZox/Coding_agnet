# 用途
把複雜的任務交給系統：先規劃成 2～6 步（每一步的目標、技能或工作流、會不會改變狀態、做完怎麼檢查）。開頭只查詢的步驟直接做，
查完照查到的事實重排要改的步驟，再把要改的部分給使用者確認（系統會直接問，不用先問使用者；第一步就要改的，開始時就確認整份計畫）。
每一步派一個新的執行者照做：只做那一步的目標、只能用計畫列的技能改變狀態；做完由系統核對它回報的事實、跑那一步的檢查，
沒過就換一個執行者重試一次；還是不行就照查到的事實重排剩下的步驟（最多兩次）。
任務的類型（系統依任務選）：
* **維運**（ops）：要改變狀態的任務（改設定、重新啟動、派工作包、處理交握），可以先查原因再處理。
* **調查**（investigate）：只查不改，原因要查好幾個地方、或好幾個對象各查原因；最後由系統整合成結論（每一則附出處、程式核對）。
* **整理報告**（report）：交班報告、事件時間線、現況整理——從好幾個地方收集資料，由系統整合成報告（每一則附出處、程式核對）。
要寫成檔案的（報告、處理紀錄、記一筆），由系統依核對過的內容寫入、讀回確認（寫檔前使用者確認），不是執行者自己寫。
一兩步就做得完的任務（查一個值、看 log、重啟一個容器）不要用這個，直接用對應的技能；正好是某個工作流的用 workflow_run。

# 語法
`EXECUTE: scripts/task_run_cmd.py "<任務描述>"`：選類型 → 規劃 → 先查 → 使用者確認要改的部分 → 執行 → 整合，一個動作完成。
* 任務描述：照使用者的原話寫完整（名稱、路徑、數值、條件，例如「先備份」「不要動 amr_12」「寫到 notes/x.md」都要帶到）。
* `--continue [<工作>]`：停下來等確認的任務接著做（使用者同意了；系統會再請使用者確認）；`--cancel [<工作>]`：不做了。
* `--profile <類型>`：指定類型（ops、investigate、report）；省略時系統依任務選。

# 範例
`EXECUTE: scripts/task_run_cmd.py "cam_driver 停了，把它重新啟動，確認 /etc/camera.conf 的 fps 還是 30，最後在 notes/cam_driver.md 記一筆"`

# 回傳
`[PASS] 任務完成（N/N 步…）`（寫了報告檔時接著寫「報告寫在 <路徑>」）、`[PASS] 任務的步驟都做了，但第 k 步…檢查沒有通過`、
`[ERROR] 任務沒有做完：第 k 步沒有完成…`，或 `[PASS] ⏸️ 任務…查完了，接下來要改變狀態的步驟等使用者確認`（系統會直接請使用者確認，同意後接著做）。
調查、整理報告有 `## 結論`／`## 報告`：系統整合、每一則附 `#編號` 並核對過出處（找不到根據的拿掉、會註明）。`## 步驟` 每一步一行：
做了什麼、核對過的事實（附 `#編號`＝那一次工具輸出的存檔）、檢查的結果；計畫重排過的列在 `## 計畫改過`。
依結果回答使用者（有〈結論〉就照結論）：引用具體的值、名稱與前後變化；沒做完的說明卡在哪裡、原因與建議。

# 異常
* 規劃不出可以執行的步驟、一步就做得完、正好是一個工作流：`[ERROR]` 寫明改用哪個技能或工作流。
* 只查不改的類型卻要改變狀態（調查、整理報告）：計畫不執行，`[ERROR]` 寫明；要改的任務用 `--profile ops`。
* 使用者沒有同意：`[DENIED]`，等使用者說明要怎麼調整（任務停在原處，同意後 `--continue`，不要了 `--cancel`）。
