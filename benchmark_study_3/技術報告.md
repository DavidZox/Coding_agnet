## 1. 引言

### 1.1 背景與問題

前兩次研究（`benchmark_study/`、`benchmark_study_2/`）的結論是：這個 harness 可以擔任「小而有測試的日常修改」的助手，還不能擔任「只給規格的長任務」
或「大型真實專案的 issue 修正」。使用者據此調整了方向：

1. **編碼任務先集中在小而有測試的專案**——一次改 5～10 個檔案、有測試可以驗證、人會看過才合併；最常見的是「幫我寫測試、確認覆蓋率有沒有涵蓋到」。
   做好之後再慢慢變成單一 agent，以後才用多個 agent 拆解大型專案。
2. **非編碼的任務**也要有像編碼一樣的 orchestrator 與 worker（任務複雜時），將來可以做成技能、應付複雜的非編碼任務：目錄與文件操作、Docker、
   ROS 2，以及使用者比較專用的操作，例如調度系統（fih_rmf_system）裡機器人與 distribute 之間的授權交握。
3. **模型先以 gemma4 系列為主**（26b 與 e4b）。

這次要回答：有沒有適合這兩個方向的資料集？目前的 harness 做得如何？依開發過程看到的問題修改後（v5）有沒有變好？

### 1.2 研究問題

- **RQ1（資料集）**：公開的資料集裡，有沒有能直接量這兩個方向的？沒有的話，要怎麼建？
- **RQ2（小專案的編碼任務）**：在 2～14 個正式程式檔的 Python／C++ 專案上——寫測試（含覆蓋率）、修多個 bug、補回跨檔功能——v4.2 做得如何？
  v5 的改動（覆蓋率、只寫測試的工作、回歸檢查、0 個測試不算通過）有沒有幫助？
- **RQ3（非編碼的維運任務）**：在隔離的沙盒裡真的執行的 50 個情境上，v4.2 做得如何？v5（維運技能、非編碼的 orchestrator、常見情況的做法）
  有沒有幫助？在開發時沒看過的 20 個保留情境上是否一樣？
- **RQ4（非編碼的 orchestrator）**：主對話什麼時候會用它？用了有沒有比較好？代價是什麼？
- **RQ5（模型）**：gemma4:e4b 能擔任哪些部分？

### 1.3 本報告的貢獻

1. **兩組可以在單機上離線重現的資料集**（第 4.1 節）：小專案 62 題（寫測試 18、修 bug 12、補功能 12、Aider polyglot 20），寫測試用覆蓋率＋突變分數計分；
   非編碼 50＋20 個情境，在 Docker-in-Docker 沙盒裡執行（含依 fih_rmf_system 寫的調度系統模擬），以最後的狀態＋回覆＋禁止動作計分。
2. **harness v5**：寫測試與驗證的機制（覆蓋率、只寫測試的工作、回歸檢查、0 個測試不算通過、規劃時試跑驗證指令）；非編碼的 orchestrator（`ops_run`）；
   六個維運技能與主提示詞裡「常見情況的做法」（第 3 節）。
3. v4.2 與 v5 在兩個模型上的比較，每個條件跑 1～3 次，以題為單位配對分析；保留組用來檢查改進能不能推廣（第 5 節）。

## 2. 背景與相關研究

### 2.1 寫測試的評測：覆蓋率不夠，要看突變分數

寫測試的基準多半量三件事：生成的測試在正確的程式上能不能過（validity）、覆蓋率、以及突變分數（把程式改壞一處，測試抓不抓得到）。
TestEval [5] 的單函式題上，7B 模型的行覆蓋率就超過 85%；Al-Ahmad 等 [6] 也發現覆蓋率「接近天花板」——覆蓋率高只代表程式被執行過，
不代表有檢查結果。突變分數比較能區分：TestGenEval [4] 上 GPT-4o 的覆蓋率 35%、突變分數只有 19%。多檔案的專案層級基準有
MultiFileTest（原名 ProjectTest）[2]：Python、Java、JavaScript 各 20 個專案（Python 平均 6.1 個檔、655 行），量正確率與覆蓋率，沒有 C++。
DevBench [1] 有單元測試的生成任務，但給的是規格、不是程式；它的 C++ 覆蓋率用 gcov 量、把測試檔也算進去。C++ 的可執行單元測試基準
在小專案上只有 DevBench 的 5 個 repo（研究筆記 `references/research_notes/coding_datasets_research.md`）。

### 2.2 小專案上的多檔修改

公開的多檔修改基準不是專案太大（SWE-bench、FEA-Bench、NoCode-bench：真實大型 repo，需要 Docker），就是只有單一檔案
（CanItEdit、HumanEvalFix、ClassEval）。Aider 的 polyglot benchmark [3] 是 Exercism 的練習題（C++ 一個 .h＋一個 .cpp、Python 一個檔），
有公開的模型成績可以對照。SWE-smith [7] 用「在可以跑的程式裡植入 bug、只留讓既有測試失敗的」產生修 bug 的任務，這次 BF 用同樣的方法。

### 2.3 非編碼／工具使用的評測

殼層與檔案操作有 AgentBench 的 OS 類 [10]（用檢查腳本在容器裡重算答案）、InterCode-Bash [11]（比對檔案系統的差異）、
Terminal-Bench [13]（用 pytest 檢查容器最後的狀態）。工具使用與有狀態的服務：τ-bench／τ²-bench [8, 9] 用「最後的資料庫狀態＋回覆裡要有的資訊」計分，
並提出 pass^k（k 次都成功）衡量可靠度；ToolSandbox [12] 加上「地雷」（不能發生的動作）。**沒有**現成的資料集涵蓋日常的容器操作
（ps／logs／exec／重啟）、ROS 2 的維運、或調度系統的交握——Docker 相關的基準都在測環境建置，ROS 2 只有沒有任務集的工具框架（ROSA、RAI [14]）。
Bhat 等 [15] 稽核工具呼叫的評測後指出：只比對字串、要求唯一的呼叫順序的檢查跟人的判斷常不一致。這次的非編碼評測因此以**最後的狀態**為主，
回覆的檢查用正規表示式並列出同義的說法。

### 2.4 orchestrator 與 worker

ADaPT [17] 發現「先規劃整份再照表執行」輸給「做不下去才拆解」；InterCode-Bash 上單純重試勝過 Plan-and-Solve [11]。ReWOO [18] 把規劃者與執行者分開、
只傳精簡的結果，token 少 5 倍。MAST [19] 分析多 agent 系統的失敗，驗證不足是三大類之一；Kim 等 [20] 的大規模比較顯示多 agent 在可以乾淨拆開的任務
上大幅勝出，在循序的規劃任務上大幅落後，且沒有集中驗證時錯誤會擴散。TaskBench [22] 顯示小模型拆解任務的能力明顯較差；Routine [21] 則顯示
給模型明確的步驟（routine）能把 Qwen3-14B 從 32.6% 提高到 83.3%。這些結果指向：**只在複雜的任務才用 orchestrator、每一步留給 worker 探索的空間、
由程式集中驗證、常見情況直接給步驟**。

### 2.5 技能

Voyager [24]、Agent Workflow Memory [25]、SkillWeaver [26] 都只把**驗證成功**的做法存成技能；SkillsBench [27] 發現整理過的技能平均 +16.6 分，
模型自己沒驗證就寫的技能反而 −8～−11.5 分。這跟這個 harness 的 `/make_skill`（從做對的對話整理成流程技能，使用者核准）方向一致，第 6 節討論
怎麼把非編碼的 orchestrator 走向技能。

## 3. 系統：v5 的改動

v5 在 v4.2 上修改；所有改動都在凍結副本裡（附錄 D）。細節見 `doc/設計筆記與已知限制.md` 2.17 節。

### 3.1 寫測試與驗證

| 改動 | 做什麼 | 依據 |
|---|---|---|
| `code_test --coverage` | Python：coverage.py（含分支）；C／C++：編譯器包裝自動加 `--coverage`＋gcovr。在暫存副本裡量，只算正式程式，列出每個檔案的行／分支覆蓋率與沒測到的行 | 使用者要「確認覆蓋率」；DevBench 自帶的量法把測試檔也算進去 |
| 只寫測試的工作 | 任務只要求寫測試時：worker 只能改測試檔；每一項的測試通過後量覆蓋率，被測的檔案低於 90% 就把沒測到的行交還一次；程式像有 bug 時照目前的行為寫或標成預期失敗 | 寫測試的任務規定不能改正式程式；worker 遇到看起來像 bug 的行為時，最省事的做法是去改程式讓測試通過 |
| 沒有斷言的測試不算完成 | Python 用 AST、C++ 看 TEST 主體 | 只呼叫函式的測試也會提高覆蓋率，但抓不到錯 |
| 0 個測試不算通過 | `code_run`／`code_test` 一個測試都沒跑到時回錯誤；規劃時先把驗證指令試跑一次，有問題交回規劃者 | 第二次研究：SWE-bench 有 3 題驗證一個測試都沒跑到卻判定通過 |
| 回歸檢查 | 開工前跑一次整個專案的測試當基準；每一項與整體驗證都檢查原本通過的測試 | 第二次研究：修好了卻弄壞既有測試 3～4 題 |
| 報告 | 測試數的前後、覆蓋率、計畫以外新增的檔案 | 人要審查 |

### 3.2 非編碼的 orchestrator（`ops_run`）

主對話用一個動作 `ops_run "<使用者的原話>"`。確認關卡先規劃：規劃 session 輸出 2～6 步，每一步的目標、技能、會不會改變狀態、做完用哪個唯讀技能檢查；
程式檢查計畫（技能存在、會改變狀態的步驟都標出來、一步就做得完的交回主對話），把具體的問題交回規劃 session 修一次。**確認畫面就是整份計畫**，
核准＝計畫裡標明會改變狀態的步驟都核准了；都只查詢的計畫不用確認。執行時每一步派一個乾淨的 worker（只看得到任務、這一步的目標、前面各步的結果摘要），
計畫沒核准的狀態變更一律擋下（`[DENIED]`）；做完由程式跑那一步的檢查，沒過就換一個 worker 帶著檢查的輸出再做一次；worker 自己回報做不到兩次才停。
最後把每一步的結果交還主對話。依據見 2.4 節：只在複雜的任務才用（主提示詞寫明「4 步以上、跨領域、或要改好幾個狀態」）、集中驗證、只傳摘要。

開發時看到並修正的問題（都在 50 個主要情境上看到，見 3.4 節）：主對話規劃完就停下來問使用者「要開始嗎」（→ 一個動作完成、只查詢的不用確認）；
「先不要修改、查原因」被當成要先看計畫（→ 主提示詞明寫）；worker 在一個字串裡失控、一次輸出三萬多個 token（→ 每個字串加長度上限）；
worker 改好檔案後一直做額外的檢查、用完步數被當成失敗（→ 用完時請它總結）；規劃者寫的檢查條件不適用（例如要「看到 0」）讓做完的步驟失敗
（→ 第二次還是沒過就標成「檢查沒過」、不擋後面的步驟）；回覆協議把 command 與 args 裡重複的參數接在一起（→ 只留一份）。

### 3.3 維運技能與主提示詞

| 技能 | 做什麼 | 開發時看到的問題（v4.2） |
|---|---|---|
| `file_ops` | 建目錄、複製、移動、寫入／附加、取代剛好一處（先備份） | 改設定檔、寫報告只能交給 coding orchestrator 或用 host_runcmd 寫殼層指令 |
| `docker_ctl` | 容器本身的狀態、log、設定；啟動／停止／重啟 | 找容器的 ERROR 時跑進容器裡 grep 整個檔案系統 |
| `ROS2_param` | 執行中的參數 list／get／set | 回答「現在的參數」時讀了設定檔（值不一樣） |
| `ROS2_topic_pub` | 對 topic 發布訊息 | — |
| `rmf_handshake` | 交握診斷（離線、沒回應、回 no、完成訊號遺失）、手動回 yes／no、補發完成訊號 | 把機器人當成容器去找；只看工作包狀態分不出原因 |
| `csv_query` | CSV 的篩選與每一組的最大／最小／平均（數字由腳本算） | 用 python 單行指令算資料：猜錯欄位名稱、沒有 pandas、引號跳脫，錯了就反問使用者 |

另外：`docker_est` 可以指定容器名稱與指令（v4.2 只能建出跟映像檔同名的容器）；`ROS2_topic_echo` 的頻率改用訊息到達的時間算（以前 2 Hz 算成 1.6 Hz）。
主提示詞（`AGENT.md`）新增「Operations」一節：檔案先在工作目錄找、執行中的參數以 ROS2_param 為準、什麼時候用 ops_run、「先不要修改」是只查詢、
**常見情況的做法**（工作包卡住：工作包狀態 → 交握診斷 → 只有完成訊號遺失且使用者要處理時才補發；容器停了；改設定檔），以及文件與 CSV 用哪個技能。

### 3.4 開發過程與保留組

v5 是在一個獨立的沙盒（另一個 DinD daemon）上用 50 個主要情境的一部分反覆試出來的：先跑 v4.2 的第一次評測、看失敗紀錄，再改、再跑。這表示
**v5 在主要情境上的分數會偏樂觀**（調整時看過這些情境）。為了量推廣性，另外寫了 20 個**保留情境**（每個領域 4 個）：在 v5 調整之前寫好、
參考解與「什麼都不做」的驗證通過後就不再看，也不拿來調整。它們用同一個沙盒，但問法不同、或是同一類操作的新變化（例如：別的欄位與統計、照手冊先備份再改、
別台機器人的交握問題、診斷後寫報告）。小專案的任務也有同樣的問題：開發時只用了 3 題（bf_readtime、tw_readtime、tw_xlsx2csv）試跑 v5 的機制，
沒有拿全部的題目調整。

## 4. 方法

### 4.1 資料

**小專案（`datasets/small_projects/`，62 題）**。每一題是一個工作區範本加上一段像使用者交代工作的任務說明（附錄 A 列出每一題的大小）。

| 類別 | 題數 | 來源與做法 | 計分 |
|---|---|---|---|
| TW 寫測試 | 18（Python 13、C++ 5） | DevBench 12 個 repo 的參考實作，拿掉全部的單元測試；ProjectTest／MultiFileTest [2] 的 6 個 Python 專案（slugify、stock2、structly、blackjack、leducholdem、limitholdem；原本就沒有測試）。任務：寫單元測試、量覆蓋率、回報還沒涵蓋的部分；不能改正式程式 | 測試在原本的程式上通過的數量（失敗與「預期失敗／跳過」分開記）；通過的測試對正式程式的行／分支覆蓋率；**突變分數**；有沒有改正式程式；沒有斷言的測試 |
| BF 修 bug | 12（Python 7、C++ 5） | DevBench 參考實作植入 3 個 bug（AST 或 token 層級的突變：運算子、比較、常數、條件），每個都讓官方單元測試失敗，分散在 1～3 個檔案（7 題跨 2 個以上）；任務列出失敗的測試名稱 | 官方的單元＋驗收測試**全部通過**才算解決；另記有沒有改測試 |
| FE 補功能 | 12（Python 7、C++ 5） | 參考實作拿掉一個跨 2～5 個檔案的功能（連同那個功能的單元測試），任務像需求說明，寫清楚行為 | 同 BF |
| AP 練習題 | 20（Python 10、C++ 10） | Aider polyglot [3] 的 Exercism 題（各語言挑 10 題），只有說明與骨架；**只當能力對照** | 官方測試全部通過 |

突變體（`mutants/`）：DevBench 的題目每個 repo 先用官方測試跑過全部的突變點，只留官方測試抓得到的（每題 4～45 個）；TW 的突變分數＝agent 的測試
抓到的 ÷ 這些突變體，所以參考答案（官方測試）是 100%。ProjectTest 沒有官方測試，每題用 60 個有效的突變體，是絕對分數，只在同一題內比較版本。
突變體記下 AST 節點或 token 的編號，計分時套到同一個位置；計分程序用參考解跑一次，官方測試抓不到的標成 unstable、不計分（只有 1 個）。
**驗證**：用參考實作與官方測試跑每一題的計分（`tools/score.py verify`），TW 的突變分數都是 100%、BF／FE／AP 都全部通過（56/56；ProjectTest 的 6 題沒有參考測試）。

**非編碼的維運任務（`datasets/ops_suite/`，50＋20 個情境）**。

| 領域 | 主要組 | 保留組 | 內容 |
|---|---|---|---|
| 目錄與文件 | 12 | 4 | 找設定值在哪個檔案、統計 log、比對設定檔、改一個參數、整理 CSV 寫成報告、搬資料夾、用範本建資料夾、路徑打錯、依文件回答 |
| Docker | 10 | 4 | 容器總覽與結束碼、看 log 找錯誤、容器裡的設定與環境變數、診斷為什麼停了（先不要重啟）、建／停／重啟容器、名稱不完整 |
| ROS 2 | 10 | 4 | node 與 topic、電量與位置、執行中的參數、domain 不同看不到 topic、觀察移動、頻率、對 topic 手動回 handshake |
| 調度交握 | 10 | 4 | 派工單並追到完成、診斷卡住（機器人回 no／沒回應／離線）、補發遺失的完成訊號、取消、OverPending、手動回 yes、語意站名 |
| 複合任務 | 8 | 4 | 處理卡住的工作包並寫紀錄、交班報告、重啟並驗證再記錄、改派、照 CSV 批次派工、改設定再派工、domain 問題的修正與確認、事件時間線 |

沙盒是一個 Docker-in-Docker daemon：agent 的 docker 技能透過 `DOCKER_HOST` 只看得到它，碰不到主機上真的容器。裡面有 5 個一般容器
（web_cache、log_writer、nav2_test、db_backup、scratch_tools，各有固定的設定、環境變數、log 與結束碼）與 `rmf_sim`——依 fih_rmf_system 的行為寫的
調度系統模擬（ROS 2 Jazzy＋`fih_rmf_msgs` 的訊息定義）：distribute 每 0.5 秒對選中的機器人授權、逾時進 OverPending 冷卻後重試、機器人回 yes 後 confirm、
做完發 task_exec_fin、orchestrtor 收到才派下一站；web_console 的 HTTP API（派工、查狀態、取消）與 manual_trigger（手動回 yes／no、補發完成訊號）；
機器人的行為可以設定（正常、忙碌回 no、不回應、遺失一次完成訊號、離線、走得慢）。檔案沙盒是固定內容的維運工作目錄（機隊與導航設定、6 天的 log、
2,260 筆的電量 CSV、交握規則與維運手冊、任務範本、交班紀錄）。每個情境開始前整個重建。

計分以**最後的狀態**為主（τ-bench [8] 的做法）：檔案快照的差異、容器的狀態、rmf_sim 的事件紀錄與工作包狀態；加上回覆裡要出現的事實（字串或正規表示式，
列出同義的說法 [15]）；**禁止動作**（ToolSandbox [12] 的「地雷」：動了沒交代的容器、取消了不該取消的工作包、對沒在運作的機器人強行回 yes、改了範圍以外的檔案…）
發生任何一個就算失敗。答案都由沙盒的內容事先算好。**驗證**：每個情境的參考解法（直接操作沙盒、不經過模型）都拿滿分（70/70）；
什麼都不做、只回一句「不知道」時每一個都不及格（70/70）。

### 4.2 執行環境

- **凍結的副本**：兩個版本各一份（`~/cah_eval/v4.2`、`~/cah_eval/v5`），評測期間在專案目錄的修改不影響結果；評測程式（`evals/`）兩份相同（附錄 D）。
- **模型**：評測專用的 Ollama（版本 0.34.4，127.0.0.1:11435，預設的 f16 KV cache，num_ctx 32768，temperature 0.2，thinking 關閉）；gemma4:26b（25.2B MoE，
  每個 token 約用 4B）與 gemma4:e4b（7.5B），都是 Q4_K_M。Gemma 4 模型卡 [16] 的 τ2（三個領域平均）：e4b 42.2、26b 68.2。
- **硬體**：RTX 5090（32 GB）、Ryzen 9 9950X3D、123 GB 記憶體；評測期間 Isaac Sim 同時在跑（佔 6.2 GB 顯示記憶體），跟第二次研究相同。
  所有評測排在同一個 GPU 佇列裡依序執行，不會同時跑兩個；開發用的沙盒在正式評測開始前停掉。
- **非編碼**：每個情境在臨時的 harness 副本裡跑主對話（比照 CLI 的 auto 模式：工具結果自動加入、連續執行到模型不再下 action，每個使用者訊息最多 25 輪），
  工具都真的在沙盒裡執行；確認關卡依情境自動回答（這次全部是同意，等同使用者核准所有要求執行的動作——所以「該不該做」要靠禁止動作來量）。
  每個情境 30 分鐘上限。
- **小專案**：每一題在臨時目錄複製工作區範本，用 coding orchestrator 跑一個 job（跟 DevBench 同一個 `job.py`：計畫自動核准、某一項失敗就跳過），
  存下改了什麼（patch），計分在背景執行緒（不擋下一題）。每一題 40 分鐘上限。

### 4.4 指標與統計

- **通過率**：所有執行合起來的比例與 Wilson 95% 區間（同一題跑好幾次不獨立，區間只是參考）。**pass^k**（τ-bench [8]）：k 次都通過的題目比例，量可靠度；
  pass@k：至少一次通過。
- **版本比較**（同一個模型）：每一題先算各版本的平均（通過率或分數），以題為單位配對：勝／負／平手與符號檢定（雙尾、精確二項，平手不算），
  差值的 95% 區間用以題為單位的 bootstrap（B=10,000，固定亂數種子）。
- **非編碼**另記：工具呼叫數、確認關卡次數、模型呼叫數、秒數、禁止動作；v5 另記主對話有沒有用 ops_run、計畫的步數與結果。
- **小專案**另記：秒數、模型呼叫數、改了幾個檔案；v5 的機制有沒有被觸發（從 job 的事件文字判斷：回歸檢查、覆蓋率交還、0 個測試、沒有斷言）。
- 回覆的檢查若事後發現漏了同義的說法，修正情境後**兩個版本的全部紀錄一起重算**（只重算回覆類的檢查，狀態類的沿用評測當時的結果；附錄 D）。
