## 架構整合（驗證過的做法）

2026-10～11 的架構整合把多步驟的機制整合成通用的元件。下表是那時驗證過的做法與它們現在在程式的哪裡，新寫的通用元件先沿用這些（討論紀錄第 6 節）：

| 做法 | 現在在哪裡 |
|---|---|
| 事實由程式產生、模型只寫說明；句子的意思跟事實核對 | 數據分析（`analysis_job.py`、`claims.py`；在子工作階段裡執行的也照它核對）；中階的報告由程式照收據整理（`mid.py`）。句子的意思只有數據分析有 |
| 每條事實附出處（行號），程式核對名稱與數值，只把對不上的那幾條交回修一次 | 提煉（`extract.py` 的 `missing_tokens`、`_repair`）；依報告回答與子工作階段收尾的 answers（`answers.py`，出處是 檔案:行號 或 #編號）；中階的合約與判斷節點（抄的原文由程式核對，`mid.py`、`judge.py`） |
| 「做完了沒」由程式判斷：每一步的檢查、最後的成功判準 | 低階照收據守門（`edg.py` 的 expect、complete）；中階的不收斂與熔斷（`mid.py`）；answers 的核對（`answers.py`） |
| 模型只填要填的欄位（schema 只有那幾個名稱），前面決定過的值沿用 | 中階的合約：schema 只有技能的參數，再交時子目標沒提到的參數沿用上一次（`mid.py`、`schemas.py`） |
| 中間產物與最終產物都存檔（`job.json`、`calls.jsonl`、`events.jsonl`） | `jobstore.py`：`logs/` 的 `extract_jobs`、`analysis_jobs`、`edg_jobs`、`mid_jobs`、`sub_jobs` |
| 程式整理好的報告不再交給提煉 | `protocol.is_exempt_result`：數據分析的報告、交給領域的結果（`DOMAIN_RESULT_HEAD`） |
