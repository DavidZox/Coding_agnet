## 1. 方向（2026-11-23 使用者決定）

```
主 session ──任務（子目標、要回答的項目）──▶ 領域 session
     ① 選領域（可以多個）→ 程式載入這些領域的技能清單
     ② 從清單選「一個」技能＋參數
     ③ 程式執行（技能自己的骨架與回退）
     ④ 結果太長 → 分段 worker 提煉（太長再提煉）
     ⑤ 看提煉結果：回報／再選技能（回 ②）／再選領域（回 ①）
     每一步的狀態是固定格式，由程式管，全部存檔
主 session ◀──經過與結果──
     做完了回答使用者；還沒就帶著這次的經過再交一次
```

- 為什麼：三階層（高階分工、中階合約＋骨架＋判斷節點、低階執行器、沒有報告接子工作階段）每一層各有自己的協定與狀態，修一個地方要動
  好幾層；後面幾次改進（B、C、A′、A″）都沒有贏 A。使用者要先把基礎做好，再想怎麼往上加。
- 留下試出來有用的：程式組命令（技能＋參數表單，參數附原文、程式核對）、骨架把穩定的步驟寫死、收據讓檔案:行號由程式核對、提煉的事實
  附行號並核對、全部存檔。
- 補三階層試出來的弱點（設計筆記 2.55）：開放的 session 讀和答不穩 → 讀交給提煉；命令列參數寫錯 → 選技能用表單；花步數載入工具說明 →
  技能清單事先載入；沒有新資訊的重做沒用 → 領域 session 看完提煉的結果才決定下一步；第一步選錯最多 → 在迴圈裡改選。
- 風險：同一個 session 要選領域、選技能、決定做完，e4b 可能吃力；靠固定格式的狀態、上限、擋重複來管。分數用真實專案評測跟 A 比。

  - 做法（都在單一迴圈裡，由程式核對；不加層、不加判斷節點）：
    1. **交辦的項目附原話**：每一項寫成 {quote, item}——quote 從使用者的話一字不改地抄（程式核對，同參數表單的原文核對；預設的原文範圍是這段
       對話裡使用者的每一則訊息，追問時項目的原話可能在前一則），item 可以把「它」這類指代補上名稱。領域 session 看到的每一項都帶著原話，
       說明改成「項目的意思以使用者的原話為準」；提煉的錨點也帶原話。程式不用判斷意思有沒有變窄，下一步直接看得到原話。
    2. **回答的完整性**：主 session 依報告回答時，報告裡這一項的回答寫的編號與數字，回答裡要有（認法用 answers.answer_problems 現在用的同一套、
       方向反過來）；漏了的交回修一次（跟現在的核對同一個地方：orchestrator.domain_reply_check）。名稱先不核對（寧可漏掉也不誤擋）。
